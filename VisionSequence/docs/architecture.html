Architecture

For anyone maintaining or extending the platform. It shares its thinking with Workflow design, but the engine is an in-process dataflow measured in milliseconds.

0. The whole thing on one page

Editing                                Running                                  Watching
GET /vision/tool-types ──▶ React Flow ──PATCH graph──▶ Flow.graph
                                                         │ compiled, cached by version
POST /flows/{id}/run ─┐                                  ▼
TCP "RUN 1"          ─┼─▶ Runner.submit ─▶ ThreadPool(10) ─▶ engine.execute (topological order)
continuous loop      ─┘        │ one run at a time per flow │ Tool.execute(ctx) → Result
                               ▼                            ▼
                        EventBus.publish ◀──── RunReport (node status, outputs, overlays, image refs)
                               │                            │
                               ├─▶ SSE /flows/{id}/stream   ├─▶ ImageStore (numpy, LRU) → GET /images/{ref}
                               └─▶ background Persister → FlowRun (a summary)

Four sentences:

  1. The graph is one JSON document in Flow.graph; the editor saves it whole and the engine reads it whole.
  2. Execution happens in memory: a run walks the graph in topological order on one thread of the pool, with images as numpy arrays that never touch disk.
  3. Tools are a registry: the engine knows no particular tool, and the palette and parameter forms come from catalogue(), so adding a tool needs no front-end change.
  4. Watching is push: results go onto an in-process event bus and straight out over SSE, and an image is only encoded as a thumbnail when somebody looks at it.

The graph JSON

{"nodes": [{"id": "blob-1", "type": "blob", "label": "Holes", "description": "", "enabled": true,
            "continue_on_error": false, "color": "", "params": {...}, "position": {"x": 0, "y": 0}}],
 "edges": [{"id": "e1", "source": "gray-1", "source_handle": "image", "target": "blob-1", "target_handle": "image"}]}
  • source_handle and target_handle are port keys; left blank, validate_graph fills in the first port.
  • Implicit ports: every executable node has an input _flow (control branching) and an output _overlays (that node's overlays, a list).
  • type: "note" is a sticky note: never executed, nothing can connect into it, and a dashed line drawn out of one is ignored by the engine.

2. The tool framework (apps/vision/tools/base.py)

Param(key, label, kind, required, default, help_text, options, unit, minimum, maximum, step, visible_when, shapes, accept, group, teach)
  kind ∈ text | multiline | number | boolean | select | range (slider) | roi | source | asset | color | json | expression | output_key | code
Port(key, label, type, required, multiple, tone)
  type ∈ image | region | number | bool | string | points | contours | matches | list | any | flow
flow_out(key, label, tone)             # a control branch output handle
ToolContext: run_id, flow_id, node, inputs, context, moment, log, asset_path(id), grab(source_id), preview
  .param/.number/.integer/.flag/.image/.require_image/.roi
Result(outputs, overlays, branch, status=ok|ng|error, message, detail, context, overlay_on)
class Tool: key label description category icon params inputs outputs heavy accepts connection_params; execute(ctx) -> Result
register(tool) / get(key) / catalogue()

Param.kind is a closed set: one case in the front end's ParamField switch, one entry in the backend's PARAM_KINDS, and register() rejects anything else.

Overlay coordinates are always the full-image coordinates of that node's input image. A tool working inside an ROI uses crop(image, region, upright=True) from tools/roi.py and maps back with Crop.to_full() or points_to_full(); the inverse matrix for a straightened rotated rectangle is in Crop.inverse.

What failure means: not finding something is status="ng" or a branch (not_found), not an error. An expected error — the ROI outside the image, a missing asset — is raise ToolError. Any other exception is caught by the engine and recorded as an error with its repr (and a traceback during preview).

Control branching: a tool returns branch="true" and the engine only executes downstream nodes wired to the true handle; nodes not selected are marked skipped, and so is everything downstream of them.

Each tolerance_judge appends {name, value, nominal, upper, lower, unit, spec_source, in_spec} to run.outputs.tolerances, so FlowRun.outputs keeps the drawing reference.

3. Validation and compilation (graph.py)

validate_graph() runs on save (PATCH) and on submit: node and edge count limits, unique ids, the type present in the registry (the error lists the available keys), both ends of an edge existing, the ports existing, type compatibility (_compatible: identical, any, number→string, bool→number, points/matches/contours→list; a flow port only connects to _flow), no two edges into a single-connection input, nothing connecting into a note, and the graph being acyclic (a Kahn topological sort).

compile_graph() produces CompiledGraph(order, nodes{id: CompiledNode(tool, inputs{port: [(src, port)]}, flow_inputs, primary_image_port)}, consumed). consumed is the set of (node, port) pairs somebody uses — an image output nobody reads never enters the cache.

4. The engine (engine.py)

for node in order:
    timed out → error, break
    has flow_inputs but no (source ok/ng with a matching branch) → skipped
    gather inputs: an upstream skipped or errored node on a required port → skipped;
                   a required port left unconnected (unless the tool allows it) → skipped
    enabled=False → pass an image straight through if one goes in and out ("disabled (pass-through)"), otherwise skipped
    result = tool.execute(ctx)   # ToolError → error; any other exception → error plus its repr
    register the outputs (an image only enters store.put when consumed, during preview, or for a source/output tool),
    _overlays, and merge context
    during preview, detail._input_ref is the input image ref, so the viewer can show "what this node saw"
run.status: any error without continue_on_error → failed; any ng, or _judge=ng → ng; otherwise ok
run.outputs = context["_outputs"], written by the judge and output tools

No tokens, no database, no sleeping: a run is a function call, and that is where the millisecond figures come from.

5. Runner and concurrency (runner.py)

ComponentWhat it does
ThreadPoolExecutor(MAX_WORKERS=10)The ceiling on flows busy at once; raise it in .env. The vision algorithms run in native code and release the GIL, so several threads really are parallel (12 flows measured at 40 ms).
FlowRuntime (per flow)The compile cache (keyed on version), a lock so one run happens at a time (the camera and the state must stay consistent), the queued count (over MAX_QUEUE_PER_FLOW → 429), the statistics, the recent RunReports, and the continuous loop.
_prefetch()On the caller's thread, opens the sources named by source parameters and resolves the paths of asset parameters — so the hot path inside the pool never touches the database.
EventBusA Condition plus a 500-entry ring buffer; SSE takes the increment with wait(since), and a reconnection sends its seq so nothing is missed.
PersisterA daemon thread with a 5000-deep queue, bulk-creating 100 at a time and trimming every 500. A foreign-key failure (the flow was deleted) skips that row.
VariableStore (variables.py)Flow and station variables: memory is the source of truth (the hot path never touches the database), loaded on the caller's thread before a run, written back by the persister every two seconds and write-through from the API; preview, batch and trial runs write to a per-run overlay instead.
ContinuousLoopOne thread per flow, carrying the Flow object and only going back to the database every two seconds to check for a disable or a settings change, at continuous_interval_ms.
Engine state lives in the process: there can be only one API process (manage.py serve is uvicorn with workers=1 plus TCP). Scaling out would mean extracting the engine into its own service, which is deliberately not done.

6. The image cache (images.py)

A ref is "{run_id}:{node_id}:{port}". Each flow keeps the images of the last KEEP_RUN_IMAGES runs, with a global LRU by bytes up to IMAGE_CACHE_MB. encode(ref, max_side, fmt, quality) is deferred until somebody asks and shrinks to the requested longest side (the front end defaults to 1600). Floating-point and 16-bit images are normalised to 8 bits for display.

5-1. Retention and the hourly roll-up

  • Four tiers: the image archive (ARCHIVE_DAYS, ARCHIVE_MAX_GB) → run detail in FlowRun (KEEP_RUN_DAYS, 30 by default, with KEEP_RUN_ROWS as a backstop) → the hourly roll-up FlowRunHourly, kept forever at 8760 rows a year. → the measurement log (MeasurementLog: one row per numeric named output per run, written in the same background batch, kept MEASUREMENT_DAYS = 365 days by default and independent of the run detail; it feeds the Measurements tab of the Statistics page and the dashboard alerts)
  • It used to be 2000 rows per flow and nothing else — at one run a second that is 33 minutes of history, quality assurance finds nothing the next day, and how far back you can look depends entirely on the cycle time.
  • _Persister._rollup accumulates the roll-up in the same batch that writes the detail (F() increments and Greatest for the maximum duration; one row per flow, hour, station and recipe). GET /flows/{id}/stats now reads the roll-up, so the yield curve stays complete after the detail is purged or the server restarts.
  • Operations commands: manage.py backup (an online SQLite backup plus the assets and a manifest; --with-images includes the archive), restore (zip-slip protected, keeping a copy of the old database), purge --dry-run and doctor (version, disk, data volume, ports, connections, DL and accounts; exit code 1 when something is wrong).
  • One source of truth for the version: __version__ in apps/vision/__init__.py, read by /healthz, /vision/integration/info, the bottom of the sidebar and doctor.

5a. The audit log (apps/core/audit.py, core.AuditLog)

  • Changes only, never runs: runs already have FlowRun, statistics and the image archive; putting them here would flush out the real edits.
  • Endpoints call audit.record(request, "flow.update", flow, summary=…, detail=…) explicitly rather than going through middleware — what we want recorded is meaningful actions, not HTTP traffic. It is currently on flows (create, graph change, settings change, delete, restore, release), recipes (create, changeover), source deletion, connections (create, modify, delete), accounts (create, modify, delete) and the engine lock.
  • A flow's graph is diffed at parameter level by graphdiff ("threshold 60 → 46"); everything else uses audit.fields_diff. detail is bounded in length and count by _clip.
  • A failed write never affects the request (record raises nothing): a broken audit trail is bad, but a line stopped by a broken audit trail is worse.
  • API: GET /vision/audit (administrator; filterable by action, actor and keyword) and GET /vision/audit.csv (UTF-8 with a BOM, so Excel opens it). Retention is VISION_AUDIT_DAYS (730 by default, 0 for forever). In the interface: /audit.
  • The trap: on an auth=None endpoint ninja does not set request.auth, so the identity has to come from what authenticate() returned. Calling principal(request) there reads request.auth and raises 401 on its own.

5b. Version history (versions.py, graphdiff.py)

  • FlowVersion(flow, version, graph, saved_by, saved_at, note, is_released): the version increments and a snapshot is stored only when the graph really changed (saving the same graph creates nothing). Creating a flow records version one with note="created".
  • The diff is written for a person (graphdiff.diff): parameter changes are listed one by one (node, parameter, before and after), structure is reduced to counts (nodes added or removed, edges changed), and a pure canvas move is not a change at all. summarize() produces a one-line "threshold 60 → 46, +1 step" for the list.
  • Restoring creates a new version rather than rewriting history: versions.restore saves the current version first, then writes the old graph as the next one (note="restored from vN").
  • Release is only a marker: is_released exists for quality sign-off and blocks nothing. Retention (KEEP_VERSIONS, 50 by default) always keeps released versions.
  • API: GET /flows/{id}/versions, GET /versions/{v} (with the diff against the current version), POST /versions/{v}/restore and POST /versions/{v}/release. In the interface, the "Versions" button in the editor toolbar (components/flow/VersionPanel.tsx).

6b. The image archive (archive.py)

  • Why: images.ImageStore keeps only the last KEEP_RUN_IMAGES runs per flow and dies with the process, so "what did the camera see when that reject went through" had no answer.
  • Where: files go to <parent of ASSET_DIR>/archive/<flow_id>/<YYYYMMDD>/<run_id>-<node>-<port>.jpg (VISION_ARCHIVE_DIR moves it to a bigger disk), with the paths recorded in FlowRun.images.
  • It stays off the hot path: the engine thread only takes a reference to the image in _record — no copy, no encode — and the encoding and writing happen on the existing _Persister background thread. When the persistence queue is deeper than QUEUE_LIMIT archiving is skipped: the line comes first, and it is better to store less than to block.
  • Policy: Flow.archive_policy overlays VISION_ARCHIVE_DEFAULT, with mode off/ng/all, pictures result (the source and the result) or all, plus an OK sample rate, the format and the quality. The shipped default is off.
  • Reading back: GET /vision/images/{ref} falls back to the archive when the image is no longer in memory — the front end need not know where it lives.
  • Purging: archive.purge() goes by age first and then by total size (oldest first), run by the persistence thread every 500 rows; and when a FlowRun row ages out, its files go with it.

7. Image sources (sources/)

open_source(model) builds a Grabber by kind and caches it (reopened only when updated_at changes). Built in: folder (looping through files, sorted, with a pattern), file (re-read when the mtime changes), capture (a camera on a capture client, see Capture client), synthetic (a synthetic part with random offset and rotation and a 30% chance of a missing hole or a scratch, so a complete flow can be built with no camera) and upload (pushed through the API). Plugins: a .py subclassing Grabber dropped into plugins/ loads automatically (or VISION_SOURCE_PLUGINS=gige=mypkg.gige:GigEGrabber); see Plugins. A Grabber is called from several threads at once and must lock internally.

The capture client (kind=capture, apps/vision/capture/): hub.py's CaptureHub listens on the capture port (9100) when manage.py serve starts, giving each connected client a ClientSession thread (the handshake, authentication, the channel table, attaching shared memory, receiving frames and waking anything pending — and never touching the ORM). CaptureGrabber.grab() asks the session for a fresh frame or takes the latest depending on the mode, returning an ndarray it owns outright, and channel_status() gives the source list its connection state and fps. The protocol constants are shared with the client through vscapture/protocol.py, the one dependency-free module the server imports. The details, the protocol tables and the performance figures are in Capture client.

8. API, SSE and TCP

The complete list is in the docstring at the top of apps/vision/api.py; how to integrate is in Automation. The highlights:

  • POST /flows/{id}/run: JSON, or multipart with an image; wait, timeout_s and include_nodes (node outputs are excluded by default, so a production response stays small).
  • POST /flows/{id}/preview: runs an unsaved graph and keeps every intermediate image; reuse_image_ref pins the picture while tuning.
  • Preview's until_node and analysis: the tool page runs only as far as that step (graph.restrict_to() takes the ancestor subgraph) and returns a histogram and value distribution. POST /flows/{id}/scratch-image puts an image in the cache without adding it to the source library, and DELETE /flows/{id}/recent resets.
  • GET /images/{ref}?max=&fmt=, GET /flows/{id}/recent, GET /flows/{id}/runs (from the database) and GET /flows/{id}/stats (hourly OK/NG).
  • SSE bypasses ninja (routed directly in config/urls.py): hello, stats, run_queued, run_started, run_finished, continuous, ping, bye. It closes after 55 seconds and the client reconnects with its since; a client that has heard nothing (ping included) for 40 seconds reconnects on its own.
  • TCP (tcp_server.py): one command per line, one JSON per line. RUN <flow> k=v returns the result synchronously. One thread per connection, all going through the same Runner.
  • The key is optional (VISION_API_KEY). An <img> tag and EventSource cannot send headers, so the image and stream endpoints also accept ?api_key= or ?token=.

9b. Accounts, ownership and the engine lock (apps/accounts)

  • Identity (security.py): Principal(kind) — integrator (X-API-Key = VISION_API_KEY, a machine identity), user (a Bearer token, stored as SHA-256, 14 days by default) and bootstrap (allowed while there are no users, so /auth/setup can create the first administrator). The image and SSE endpoints accept ?token=.
  • Roles and permissions (UserPref.role, the closed set accounts.models.ROLES): admin (kept in step with User.is_staff), engineer (the default) and operator. What each role may do is not hard-coded: accounts/permissions.py holds the closed set of functions (FEATURES: flows.run, flows.teach, flows.edit, sources, assets, batch, golden, dl, agent, integration, connections, audit) and an administrator ticks them per role on the Users page (RolePermission, one row per role; no row means the factory default, which is exactly the old three tiers). The gatekeepers are require_feature(request, "<key>") and require_admin (accounts, permissions, system settings — never delegable, or an engineer could promote themselves). Principal.can() reads the row once per request and remembers it, so a check costs at most one indexed query.
  • A flow belongs to the line, not to a person: _visible_flows returns every flow to any signed-in user and can_edit_flow looks only at the role. Flow.owner degrades to "who created it", used for display and the ?mine=1 filter.
  • The operator's parameter boundary (apps/vision/teachguard.py): for an operator, PATCH /flows/{id} only allows a change where no field outside the graph moved and the only difference between the old and new graphs is the value of Param.teach=True parameters; anything else is 403 teach_only. The list of adjustable parameters is exactly the teach flags the tools already carry (58 of them), maintained nowhere else. A changeover goes through POST /flows/{id}/recipes/{rid}/activate, which an operator may use; editing a recipe's contents still needs an engineer.
  • The engine lock: a single EngineLock row. An integrator or an administrator POSTs to /vision/lock (with a reason and a ttl_s). While locked, run, preview and continuous return 423 engine_locked and editing is unaffected; locking stops every continuous run and broadcasts an SSE lock event; the integrator and the holder are exempt; and the TCP interface counts as an integrator. The interface shows a banner and disables the run buttons.

9c. Templates, batch testing and the integration tools (api_more.py)

  • Templates: the built-in ones are produced by builders in demo.py with a {SOURCE} placeholder, and a saved one goes into FlowTemplate. instantiate substitutes the source id back and can prefix node ids to avoid collisions. A template is never tied to one machine's source id, which is what makes "click and it works" possible.
  • Batch testing: each image runs in preview mode (its images stay in the cache) and comes back with its verdict, outputs, failing node and source image ref. Up to 50 images, bounded by KEEP_RUN_IMAGES, with older ones released. (The stored, larger batch workbench is Batch testing.)
  • The integration tools: integration/tcp really connects to the local TCP port and sends a line (when the port is closed it calls handle_command directly and marks the result via=direct), so an integrator can verify the exact string their equipment will send, from a browser.

9d. Teach page, recipes, Golden Set and Modbus

  • Param.teach: a tool marks the parameters that need teaching on the line, the teach page (/flows/:id/teach) lists only those and previews up to that step live, and while Flow.commissioned is false a RunReport carries a warning without being blocked.
  • FlowRecipe: param_overrides = {node_id: {param: value}}, applied by apply_recipe() before compiling, with the cache keyed on (version, recipe_id, updated_at). HTTP recipe, TCP recipe=, or the bound recipe when nothing is named. An override may only name an existing node and a declared parameter, and the resulting graph must pass validate_graph.
  • station_id: VISION_STATION_ID is written into FlowRun, the RunReport and the TCP response, indexed on (station_id, -started_at).
  • Golden Set (apps/golden): cases with expectations, regression run outside preview mode, images kept only for mismatches, the baseline comparison listing what regressed, and manage.py regress for CI. Flow export and import is manage.py flow export|import|run with a stable serialisation (sorted, integer coordinates, the {SOURCE} placeholder). See Golden Set.
  • Pushing to Modbus (apps/comm): a Connection (modbus_tcp, modbus_server, tcp_client or a plugin) plus the write_modbus tool, with connections opened by Runner.prefetch_hooks on the caller's thread, and a failed write degrading rather than failing the run. See Modbus.
  • Calibration (calib.py, api_calib.py): one asset holds the lens intrinsics and the pixel-to-world mapping; solved by least squares with per-point residuals, camera matrix rescaled when the running resolution differs. Board (board.py, api_board.py): per-flow display configuration plus a single endpoint that prepares everything an operator screen shows.
  • Deliberately deferred: a built-in GenICam source.
