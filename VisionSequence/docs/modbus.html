Pushing results out (Modbus TCP and host systems)

Automation is passive: equipment or a host system calls us and collects the result. This page is active: when a flow finishes, the engine writes the judgement and the measurements into the equipment's coils and registers over Modbus TCP, or pushes a line of text to a host system. It works like image sources — create a connection on the settings page, then put a write Modbus (write_modbus) tool in the flow, point it at that connection and fill in the mapping table.

0. Two roles: client and server

Modbus/TCP has a master and a slave. The platform can be either; choose the kind when you create the connection under Integration ▸ Connections:

RolekindWho initiatesWhen to use it
Client (master)modbus_tcpThe platform connects to the device's IP and portThe device — a controller, a drive, an I/O module, a host program, anything that speaks Modbus TCP — is itself a Modbus server (slave) and the platform reads and writes its coils and registers.
Server (slave)modbus_serverThe platform listens on a port (5020 by default) and waits for a masterThe other side is the master and prefers to poll. The flow writes results into the platform's registers for the master to collect; the master can also write a part number or a trigger flag in, which the flow picks up with "read Modbus".

The address format, the mapping table and the tools are identical for both roles — the only difference is who initiates the connection. In server mode size is the number of points in each area (coils, discrete inputs, holding registers, input registers) and defaults to 512.

A server opens its port by itself: it starts listening as soon as the connection is created or changed, and again when the server starts (manage.py serve calls writers.autostart(); --no-comm turns that off). The master does not have to wait for somebody to press Test in the web interface. If another program is already using the port, the reason appears directly in the connection status. Disabling or deleting the connection closes it.

1. Connection kinds and their config

kindWhat it is forconfig
modbus_tcpModbus TCP: coils (digital outputs) and holding registers (values), using pymodbus. 
{"host": "192.168.1.10", "port": 502, "unit_id": 1,
 "timeout_s": 2, "word_order": "big"}
word_order is the word order of 32- and 64-bit values. Most devices are big; some are little.
tcp_clientA long-lived connection that sends the result to a host system: one line of text from a template, or the whole thing as one line of JSON. 
{"host": "192.168.1.20", "port": 5000, "timeout_s": 2,
 "template": "RESULT {judge} {width_px}",
 "newline": "\n", "encoding": "utf-8", "wait_reply": false}
Without a template it sends {"judge": 1, "width_px": 12.3}\n. A field missing from the template becomes an empty string rather than an error. wait_reply=true waits for one line back and puts it in the result as reply.
tcp_imagePushes the image of a flow step to a host program over one long-lived connection, with the send_image tool. One frame = a fixed 13-byte prefix (VSIM, version 1, header length, payload length; big-endian) + a JSON header (name, run_id, flow_id, node, width, height, channels, dtype, encoding, values) + the image bytes. write() on this kind sends a header-only frame carrying the values, so a mapping table can use it too. 
{"host": "192.168.1.20", "port": 9001, "timeout_s": 2,
 "encoding": "jpeg", "quality": 85}
encoding is jpeg (small, lossy), png (lossless) or raw (row-major pixels; the header carries the shape and dtype). The first failed send reconnects once before giving up. Test on the connection actually connects, so the receiving program must already be listening — the platform connects out to it, never the other way round.
plugin or a plugin's own kindA Writer of your own (OPC UA, a vendor SDK, …)Drop a .py file subclassing Writer into plugins/ and it loads automatically. A CSV logger ships as an example; see §6 and Plugins.

Common field: timeout_s, the timeout of a single write, two seconds by default. Changing a connection's settings (PATCH) closes the old connection, and the next run reopens it.

1-1. Triggering: the master writes a flag and the platform inspects

In server mode the other side is the master — it writes registers, it does not call the platform's HTTP or TCP interfaces. Without this layer, a trigger flag written by the master does nothing at all and the line has to fall back to continuous mode, grabbing an image on every cycle and wasting camera bandwidth and CPU. So both kinds of Modbus connection can be given a trigger address:

{"host": "0.0.0.0", "port": 5020, "unit_id": 1, "size": 512,
 "trigger_address": "coil:0",        ← the master writes non-zero and one inspection runs
 "trigger_flow": "appearance",        ← a flow name or id (a disabled flow is never triggered)
 "trigger_interval_ms": 50,           ← polling interval, minimum 10
 "trigger_mode": "rising",            ← rising: runs once on 0 → non-zero; nonzero: runs while it stays non-zero
 "trigger_clear": true,               ← clear the flag before running, so a long run cannot re-trigger
 "trigger_done_address": "coil:1",    ← write 1 when finished (optional)
 "trigger_recipe": ""}                ← use a specific recipe (optional)

A complete handshake:

Master  : trigger := 1
Platform: sees it → clears trigger → runs the flow → the flow's "write Modbus" step puts the
          judgement and measurements into the registers → done := 1
Master  : sees done → reads the results → done := 0
  • The flow writes its own results: put a "write Modbus" node at the end and map as many values as you like. The trigger settings only clear the flag and set the done address.
  • One connection gets one polling thread, which does nothing but read a single address. The flow itself still goes through the Runner, so statistics, events and history are identical to any other trigger source (the trigger is recorded as modbus).
  • If the device drops off, polling backs off exponentially to a maximum of five seconds and keeps retrying, resuming automatically when the connection returns. The failure count and the last reason are in the connection status under trigger.
  • Client mode (modbus_tcp) can do this too: poll a register on the device as the trigger source.
  • Both the trigger and the run it starts appear under Commands and results (see §6b), so while debugging you can see how long each trigger took and what it judged.

2. Address format (modbus_tcp)

AddressMeaning
coil:10Coil 10, a bool. Aliases: co:, c:.
holding:100Holding register 100 as uint16 (a float is rounded, and anything outside 0–65535 is clamped). Aliases: hr:, register:.
holding:100:int16 / uint16 / int32 / uint32 / int64 / uint64 / float32 / float64An explicit type. 32-bit values take two registers and 64-bit values four, in the connection's word_order.
discrete:3, input:7Discrete inputs and input registers, read-only — usable from read and /state; writing returns an error.

The offset may be hexadecimal (holding:0x100). It is the zero-based protocol address: where the device's manual says 40001, write holding:0.

For tcp_client the "address" is a field name in the template ({judge} → "judge").

3. The flow tools: write_modbus, read_modbus and send_image

send_image pushes the image on its input port to a tcp_image connection: choose the connection, optionally override the encoding and JPEG quality, tick "rejects only" to send NG images alone, and the header carries the run id, the verdict and the named outputs so far (include_values). Like write_modbus it degrades by default — a failed send logs a warning and the run goes on — unless "fail the run" is chosen. A minimal receiver in Python:

import json, socket, struct
HEAD = struct.Struct(">4sBII")
srv = socket.socket(); srv.bind(("0.0.0.0", 9001)); srv.listen(1)
conn, _ = srv.accept()
def exact(n):
    buf = b""
    while len(buf) < n:
        chunk = conn.recv(n - len(buf)); assert chunk; buf += chunk
    return buf
while True:
    magic, version, hlen, plen = HEAD.unpack(exact(HEAD.size))
    header = json.loads(exact(hlen)); image = exact(plen)
    print(header["run_id"], header.get("values"), len(image), "bytes")
ParameterWhat it does
connection (text)The connection's name (a numeric id is also accepted).
mapping (json)An array, one entry per address — see below.
on_error (select)warn (the default): a failed write only logs a warning and the run continues. fail: the run fails.
timeout_s (number)0 uses the connection's setting; anything else overrides the timeout for this write.

Input port values (any, multiple edges allowed); output ports written (how many were written) and ok (bool).

[
  {"src": "judge",    "address": "coil:0",              "dtype": "bool"},
  {"src": "width_px", "address": "holding:100:float32", "scale": 1.0},
  {"src": "hole_count", "address": "holding:102"},
  {"src": "v0",       "address": "holding:103:int32",   "scale": 1000, "dtype": "int"},
  {"address": "coil:1", "value": 1}
]
FieldWhat it means
srcWhere the value comes from: judge (the run's verdict, OK → 1, NG → 0), the name of a named output (a key the output tool wrote into _outputs), or v0, v1… for the Nth edge into this node's values port, in connection order.
addressWhere it goes. Omitted, it equals src — which is how tcp_client is usually written.
dtypebool, int or float: the conversion applied before writing. When the Modbus address carries its own type, the writer converts again to match it.
scale, offsetvalue × scale + offset — for example millimetres as integer micrometres: scale: 1000, dtype: int.
valueA constant, such as a "processing complete" handshake bit. With value set, src is ignored.

An entry whose source cannot be found is skipped and recorded in detail.missing; the others are still written. When nothing in the whole table can be written you get "nothing to write" and the run is still ok.

Node ordering: write_modbus has no required input, so connect judge.verdict (or the last tool's output) to values to make sure it runs after the judgement. A tcp_client example:

template = "RESULT {judge} {width_px} {lot}"
mapping  = [{"src": "judge"}, {"src": "width_px"}, {"src": "lot"}]
→ sends "RESULT 1 12.34 A123\n"

3-1. Reading Modbus (read_modbus)

Bring coil and register values into the flow. On a client connection that reads the device; on a server connection it reads what the master wrote into the platform — a part number, a trigger flag, a recipe number. Parameters:

ParameterWhat it does
connectionThe connection name, as in write_modbus.
mappingAn array of {"name": …, "address": …, "scale"?: …, "offset"?: …}. With no name, the address is used as the name.
publishWhen on, the values read are merged into the run's outputs, so they come back over the API and TCP.
on_errorDegrade on a failed read (the default) or fail the run — the same as write_modbus.

Output ports: values (a list in mapping order), value (the first number, convenient for feeding a judgement or a branch) and ok. For example:

[
  {"name": "recipe", "address": "holding:0"},
  {"name": "trigger", "address": "coil:1"},
  {"name": "temperature", "address": "holding:10:float32", "scale": 0.1}
]

The typical arrangement: the master writes the part number into holding:0 and the trigger flag into coil:1; the flow starts with read_modbus to pick up the part number and choose a recipe, and ends with write_modbus putting the judgement back into coil:10.

4. Degradation

A production line would rather lose one record than stop: a failed write does not fail the run by default.
  • Inside the Writer: every write has a timeout, and a failure closes the connection, reconnects once and writes again. Only the second failure counts (CommError).
  • In the tool: on_error=warn (the default) leaves the node at status=ok with the message "write failed (degraded): …", sets the ok output to false and logs one warning on the node. The run's verdict is unaffected. on_error=fail puts the node in error and fails the run.
  • A connection that does not exist, is disabled, or could not be opened in advance degrades the same way, with the reason in the message.
  • A connection's info() accumulates writes, errors, reconnects and last_error, visible on the settings page and from GET /connections.

An integrator (API key) counts as an administrator. test and write report failures as 200 with ok=false, so the integration page can show the reason.

6. Writing your own Writer

Drop a .py file subclassing Writer into plugins/ at the project root and it loads automatically — no .env change needed. The rules and the module variables are in Plugins, and plugins/example_csv_writer.py ships as a working example:

# plugins/opcua.py — drop it in plugins/ and it loads
from apps.comm.writers import Writer, CommError

class OpcUaWriter(Writer):
    kind = "opcua"
    def __init__(self, config, **kw):
        super().__init__(config, **kw)      # gives you self.timeout, self._lock and the counters
        self._open()
    def _open(self):  ...                    # raise CommError if it cannot connect
    def _write(self, values):                # {address: value} → {"written": n}
        ...
    def _read(self, addresses): ...          # optional
    def _close(self): ...
    def info(self): return {**super().info(), "endpoint": ...}

You only override _open, _write, _read and _close; the lock, the timeout, the single reconnect and the counters all live in the base class's write() and read(). Module-level label, description and enabled control the display name, the description and whether it loads at all. You can also create a connection of kind plugin and name the class directly in its config with "class": "mypkg.opcua:OpcUaWriter".

6b. Commands and results (debugging)

Integration ▸ Connections and Integration ▸ Modbus both have Commands and results at the bottom. While the page is open, every write and read (address, value, duration, success) and every master request the server receives is listed live; click a row for the full detail. Once the page is closed only errors are kept, so there is no cost on the line. Trigger polling itself is not traced — reads happening dozens of times a second would flush the real commands out of the buffer — so only a successful trigger, the flag clear, the done write and read failures appear. One trigger therefore reads as a complete handshake: write coil:0=1 (the master) → write coil:0=0 (cleared) → write coil:1=1 (done) → trigger coil:0 → flow name: ok. The arrows: ← came in from outside, → went out from the platform. More in Automation §5c.

7. How it is put together

  • apps/comm/models.py: Connection(name unique, kind, config JSON, is_enabled, created_at, updated_at).
  • apps/comm/writers.py: the Writer base class, the built-in writers, open_connection(model) with a cache keyed on updated_at, close_connection, get_writer(name) (memory only) and prefetch_connections(compiled).
  • The hot path never touches the database: apps/comm/apps.py hooks prefetch_connections into Runner.prefetch_hooks in ready(). When the Runner compiles a flow — on the caller's thread — it collects the connection parameter of every tool that declares one, looks them up and opens them into a name → writer cache. Tools running on the thread pool only call get_writer(name).
  • apps/vision/tools/builtin/modbus.py: the write_modbus and read_modbus tools.
  • apps/comm/api.py: the connection API, mounted under /api/vision.
  • tests/test_comm.py: an in-memory fake writer (tests/fakes.py), tcp_client (against a temporary local socket server), modbus_tcp (pymodbus's TCP server on a thread), tool degradation, Runner prefetch and the API.
