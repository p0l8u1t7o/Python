Automation (Modbus TCP, host systems, MES)

Three ways in, all returning the same shape.

0. Identity (the same on every endpoint)

  • Integrator: when a key is configured (VISION_API_KEY), send X-API-Key: <key> or ?api_key=. An integrator can always execute, even while the engine is locked.
  • User token: Authorization: Bearer <token>. The event stream and the image endpoints take the same header; ?token= exists only for the browser's EventSource and <img> tags, which cannot send headers.
  • Missing or invalid credentials always return 401 {"error": {"code": "unauthenticated", …}}, in the same shape as every other error.

1. HTTP synchronous run (the common case)

POST /api/vision/flows/{flow_id}/run
  • JSON: {"context": {"lot": "A123"}, "wait": true, "timeout_s": 5, "include_nodes": false}
  • Or multipart: image (a file — PNG, JPG, BMP, TIFF and the other usual formats) plus context as a JSON string. With an image attached, the image_source node (mode=auto) uses it directly instead of grabbing from the camera.
  • ?wait=false returns 202 immediately with {"queued":true,"flow_id":1,"run_id":"…"}. Fetch the result later with GET /api/vision/runs/{run_id}; while it is still going you get {"status":"queued|running","pending":true}. Subscribing to SSE works too.
  • timeout_s is "how long I am willing to wait". On expiry you get 504 run_timeout with details.run_id so you can collect the result afterwards — the run itself is not aborted; that is the engine's own VISION_RUN_TIMEOUT_S. Leave it out and the wait is RUN_TIMEOUT_S + 5 seconds, so the engine's timeout fires first and returns a complete report.
  • include_nodes=1 (the old name include_images still works) adds each step's outputs and overlays to the response. Images are never embedded in the JSON; you get an image ref and fetch the picture with GET /api/vision/images/{ref}.

The 200 response:

{"id": "…", "status": "ok|ng|failed", "duration_ms": 12.3,
 "outputs": {"judge": "OK", "hole_count": 5, "width_mm": 12.34},
 "nodes": {"blob-1": {"status": "ok", "duration_ms": 0.9, "message": "5 blobs"}}, "error": ""}
  • outputs comes from the named output and OK/NG judge tools in the flow; you choose the key names.
  • status: ok, ng (judged a reject) or failed (a tool error, a timeout, or no image from the source).
  • 429 flow_queue_full means this flow already has VISION_MAX_QUEUE_PER_FLOW triggers waiting (16 by default). A flow runs one run at a time — the camera and the hardware have to stay consistent — so when several stations share a flow, requests queue. The limit and the current depth are visible from GET /api/vision/capacity or the TCP command STATUS <flow>. 409 means the flow is disabled.

With curl:

curl -X POST http://127.0.0.1:8000/api/vision/flows/1/run -H "Content-Type: application/json" -d "{}"
curl -X POST http://127.0.0.1:8000/api/vision/flows/1/run -F image=@part.png -F context='{"lot":"A1"}'

2. One-line TCP commands (easiest for equipment)

Connect to VISION_TCP_PORT (9000 by default). One command per line, one JSON response per line, terminated with \n:

CommandResponse
RUN 1 / RUN hole_count lot=A1{"ok":true,"status":"ok","judge":"OK","outputs":{…},"duration_ms":12.3,"run_id":"…"}
RUN 1 fmt=lineOK,12.35,8.10 — plain text, not JSON: the named output built by a Format a reply step (see 2-3)
TRIGGER 1 / TRIGGER 1 lot=A1{"ok":true,"queued":true,"run_id":"…"} — it does not wait; collect the result with GET /api/vision/runs/{run_id}
STATUS / STATUS 1Capacity and the engine lock, or that flow's statistics
START 1 / STOP 1Continuous mode
LOCK / LOCK reason="camera calibration" ttl=600{"ok":true,"lock":{…}} — hold the hardware: the web interface can edit but not run, and a banner says who holds it. ttl is an optional auto-release in seconds.
UNLOCKRelease the lock
LISTEvery flow
VARS 1 / VARS station{"ok":true,"scope":"hole_count","items":{"parts":128,"lot":"A17"}} — the values a flow keeps between runs (see 2-4)
SET 1 lot=A17 parts=0 / SET station shift=nightWrites variables and stores them at once; answers like VARS. Same value rules as RUN, so lot=00123 keeps its zeros
PING{"ok":true,"pong":true}
AUTH <key>{"ok":true,"authenticated":true} — only when the station has VISION_TCP_AUTH set (the installer generates one): send it once per connection before any other command except PING; otherwise every command answers {"ok":false,"code":"unauthorized"}. A wrong key is delayed half a second. With no key configured the port is open to whoever the firewall lets in.

key=value pairs go into context, where formulas and outputs in the flow can read them. The connection can be held open indefinitely; NODELAY is already on.

2-1. Argument types (part numbers and barcodes survive intact)

  • Values are strings by default. Only a clean decimal number (1, -3, 2.5) becomes a number. So lot=00123 keeps its leading zeros, sn=1_000 does not turn into 1000, and exp=1e3 arrives as written.
  • Quote a value that contains a space: RUN 1 barcode="ABC DEF". The same goes for a flow name with a space: RUN "my flow".
  • An argument that is not in key=value shape returns bad_argument, rather than silently dropping half a barcode.

2-3. Plain text for equipment that cannot read JSON

Plenty of PLCs, older host programs and print controllers can only take a fixed line such as OK,12.35,8.10. Build that line inside the flow with the Format a reply step, then ask for it by name:

WhereHowAnswer
In the flowAdd Format a reply after the verdict. Layout {judge},{width:.2f},{height:.2f}, line ending CRLF, output name line.The run now carries outputs.line
TCPRUN 1 fmt=lineOK,12.35,8.10 exactly as laid out, with no JSON wrapper
HTTPPOST /api/vision/flows/1/run with {"format": "line"}text/plain with the same line

Names in braces are filled from the verdict (judge), any named output made earlier in the flow, whatever the trigger sent (lot, sn), that step's own inputs a to d, plus run_id and station. Round with {width:.2f}, pad with {count:05d}, and type or where the protocol needs them. A name with no value is left empty by default, so one missing measurement does not stop the line; switch that to Fail the step while you are commissioning.

If the run has no output under that name the answer is still JSON, with code: "no_such_output" and the list of names that are there — a device that gets nothing back is much harder to diagnose than one that gets a reason.

The same line can be pushed instead of pulled: wire the step's text output into Write Modbus aimed at a tcp_client connection, and the platform sends it to the host program as each part is inspected.

2-4. Variables: the lot number, a running count, the previous part

A flow can keep values between runs: a running count, the previous part's measurement, the lot number the PLC sent at a changeover. Inside the flow the Store a variable and Read a variable steps use them (scope flow for that flow, station shared by every flow); from outside:

HowReadWrite
TCPVARS 1, VARS stationSET 1 lot=A17 parts=0, SET station shift=night
HTTPGET /api/vision/flows/{id}/variables → {"items": {...}, "station": {...}}; GET /api/vision/variablesPUT /api/vision/flows/{id}/variables with {"values": {"lot": "A17"}} (merges); DELETE .../variables/{name}; the same under /api/vision/variables for the station

Writes from outside are stored immediately; values written by a running flow are saved within two seconds and survive a restart. Names are letters, digits and underscores; values are numbers, text, booleans or JSON (64 KB). Writing needs the on-site teaching permission, which an operator has by default — a changeover is an operator's job. Previews, batch tests and the assistant's trial runs never touch these values: each trial sees its own copy.

2-5. One call for a custom operator screen

If you build your own HMI or dashboard, GET /api/vision/flows/{id}/board returns everything an operator screen shows for that flow, already prepared: the board configuration made in the flow editor, the latest run (verdict, verdict label, the picture's image ref and marks), the values to show with their label, unit, formatted text and tolerance verdict (ok: true, false or null when no tolerance is set), today's OK/NG/yield from the hourly roll-up, and the flow's variables. Poll it, or subscribe to the SSE run_finished event and fetch it on each part. The platform's own full-screen board (/board/{id}) uses the same data, so what your screen shows matches ours.

3. Live SSE events (HMI and dashboards)

GET /api/vision/flows/{id}/stream?since=<seq>     one flow
GET /api/vision/events?since=<seq>                everything

Authentication is the same as everywhere else (Authorization: Bearer, X-API-Key, or ?token= from a browser). These two are streams, so they are not in /api/openapi.json; their paths are also available from GET /api/vision/integration/info as events_url and flow_events_url.

Events: run_queued, run_started, run_finished (run is the full result, stats the running totals), continuous, stats, ping (a heartbeat every 15 seconds — the web interface treats 40 seconds of silence as a dropped connection and reconnects, because behind a proxy a dead backend does not necessarily close the client socket) and bye (reconnect after 55 seconds, sending seq back so nothing is missed). ?outputs=0 sends node status without outputs, to save bandwidth.

4. When the camera is not on this machine: push an image

Create an image source of kind upload, push to POST /api/vision/sources/{id}/push (multipart image), and select it in the flow. config.max_age_s stops a stale image from being used.

4-1. The camera is on another PC: the capture client

Rather than writing your own push program, use the capture client: a downloadable desktop program drives webcams, Basler and IDS cameras where they are and connects out to the server's capture port 9100. Add a "capture client camera" source in the web interface and an HTTP- or TCP-triggered run can ask that camera for a fresh frame (on demand) or take the latest one (continuous streaming). On the same machine it goes through shared memory; across machines it is a single TCP connection with lossless transfer.

Performance advice

  • On large images, resize or crop before the heavy tools. Set VISION_CV_THREADS=1~2 so parallel flows do not fight over cores.
  • VISION_PERSIST_RUNS=0 turns off database records and keeps only in-memory statistics — worth it at thousands of runs a minute.
  • Flows are independent of each other; one flow runs a single run at a time (for camera and state consistency), and different flows run in parallel up to VISION_MAX_WORKERS.

5. Identity and the engine lock (the hardware belongs to the line)

  • An integrator calls with X-API-Key: <VISION_API_KEY> (or ?api_key=) and is a machine identity: always able to execute, unaffected by the lock. The TCP interface counts as an integrator too.
  • Browser users sign in with an account (POST /api/auth/login → a Bearer token).

Locking:

POST   /api/vision/lock   X-API-Key: ...   {"reason": "production run", "ttl_s": 28800}   → lock (ttl optional, auto-releases)
GET    /api/vision/lock                                                                  → {"locked", "holder", "reason", "locked_at", "expires_at"}
DELETE /api/vision/lock   X-API-Key: ...                                                 → unlock

TCP:   AUTH 0f3c…                                 → {"ok": true, "authenticated": true}   (once per connection, when VISION_TCP_AUTH is set)
       LOCK reason="production run" ttl=28800     → {"ok": true, "lock": {...}}
       UNLOCK                                     → {"ok": true, "lock": {...}}
       STATUS                                     → capacity plus the current lock
  • While locked, any user — administrators included — calling run, preview or continuous gets 423 {"error": {"code": "engine_locked", ...}}, but can still sign in, edit and save flows. Locking also stops every continuous run in progress.
  • The lock is an integration command, over HTTP or TCP; the web interface does not take it. While it holds, a banner across the top of every page says who has it and why, and an administrator or the holder can release it from there. The holder can always execute.
  • The recommended pattern: POST lock with a ttl at the start of the start-up or changeover program, and DELETE lock when the line stops.

"Integration" in the web interface expands into a tree in the sidebar, and every method is its own page with its own URL, so you can bookmark or share it directly:

Connections are managed by the integration that uses them: Modbus server connections on the Modbus server page, Modbus client connections on the Modbus client page (no kind to pick — the page decides), host TCP on the TCP page, and connections of a plugin-provided kind on the Plugins page. There is no separate connections page. Old URLs — /connections, /integration/connections, /integration/lock, /integration/format and the /integration?tab=modbus style — all redirect.

5c. Commands and results (debugging)

Every integration page is split into tabs (try it, the reference material, the connections, and Commands and results), so nothing has to be scrolled past. While the commands tab is open, the commands and replies this interface handles are listed live — time, direction (→ came in from outside, ← went out from the platform), source, a summary and the duration, with failures highlighted. Click a row to expand the full JSON.

  • HTTP: the trigger source, judgement, named outputs and run_id of each POST /flows/{id}/run.
  • TCP: the whole command line received and the JSON returned.
  • Modbus: the address and value of every write and read. When the platform acts as a slave it also lists every request from the master and our reply.
  • Capture: capture clients connecting and disconnecting.

It is an in-process ring buffer (300 entries per channel, apps/vision/trace.py) — nothing is written to disk or to the database — and while nobody has an integration page open only errors are recorded, so a long production run carries no extra cost. API: GET /api/vision/integration/trace?channel=http|tcp|modbus|capture&since=&limit=, and DELETE to clear.

6. Pushing results out (Modbus client or slave)

All three methods above have the caller come and collect the result. If the equipment would rather wait for a coil or a register to change, use an outgoing connection instead: create one on the matching integration page (Modbus server, Modbus client or TCP) and put a "write Modbus" (write_modbus) tool at the end of the flow with a mapping table — or a "send image" (send_image) tool with a tcp_image connection to push the image itself to a host program — for example judge → coil:0 and width_px → holding:100:float32. A failed write only logs a warning by default and the run continues, so the line does not stop. Address format, the connection API and writing your own Writer are in Modbus.

Shape model assets

A shape model holds the edge points and gradient directions of a part, per pyramid level; the shape_match tool searches for it. Build one from an image asset (or a picture in the image cache, ref) and a template region, optionally leaving out an area that changes from part to part:

curl -X POST http://HOST/api/vision/assets/shape-model -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"asset_id":"<image asset id>","region":{"shape":"rect","x":520,"y":390,"w":250,"h":190},
       "exclude":{"shape":"rect","x":600,"y":500,"w":60,"h":20},"name":"bracket","min_contrast":10}'
curl http://HOST/api/vision/assets/{id}/shape-model -H "X-API-Key: $KEY"                 # levels, points, contrast, edge points
curl "http://HOST/api/vision/assets/{id}/shape-model/preview?api_key=$KEY" -o model.png  # template with the model edges drawn

Teaching parameters (contrast_low/contrast_high, automatic by default; min_contrast; pyramid_levels; max_points; angle_start/angle_extent; scale_min/scale_max) are stored in the asset and can be overridden on the tool. On the server, manage.py shape_model --name NAME --image FILE [--region JSON] [--exclude JSON] does the same.

Statistical template assets

A statistical template is a per-pixel mean and standard-deviation model built from many good images; the defect_stat tool compares against it. Build one from uploads or from a batch image set, then pick the asset in the tool:

curl -X POST http://HOST/api/vision/assets/stat-template -H "X-API-Key: $KEY" \
  -F name="print stat" -F align=phase -F region='{"shape":"rect","x":40,"y":30,"w":240,"h":180}' \
  -F images=@good01.png -F images=@good02.png -F images=@good03.png ...        # at least 3, 10 or more recommended
curl -X POST http://HOST/api/vision/assets/stat-template -H "X-API-Key: $KEY" -F batch_set_id=12 -F only_ok=true
curl http://HOST/api/vision/assets/{id}/stat-template -H "X-API-Key: $KEY"          # samples, size, alignment residuals, std quantiles
curl "http://HOST/api/vision/assets/{id}/stat-template/std?api_key=$KEY" -o std.png # mean | std | valid as PNG

On the server, manage.py stat_template --name NAME --folder DIR [--region JSON] [--align phase|none] does the same from a folder of images.
