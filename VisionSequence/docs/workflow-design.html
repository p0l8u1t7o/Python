0. 一頁總覽

編輯                          執行                                   觀看
────────────────────────      ─────────────────────────────────      ──────────────────

       ▼                            │  在呼叫者執行緒先開好）
  (Flow.graph)  ──編譯快取──▶  engine.run_graph()：一條執行緒內
   apply_recipe() 疊參數        以拓樸順序執行整張圖，影像用

                                    │
                                    ├→ 影像快取（前端檢視器取圖）
                                    ├→ write_modbus → Connection（主動輸出）
                                    └→ FlowRun（背景執行緒批次寫 DB）

核心思想四句：

  1. 圖是一份 JSON：存在 Flow.graph 一個欄位，編輯器整份存、引擎整份讀。
  2. 執行是一次函式呼叫：一次 run 在執行緒池的一條執行緒內以拓樸順序跑完，中間狀態全在記憶體，跑完才落地。
  3. 工具是 registry：引擎不認識任何工具；前端調色盤與參數表單從 catalogue() 產生，加工具不用改引擎、不用改前端。
  4. 整合是兩條路：被動（HTTP／TCP／SSE 來拿結果）與主動（write_modbus 寫進 Modbus TCP 設備／上位機），主動路一律可降級。

1. 為什麼是資料流，不是控制流程

本平台的引擎脫胎於 ZQS Cloud 的控制流程引擎（畫布、registry、封閉集合、SSE 這些設計都沿用），但執行模型整個換掉。理由是兩者要解的問題不同：

控制流程（ZQS Cloud）資料流（VisionSequence）
問的問題「下一步走到哪個節點？」「這個節點的輸入資料是什麼？」
執行單位DB 裡的 token，stepper 每 tick 推一步；一次執行可以活數小時、跨行程重啟一次函式呼叫；一次 run 幾十毫秒～幾秒，在一條執行緒內跑完
節點間傳什麼控制權（token 位置）＋變數表資料本身：影像（numpy）、數值、點集、輪廓，沿邊在記憶體傳
並行token 數＝並行分支數執行緒池大小＝同時忙碌的流程數；單一 run 內不並行（OpenCV 自己已多核）
持久化每步寫 DB（token、log），重啟續跑跑完才寫一列 FlowRun（背景批次）；當機丟的是「這一張」，下一張照跑

機器視覺的一次檢測是「取像 → 前處理 → 定位 → 量測 → 判定」的短生命週期資料管線，讓它走 DB token stepper 會把毫秒級的事拉成秒級、還把影像逼到落地。反過來，產線排程那種「等訊號、跨小時、要斷點續跑」的長流程也不該塞進資料流引擎。兩個引擎，各管各的問題。

控制分支在資料流裡退化成一種特例：工具可宣告 kind="flow" 的輸出把手（例如 if 的 true／false、判定的 pass／fail），帶 flow 邊連入的節點只有在至少一條連入分支被選中時才執行，被跳過的節點其下游（資料邊）也一併跳過（除非該輸入是選填）。這樣一張圖同時是資料管線與淺層決策樹，而引擎仍然只是「照拓樸順序走一遍」。

2. 圖：一份 JSON、封閉集合、隱含埠

  • 一份 JSON：{"nodes": [...], "edges": [...]}，節點記 type（工具 key）與 params；存檔時 validate_graph() 驗（埠型別相容、必填、單線埠、DAG），執行時 compile_graph() 編譯並依 flow version 快取。改名過的工具 key 走 LEGACY_TOOL_TYPES 自動換新（DB 另有資料轉移）。
  • 封閉集合：Param.kind 與 Port.type 都是列舉死的集合，不是 JSON Schema。前端 ParamField 一個 switch 就能畫出任何工具的參數表單；埠顏色、連線相容性都能窮舉。要加一種 kind，後端集合、前端 switch、catalogue()、contract、glossary 五處同步——刻意讓它有成本，避免參數表單長成第二個表單引擎。
  • 隱含埠：每個可執行節點有隱含控制輸入 _flow（分支語意）與隱含輸出 _overlays（該節點的標記，接給 draw_result 疊圖）。它們不在工具宣告裡，由框架統一處理，工具作者不用管。
  • overlays 座標約定：一律是該節點輸入影像的全圖座標。這是前端影像檢視器能把任何工具的標記畫對的唯一原因；ROI 裁切後用 Crop.to_full() 換回。

3. 工具是 registry，安全邊界在框架

工具繼承 Tool，宣告 params／inputs／outputs，實作 execute(ctx) -> Result。引擎只做三件事：查 registry、餵輸入、收 Result。所有防呆都在框架層，不散在工具裡：

  • 註冊時就驗 kind／type 在封閉集合內、key 全域唯一；查無 key 回 UnknownToolType 附可用清單。
  • 工具「找不到東西」回 status="ng" 或走分支；「可預期的失敗」raise ToolError（節點 error）；其他例外框架接住附 repr，平台不會因為一個工具當掉。
  • 工具能看到的世界只有 ToolContext：參數、輸入、run 層級共享變數、asset_path()、grab()、log。不給 ORM、不給 request。

4. 執行：一條執行緒跑完一次 run

  • Runner 是生命週期管理者：每個 Flow 一個 runtime（編譯快取、一次只跑一個 run 的鎖、最近結果、統計）；全域 ThreadPoolExecutor(VISION_MAX_WORKERS)；同一流程排隊上限 MAX_QUEUE_PER_FLOW，超過回 429——寧可拒絕也不無限堆積。
  • engine 是純函式風格：拿編譯好的圖與輸入，照拓樸順序執行，回 RunReport。停用的節點若是「單輸入單輸出同型別」會把輸入直通（關掉一個濾鏡不該讓下游斷線）。
  • 影像快取：影像輸出只有「有人連線用到」或編輯器試跑才登記；每流程保留最近 N 次、全域上限 MB，超過淘汰最舊。前端拿 {ref,width,height} 再去 GET /images/{ref} 取檔。
  • 連續模式：每個流程一條 loop 執行緒，間隔 continuous_interval_ms，每 2 秒才回 DB 確認一次設定還在。
  • 單一 API 行程：引擎狀態、影像快取、SSE bus 都在行程內（manage.py serve = uvicorn workers=1 + TCP）。水平擴展要把引擎拆成獨立服務，不是加 worker。

5. 熱路徑不碰資料庫

執行緒池內的程式碼不查 DB。所有需要 DB 的資源在 Runner._prefetch()（呼叫者執行緒）先開好：影像來源、資產路徑、通訊連線（Runner.prefetch_hooks，apps.comm 掛 prefetch_connections 掃出 write_modbus 用到的連線）。工具在熱路徑只做純記憶體查詢（get_writer(name)）。FlowRun 落地由背景執行緒批次寫。這條規則換來的是：SQLite 也扛得住、執行緒池不會被 I/O 卡死、單次 run 的耗時可預測。

6. 降級策略：產線不停線

寧可漏傳一筆，也不要停線。所有「往外寫」的路都有降級。
  • Writer 內部：逾時＋失敗自動重連一次，第二次才算失敗（CommError）。
  • write_modbus 預設 on_error=warn：寫入失敗記警告、run 照常，判定不受影響；要嚴格可改 fail。
  • 來源抓不到圖、模型資產不見：該節點 error、run failed，但平台照常服務下一張。
  • 未 commissioned（現場教導沒做完）的流程只加 warnings，不阻擋執行。

7. 配方與站台

  • 配方（FlowRecipe）：同一張圖、不同料號的參數集。執行時 apply_recipe() 把配方參數疊在圖上再編譯，編譯快取鍵 (version, recipe_id, updated_at)；run／preview／TCP recipe= 都可指定，未指定用預設配方。圖與參數分離，換料號不改圖。
  • 站台（station_id）：每筆 run 帶 VISION_STATION_ID，報表與上位機據此分流；多站台就是多個行程各帶自己的 id。
  • 現場教導（teach）：參數標 teach=True 的才出現在參數卡頁——現場人員只看得到該調的，其他鎖在工程師的編輯器裡。

8. 三個擴充接縫（外掛）

平台刻意只留三個擴充點，全部走物件繼承 + 資料夾自動偵測（繼承基底類別、丟進 plugins/、重啟即掛載；外掛檔內用 ENABLED／label／description 變數控制掛載與顯示，詳見擴充外掛）：

接縫基底解決什麼
工具Tool新的檢測／量測／邏輯節點；前端零改動出現在調色盤
影像來源GrabberGigE、廠牌 SDK 等取像方式；設定頁 kind 下拉自動出現
整合輸出WriterModbus TCP 之外的目的地（OPC UA、MES、檔案…）；沿用降級與重連框架

三個接縫共用同一套哲學：基底類別把並發、逾時、重試、統計都做完，子類只填「怎麼抓一張圖」「怎麼寫一批值」「怎麼算這個節點」。擴充者寫的程式碼越少，現場出事的面積越小。

9. 帳號與引擎鎖定

  • 身分收斂成一個 Principal(kind=integrator|user|bootstrap)：整合方（API 金鑰）永遠可執行；沒有任何使用者時放行 bootstrap 讓 /auth/setup 能建帳號。
  • 端點只有三種接縫：執行類看 can_execute()（鎖定時 423）、修改類看 _editable_flow()（擁有者或管理員）、讀取看 _visible_flows()。新增端點照這三個模子套，不發明第四種。
  • 鎖是 EngineLock 單列（id=1）：鎖定時停掉所有連續執行並發 SSE lock 事件，整台機器一個開關，語意簡單到不會出錯。

10. 要守住的原則（紅線）

  1. 不重寫引擎、不改 graph JSON 格式、不把 Flow.graph 搬出資料庫、不引入 Node.js／微服務。
  2. 執行緒池內不碰資料庫；資源一律 prefetch。
  3. 只有一個 API 行程；runserver 開發要加 --noreload。
  4. 封閉集合不擴散：新增 Param.kind／Port.type 必須五處同步（後端集合、前端 ParamField、catalogue()、contract.html、glossary.html）。
  5. 工具不 raise 表達「沒找到」；overlays 一律輸入影像全圖座標。
  6. 改動優化過的函式（blob 預濾、_roi_hist、find_edges_rows、caliper_points、apply_mask、mask_for、RANSAC 向量化、template_match 金字塔）必須重跑等價性檢查，不能只看測試綠。
  7. 往外寫的路（Modbus、上位機）預設降級不停線。

11. 名詞對照（ZQS ↔ VisionSequence）

ZQS Cloud（控制流程）VisionSequence（資料流）差異
WorkflowFlow都是「圖的定義」，一份 JSON
WorkflowRun＋WorkflowTokenFlowRun（RunReport 落地）token 消失了：一次 run 就是一次函式呼叫，沒有「停在半路」的狀態
WorkflowLog（每步一列）FlowRun.nodes（各節點摘要）＋節點 log跑完一次寫一列，不逐步落地
NodeType／nodes/base.pyTool／tools/base.py多了輸入／輸出埠宣告（資料流）；Param 封閉集合相同
把手（Handle）輸出埠；kind="flow" 的把手＝分支把手從「控制去向」變成「資料出口」，flow 埠保留分支語意
stepper advance() 每 tick 推一步engine.run_graph() 一次跑完沒有 tick、沒有 step budget、沒有防 runaway（DAG 天生會停）
run_workflows 常駐行程Runner 執行緒池（同一行程）並行單位從 token 變成流程
dispatch_command（設備命令）write_modbus＋Connection（apps.comm）主動輸出獨立成連線子系統，帶降級與重連
SSE run streamSSE /events（run／lock 事件）相同思想：行程內真推播，不輪詢 DB
