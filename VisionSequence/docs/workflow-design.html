Workflow design

This page is about the thinking: why the VisionSequence engine looks the way it does, what each trade-off bought, and which principles hold. The module-by-module description of the internals is in the Architecture page. The code this page talks about: apps/vision/ (models.py, graph.py, engine.py, runner.py, tools/, sources/), apps/comm/, apps/accounts/, plugins/, and on the front end frontend/src/pages/FlowEditorPage.tsx with components/editor/*.

Four sentences:

  1. The graph is one JSON document, in a single Flow.graph column. The editor saves it whole and the engine reads it whole.
  2. A run is one function call. It executes in topological order on one thread of the pool; everything intermediate stays in memory and only the result is persisted.
  3. Tools are a registry. The engine knows nothing about any particular tool; the palette and the parameter forms are generated from catalogue(), so adding a tool touches neither the engine nor the front end.
  4. Integration goes two ways: passive (HTTP, TCP and SSE come and collect) and active (write_modbus writes into a Modbus device or a host system), and the active path always degrades rather than stopping the line.

1. Why dataflow rather than control flow

The engine grew out of a control-flow workflow engine — the canvas, the registry, the closed sets and SSE all carry over — but the execution model was replaced entirely, because the two solve different problems:

Control flowDataflow (VisionSequence)
The question it asks"Which node do we go to next?""What is this node's input?"
Unit of executionA token in the database, advanced one step per tick; a single execution can live for hours and survive restartsOne function call; a run takes tens of milliseconds to a few seconds, on one thread
What travels between nodesControl (where the token is) plus a variable tableThe data itself: images (numpy), numbers, point sets, contours — along the edges, in memory
ConcurrencyThe number of tokens equals the number of parallel branchesThe thread pool size equals the number of flows busy at once; a single run is not parallelised internally (the algorithms inside the tools already use several cores)
PersistenceEvery step writes to the database (tokens, logs) and resumes after a restartOne FlowRun row after the run, written in the background; a crash loses the current image and the next one still runs

One inspection is a short-lived pipeline — acquire, pre-process, locate, measure, judge. Pushing that through a database token stepper turns a millisecond job into a second-long one and forces images onto disk. The converse holds too: a line-scheduling workflow that waits for signals, spans hours and must resume from a breakpoint does not belong in a dataflow engine. Two engines, each for its own problem.

Branching survives as a special case: a tool can declare an output handle of kind="flow" (true/false on an if, pass/fail on a judgement), and a node with incoming flow edges executes only when at least one of them was selected. A skipped node takes its downstream data edges with it, unless that input is optional. So one graph is both a data pipeline and a shallow decision tree, while the engine still just walks it once in topological order.

1a. Inline subflows, item loops and tiles

trigger_flow and call_flow deliberately solve different jobs. trigger_flow submits another flow to the runner: it gets its own run id, queue slot, SSE events, statistics and optional FlowRun row. call_flow compiles the target flow through the same cache, then calls the engine inline on the same thread. It returns to the parent node with the child verdict and named outputs, but it never enters the runner queue and never updates runtime statistics.

Inline calls share the parent run deadline and the same trigger chain used by trigger_flow, so a mixed loop such as A triggering B and B calling A is rejected before it can recurse. A second depth guard keeps long acyclic chains from turning one inspection into an unbounded nested run.

for_each is the item form of the same mechanism. A match, region or image list is expanded one item at a time; a region is cropped to a child image, the child flow runs on that crop, and crop-local points or matches are restored with the existing geometry offset logic before they appear in the per-item summary. tile only produces rectangular regions, so it can feed for_each or any array-oriented tool without touching image pixels.

2. The graph: one JSON document, closed sets, implicit ports

  • One document: {"nodes": [...], "edges": [...]}, where a node records its type (a tool key) and its params. Saving runs validate_graph() (port type compatibility, required inputs, single-connection ports, acyclicity) and running compiles it with compile_graph(), cached by flow version. Renamed tool keys are mapped through LEGACY_TOOL_TYPES automatically, with a data migration alongside.
  • Closed sets: Param.kind and Port.type are enumerated sets, not JSON Schema. One switch in the front end's ParamField can then render any tool's parameter form, and port colours and connection compatibility can be enumerated exhaustively. Adding a kind means changing five places in step — the backend set, the front-end switch, catalogue(), the contract page and the glossary — deliberately, so the parameter form never grows into a second form engine.
  • Implicit ports: every executable node has an implicit control input _flow (the branching semantics) and an implicit output _overlays (that node's overlays, for draw_result to compose). They are not in the tool's declaration; the framework handles them, so tool authors never think about them.
  • The overlay coordinate convention: always the full-image coordinates of that node's input image. That single rule is why the image viewer can draw any tool's overlays correctly; after cropping to an ROI, map back with Crop.to_full().

3. Tools are a registry; the safety boundary is in the framework

A tool subclasses Tool, declares params, inputs and outputs, and implements execute(ctx) -> Result. The engine does three things: look up the registry, feed the inputs, take the Result. Every safeguard is in the framework rather than scattered through the tools:

  • Registration checks that kinds and types are inside the closed sets and that the key is globally unique. An unknown key returns UnknownToolType with the list of what is available.
  • "Not found" is status="ng" or a branch. An expected failure is raise ToolError (the node errors). Anything else is caught by the framework with its repr attached, so one misbehaving tool cannot take the platform down.
  • The only world a tool can see is ToolContext: its parameters, its inputs, run-level shared variables, asset_path(), grab() and logging. No ORM, no request.

4. Running: one thread per run

  • Runner manages lifecycle: one runtime per flow (the compile cache, a lock so only one run at a time, the recent results, the statistics), a global ThreadPoolExecutor(VISION_MAX_WORKERS), and a per-flow queue limit of MAX_QUEUE_PER_FLOW beyond which it returns 429 — better to refuse than to pile up without bound.
  • engine is written in a pure-function style: given a compiled graph and the inputs, walk it in topological order and return a RunReport. A disabled node that is single-input, single-output and same-type passes its input straight through — turning off one filter should not disconnect everything downstream.
  • The image cache: an image output is registered only when something is connected to it, or during an editor preview. Each flow keeps the last N runs, with a global size cap in megabytes and the oldest evicted. The front end receives {ref, width, height} and fetches the picture from GET /images/{ref}.
  • Continuous mode: one loop thread per flow at continuous_interval_ms, checking the database that the settings still hold only every two seconds.
  • One API process: engine state, the image cache and the SSE bus all live in it (manage.py serve is uvicorn with workers=1 plus TCP). Scaling out means extracting the engine into its own service, not adding workers.

5. The hot path never touches the database

Code running on the thread pool issues no queries. Everything that needs the database is opened in Runner._prefetch() on the caller's thread: image sources, asset paths and communication connections (via Runner.prefetch_hooks — apps.comm registers prefetch_connections, which collects the connections any tool declares). On the hot path a tool only does an in-memory lookup (get_writer(name)). FlowRun rows are batched out by a background thread. What this rule buys: SQLite copes, the thread pool never blocks on I/O, and the duration of a run is predictable.

6. Degradation: the line does not stop

Better to lose one record than to stop the line. Every outward path degrades.
  • Inside a Writer: a timeout, then one automatic reconnect and retry; only the second failure counts (CommError).
  • write_modbus defaults to on_error=warn: a failed write logs a warning, the run continues and the verdict is unaffected. Set fail if you want it strict.
  • A source with no image, or a missing model asset: that node errors and the run fails, but the platform serves the next image normally.
  • A flow that is not yet commissioned only adds warnings; it is never blocked from running.

7. Recipes and stations

  • Recipe (FlowRecipe): one graph, different parameter sets for different part numbers. At run time apply_recipe() overlays them before compiling, and the compile cache is keyed on (version, recipe_id, updated_at). run, preview and TCP recipe= can all name one; without one the bound recipe applies. Graph and parameters stay separate, so a changeover never edits the graph.
  • Station (station_id): every run carries VISION_STATION_ID, which reports and host systems use to separate them. Several stations means several processes, each with its own id.
  • Teaching parameters: only parameters marked teach=True appear on the teach page, so a line operator sees exactly what they are meant to adjust and nothing else. The server enforces it for the operator role.

8. Four extension seams (plugins)

The platform deliberately offers only four extension points, all working the same way — subclass a base class, drop the file in plugins/, restart. Module-level ENABLED, label and description control loading and display; see Plugins.

SeamBase classWhat it solves
ToolToolA new inspection, measurement or logic node; it appears in the palette with no front-end change
Image sourceGrabberAnother way to acquire images — GigE, a vendor SDK — appearing in the kind dropdown automatically
Outgoing connectionWriterDestinations beyond Modbus TCP (OPC UA, MES, a file), reusing the degradation and reconnect framework
Deep-learning modelTrainerA new trainable model kind; the teaching interface is driven by the catalogue and shared, and the result is always an asset

All four share a philosophy: the base class has already dealt with concurrency, timeouts, retries and statistics, and the subclass only fills in "how do I grab one image", "how do I write a batch of values", "how do I compute this node". The less code an extender writes, the smaller the surface that can fail on the line.

9. Accounts and the engine lock

  • Identity collapses into one Principal(kind=integrator|user|bootstrap) with a role. An integrator (an API key) can always execute; with no users at all, bootstrap lets /auth/setup create the first account.
  • Endpoints have three seams and no more: executing checks can_execute() (423 while locked), modifying checks _editable_flow() (an engineer or an administrator; a flow belongs to the line, not to a person), and reading checks _visible_flows(). New endpoints follow one of the three rather than inventing a fourth.
  • The lock is a single EngineLock row (id=1). Locking stops every continuous run and emits an SSE lock event — one switch for the whole machine, with semantics simple enough to be hard to get wrong.

10. The principles that hold

  1. Do not rewrite the engine, change the graph JSON format, move Flow.graph out of the database, or introduce Node.js or microservices.
  2. No database access inside the thread pool; every resource is prefetched.
  3. One API process only; development with runserver needs --noreload.
  4. Closed sets stay closed: a new Param.kind or Port.type means five places changed together (the backend set, the front-end ParamField, catalogue(), contract.html and glossary.html).
  5. A tool never raises to mean "not found", and overlays are always in the input image's full coordinates.
  6. Changing an optimised function (the blob pre-filter, _roi_hist, find_edges_rows, caliper_points, apply_mask, mask_for, the vectorised RANSAC, the template_match pyramid) requires re-running the equivalence check, not just a green test suite.
  7. Outward paths (Modbus, host systems) degrade by default rather than stopping the line.

Cross-flow queues

Station A uses queue_push to keep a part's readings and an optional image reference. On a later trigger, station B uses queue_pop with the same part key to combine readings. No real on-site scenario has been validated.

MechanismUse it forLifetime and execution
Flow variablesLatest values, counters or shared settingsSerializable values can persist; one current value per name
Trigger flowStarting another flowSchedules an execution; does not retain a sequence of part records
Call flow / For eachReusable processing inside the current executionReturns child results to the caller
Cross-flow queueMatching individual parts across separate triggersBounded process-local memory; cleared on process restart

Names follow the flow-variable rule: 1–64 letters, digits or underscores, with no leading digit. Records contain sequence, insertion time, key, values, optional image reference, source flow ID and run ID. Values are dictionaries of scalar, list or dictionary data, at most 64 KB per record. Embedded images are rejected.

Push values use one name=source per line (for example height=a), or a connected data dictionary, which takes precedence. Keys use the same layouts and value resolution as Format a reply, such as {serial:05d}. Missing sources or key fields fail the step. Capacity defaults to 64 and is limited to 1024; each push uses its configured capacity. Reducing capacity with Drop oldest removes enough oldest records to fit. Reject push returns NG and the Full branch without inserting. Lifetime is per item: ttl_s=0 keeps it until removed; expired items are discarded on access.

Read supports FIFO, LIFO or exact key; duplicate keys match the oldest remaining record. Disable Remove after reading to peek. Wait is 0–2000 ms, using a condition that wakes for new records. No match takes Not found and returns empty values, no image and found=false. Connect Matched to downstream checks so they cannot accept missing measurements. Size and oldest age describe the remaining queue. Optional Publish values replaces named outputs with the matched dictionary fields.

Images use the bounded image cache and may expire before queue records. Missing images return no image and a warning in the step log and details; values remain available. There is no durable delivery, acknowledgement, reservation or coordination across multiple API processes. Removed records are not restored if a later step fails. For persistence, use flow variables or the manufacturing execution system. Preview, batch, assistant trials and benchmarks use private snapshots; pushes and removals cannot change production queues. New preview images also stay private.

The Queues card beside flow variables lists sizes, oldest ages and cumulative discarded counts (capacity eviction plus expiry; rejected pushes are not discarded records). Listing requires Integration; clearing requires Connections or Edit flows and is audited. API: GET /vision/queues and DELETE /vision/queues/{name}. Clearing removes pending records while keeping sequence history and counters.
