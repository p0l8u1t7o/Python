Plugins: drop a file in a folder and it loads

All four extension points work the same way — subclass a base class, put the .py file in the plugins/ folder at the project root, and the backend detects and loads it on the next restart, with no .env change and no front-end work.

To extendSubclassIt appears inShipped example
A tool (a canvas node)apps.vision.tools.base.ToolThe editor palette, in its categoryplugins/example_dark_ratio.py
An image sourceapps.vision.sources.grabbers.GrabberThe kind dropdown on the Image sources page§4 below (GigE)
An outgoing connectionapps.comm.writers.WriterThe kind dropdown on the Connections pageplugins/example_csv_writer.py
A deep-learning model kindapps.vision.dl.base.TrainerThe model kind dropdown on the Deep learning page (it shares the teaching interface)See Deep-learning teaching §5

Only want a few lines of Python rather than a plugin? The built-in "Python script" tool (python_script) lets an administrator write def run(ctx) directly on the tool page — restricted execution in the engine process, with fixed output ports. Write a plugin when you need your own ports and parameters, an external dependency, or something a whole team will reuse.

Where to look when something does not load: External integration ▸ Plugins lists every file in the folder with what it mounted (tool:key, source:kind, comm:kind, dl:kind), whether it is disabled, and — for a file that failed — the exception or the missing package with the pip command. Rescan mounts files added since the server started and retries the ones that failed; a file that is already loaded needs a server restart after it changes, because Python modules cannot be reloaded safely. Connections of a plugin-provided kind are managed on that page unless the Writer declares section ("tcp", "modbus-server" or "modbus-client") to appear elsewhere. API: GET /api/vision/plugins, POST /api/vision/plugins/rescan (administrator).

1. Loading rules and the module variables

  • At start-up the platform scans plugins/ for single-file plugins (x.py) and folder plugins (x/__init__.py — drop a whole plugin project in), in name order, skipping anything starting with an underscore (_xxx.py, _xxx/). VISION_PLUGIN_DIR overrides the folder location (the default is plugins/ at the project root).
  • After importing a file, the loader finds the Tool, Grabber, Writer and Trainer subclasses that file defines itself and registers them. One file may hold several classes of different kinds.
  • A key or kind that clashes with a built-in, or with a plugin loaded earlier, does not override it: the loader logs and skips. A file that fails to load is logged and skipped too, without affecting other plugins or start-up.
  • The loader is apps/core/plugins.py; what loaded is in the backend start-up log ("plugin xxx.py loaded: tool:dark_ratio…").

Module-level variables control the display and whether it loads — by convention at the top of the file, so renaming or disabling on site does not mean touching the logic:

DISPLAY_NAME = "Dark ratio"      # the label
DESCRIPTION  = "Description…"    # the description
ENABLED      = True              # False = the whole file does not load

class MyTool(Tool):
    label = DISPLAY_NAME
    description = DESCRIPTION
    enabled = ENABLED            # per class: False disables only this one, the rest still load
VariableLevelEffect
ENABLED = FalseModule (top of the file)The whole file is skipped
enabled = FalseClass attributeOnly that class is skipped
label / descriptionClass attributeThe display name and description (a tool shows in the palette; a Grabber or Writer in the kind dropdown)
fieldsClass attribute (Grabber, Writer)A hint at the config field names for the settings page, e.g. ["path"]

2. A custom tool (example one: plugins/example_dark_ratio.py)

DISPLAY_NAME = "Dark ratio (sample plugin)"
DESCRIPTION = "The ratio of pixels darker than the threshold inside the ROI; above the allowed ratio it takes the fail branch."
ENABLED = True

import cv2
from apps.vision.tools.base import Param, Port, Result, Tool, ToolContext, ToolError, flow_out
from apps.vision.tools.roi import crop, region_overlay

class DarkRatioTool(Tool):
    key = "dark_ratio"                 # globally unique; this is what the graph JSON records
    label = DISPLAY_NAME
    description = DESCRIPTION
    enabled = ENABLED
    category = "detect"                # source|preprocess|locate|measure|detect|dl|logic|output
    icon = "Moon"                      # a lucide-react icon name
    params = [
        Param("roi", "Region", kind="roi", shapes=["rect", "rotated_rect", "circle", "polygon"]),
        Param("threshold", "Threshold", kind="number", default=80, minimum=0, maximum=255, teach=True),
        Param("max_ratio", "Allowed ratio", kind="number", default=0.1, minimum=0, maximum=1, step=0.01, teach=True),
    ]
    inputs = [Port("image", "Image", "image"), Port("roi", "Region (dynamic)", "region", required=False)]
    outputs = [Port("ratio", "Ratio", "number"), flow_out("pass", "Pass", "ok"), flow_out("fail", "Fail", "critical")]

    def execute(self, ctx: ToolContext) -> Result:
        image = ctx.require_image()
        if image.ndim == 3:
            image = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
        region = ctx.roi()
        c = crop(image, region, upright=True)
        if c.image.size == 0:
            raise ToolError("The ROI falls outside the image")
        pixels = c.image[c.mask > 0] if c.mask is not None else c.image
        ratio = float((pixels < ctx.number("threshold", 80)).mean()) if pixels.size else 0.0
        ok = ratio <= ctx.number("max_ratio", 0.1)
        overlays = [region_overlay(region, label=f"dark {ratio*100:.1f}%")] if region else []
        return Result(outputs={"ratio": ratio}, branch="pass" if ok else "fail",
                      status="ok" if ok else "ng", overlays=overlays, message=f"dark {ratio*100:.1f}%")

There is no register() to write — putting the file in the folder is enough. Restart the backend and "Dark ratio (sample plugin)" appears under Detect in the palette.

3. A custom outgoing connection (example two: plugins/example_csv_writer.py)

Outgoing connections (the "connections" of Modbus) extend the same way: subclass Writer and override only _open, _write, _read and _close — the lock, the timeout, the single reconnect on failure and the counters all live in the base class's write() and read(). The shipped example appends written values to a CSV file, which exercises the whole "flow → write Modbus tool → connection" path with no hardware at all:

DISPLAY_NAME = "CSV log (sample plugin)"
DESCRIPTION = "Appends every written value to a CSV file (time, address, value)."
ENABLED = True

import csv, os, time
from apps.comm.writers import CommError, Writer
from apps.core.errors import ValidationError

class CsvLogWriter(Writer):
    kind = "csv_log"                   # this is what Connection.kind records
    label = DISPLAY_NAME
    description = DESCRIPTION
    enabled = ENABLED
    fields = ["path"]                  # a config field hint for the settings page

    def __init__(self, config, **kw):
        super().__init__(config, **kw)
        self.path = str(config.get("path") or "")
        if not self.path:
            raise ValidationError("csv_log requires a path", code="comm_config")

    def _write(self, values):          # {address: value} → {"written": n}
        ...                            # the full implementation is in plugins/example_csv_writer.py

Once loaded, "CSV log (sample plugin)" appears in the kind dropdown on the Connections page. Create a connection with {"path": "D:/logs/results.csv"} as its config, put a "write Modbus" tool at the end of the flow, and give it the connection name. OPC UA, a vendor SDK and anything else follow the same pattern: raise CommError when you cannot connect, and the tool layer degrades according to on_error (which by default does not fail the run).

4. A custom image source (GigE, a vendor SDK, …)

Read this first: when the camera is on another PC, or needs a vendor SDK such as Basler or IDS, the built-in capture client already covers it — the SDK is installed on the camera's PC and the server needs nothing — so a plugin is usually unnecessary. A Grabber plugin suits devices the server itself can open, or unusual sources: a GigE Vision library, a streaming server, images out of a database.

# plugins/gige.py — drop it in plugins/ and it loads
DISPLAY_NAME = "GigE camera"
ENABLED = True

import numpy as np
from apps.vision.sources.grabbers import Grabber

class GigEGrabber(Grabber):
    kind = "gige"
    label = DISPLAY_NAME
    description = "A vendor SDK wrapper; config: serial, exposure_us"
    fields = ["serial", "exposure_us"]
    enabled = ENABLED

    def __init__(self, config, **kw):
        super().__init__(config, **kw)
        self.cam = open_camera(config.get("serial"))   # the vendor SDK
        self.cam.set_exposure(float(config.get("exposure_us", 5000)))
    def grab(self) -> np.ndarray | None:
        frame = self.cam.snap(timeout_ms=1000)
        if frame is None:
            self.last_error = "timeout"; return None
        self.frames += 1
        return frame                      # BGR or grayscale uint8
    def close(self): self.cam.close()
    def info(self): return {**super().info(), "serial": self.config.get("serial")}

Once loaded, the source appears in the kind dropdown on the Image sources page and its config is entered as JSON. The source object is cached and reused (it only reopens when the settings change), and grab() may be called from several flows' threads at once, so lock inside it yourself (self._lock).

5. Rules for writing a tool

  • Param.kind must come from PARAM_KINDS and Port.type from PORT_TYPES (apps/vision/tools/base.py).
  • For an expected failure, raise ToolError("…") (the node errors and the run fails). For "not found", return status="ng" or take a branch — do not raise.
  • Overlay coordinates are always in the full-image coordinates of this node's input image. For a rotated ROI, use crop(upright=True) and map back with Crop.to_full().
  • Never sleep or touch the database inside a tool. Use ctx.asset_path(id) for files and ctx.grab(source_id) for a camera.
  • For a heavy tool (deep-learning inference), cache the session at module level with a lock, and set heavy = True so the interface can say so.
  • Mark parameters that get adjusted on the line with teach=True — the teach page lists only those.

6. Integration: dependencies, separate projects, Python versions

A plugin loads into the platform process — that is what lets images travel as numpy arrays with no copying and a node cost around 0.1 ms — so the boundary is clear: if it can be imported into the platform's Python it loads in process; if it cannot, run it as a sidecar process and connect through an existing integration point. The plugins folder is VISION_PLUGIN_DIR (a checkout's plugins\; on a station C:\VisionSequence\plugins\, outside the version tree) and is always imported as the package plugins, so relative imports inside a folder plugin work the same in both. Three common situations:

6-1. The plugin has its own dependencies

  • They must be installed into the platform's Python — there is no second site-packages in one process. By convention a folder plugin ships plugins/<name>/requirements.txt and a single-file plugin plugins/<name>.requirements.txt; in a checkout .\scripts\dev.ps1 -Setup installs them all (or .venv\Scripts\pip install -r plugins\<name>\requirements.txt).
  • On an installed station (no internet, embedded Python) put the wheels next to the plugin — plugins\<name>\wheels\, or plugins\_wheels\ shared by all plugins — produced with pip download -r requirements.txt -d wheels --platform win_amd64 --python-version 3.12 --only-binary=:all:, and let vsctl plugins install <zip> / vsctl plugins deps install them offline (-Online allows PyPI). The station's Python is 3.12, so wheels must be cp312 or py3-none-any. Each installed version has its own site-packages; vsctl update reinstalls every plugin's dependencies into the new version before switching. The on-site steps and the zip layout are in deployment §11.
  • A missing dependency does not break anything: that plugin fails to load, the log says so and prints the install command, and everything else starts normally.
  • Follow the built-in pattern (pymodbus, onnxruntime): import heavy dependencies lazily inside the method, so "installed means usable" rather than "not installed means broken".
  • Version conflicts: write requirements as ranges (>=) rather than pinning. Where they conflict with the platform's own requirements.txt, the platform's pin wins — numpy and the vision library are the platform's call, so do not pin them separately.

6-2. The plugin is a separate project with its own repository

Three ways, from simplest to most formal:

ApproachHowSuits
(a) Drop the whole folder inPut the project (or its package directory) at plugins/<name>/ and import or define the classes to load in __init__.py — definitions in submodules re-exported from __init__ are recognised too — with a requirements.txt alongside.Deployment on site: copy the folder, restart, done
(b) pip install plus a thin adapterMake the plugin project a normal Python package and install it into the platform venv with .venv\Scripts\pip install -e D:\path\to\proj. Then put a few-line adapter in plugins/: from myproj.vision import MyTool, MyWriter — re-importing is enough to register it.A plugin developed independently, with its own tests and versioning
(c) A module path in .envAfter installing into the venv, set VISION_TOOL_PLUGINS=myproj.vision (the module calls register() itself).Deployments that would rather not touch the plugins/ folder

The principle in all three: the plugin project imports the platform, never the other way round, and it depends only on the four stable interfaces — the Tool, Grabber, Writer and Trainer base classes plus tools/roi.py. Compatibility of any other internal module is not guaranteed across upgrades.

6-3. The plugin needs a different Python version

One process has one interpreter. If the version differs — or dependencies genuinely cannot coexist, say two different major versions of numpy — it cannot load in process. Run it as a sidecar process instead, with its own Python and its own venv, maintained by the plugin's author, and connect it through an existing integration point. The platform core will not gain multiple interpreters or microservices:

What the plugin doesHow the sidecar connects
Image sourceThe sidecar grabs the image itself and calls the platform over HTTP: POST /flows/{id}/run with the image, or POST /sources/{id}/push to an upload source and then a trigger. Alternatively write a thin Grabber (no dependencies, the platform's Python) that asks the sidecar for a frame over HTTP or TCP.
Tool (inference or an algorithm)Write a thin Tool that encodes the image, sends it to the sidecar over HTTP or TCP and fills in a Result from the reply. Keep the timeout short and degrade — status="ng" or a warning — so a dead sidecar cannot drag the run down.
Outgoing connectionWrite a thin Writer that just forwards the values, or have the sidecar subscribe to SSE /events or poll the run API itself, which needs no platform code at all.

Try them in order: 6-1 (install into the platform venv) → 6-2(b) (package it) → 6-3 (a sidecar) only when the versions really cannot coexist. A sidecar adds a network hop and serialisation (milliseconds for an image round trip), so keep it for cases that need it.

7. Advanced: loading from .env

When you would rather not use the plugins/ folder — because the plugin is installed as a package, say — you can name module paths in .env:

VISION_PLUGIN_DIR=D:/site-plugins                     # a different folder (still auto-detected)
VISION_TOOL_PLUGINS=mypkg.my_tools                    # import this module; it calls register() itself
VISION_SOURCE_PLUGINS=gige=mypkg.gige:GigEGrabber     # kind=module:Class
VISION_COMM_PLUGINS=opcua=mypkg.opcua:OpcUaWriter     # kind=module:Class

Image sources and connections also keep the kind plugin: create one and name the class path directly in its config with "class": "mypkg.mod:Class".
