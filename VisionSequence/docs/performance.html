Performance report

Every built-in tool and the engine were benchmarked, the slow ones optimised without changing any interface, and the before-and-after recorded here along with the advice that follows from it. The raw numbers are in docs/bench-before.txt and docs/bench-after.txt; the measurement script is scripts/bench_tools.py.

1. The machine and the method

ItemDetail
CPUIntel Core Ultra 9 275HX (8 P-cores + 16 E-cores, a laptop), 32 GB RAM, Windows 11 Home 26200
SoftwarePython 3.12.10, the vision library 4.11, numpy 2.2.3, onnxruntime (CPU), with VISION_CV_THREADS=2 (the project default)
ImagesSyntheticGrabber (pattern=parts, seed=7, defect_rate=0): one 1280×960 and one 640×480 BGR image — a plate, five holes, barcode-like lines and Gaussian noise (σ=6)
Tool settingsEvery tool gets sensible parameters: the ROI sits on the plate or the centre hole; template_match's template is the centre-hole region cropped out of the same image (PNG); defect_diff's golden template is the whole grayscale image; the dl_* tools use the hand-built ONNX from tests/_helpers.py (GlobalAveragePool, Identity, Flatten). A tool with several representative settings gets several rows — blob whole-image versus blob in an ROI, for instance.
MeasurementA ToolContext is built and tool.execute() called directly, bypassing the engine. Each row warms up three times then runs 30 times, reporting the median and p95. The engine is measured separately on the "hole count" demo flow: the whole engine.execute() and the distribution across nodes. The "after" numbers use --pin for P-core affinity and high priority.
NoiseOn a laptop with mixed core types, anything under 0.5 ms carries about ±0.1–0.15 ms of single-run noise (allocator state, clock changes). So a difference below 0.15 ms or 8% is marked ≈ (within noise) and only a clear improvement counts. Tools whose code did not change (grayscale, blur, canny, hough, barcode…) should land on ≈ by construction.

4.2 The engine's fixed overhead

  • Forty formula nodes chained together: 0.23 ms in total, 5.7 µs per node, of which the tool itself is 4.2 µs and the engine loop (building the ToolContext, gathering inputs, registering outputs) about 1.5 µs. Far below the 0.05 ms that would be worth optimising.
  • The 40–60 µs per node measured on image flows is, under cProfile, 60% ImageStore._drop_run_locked: releasing several megabytes of numpy arrays when the images of a run eight runs ago age out, and the OS reclaiming the pages. That is the fixed cost of "keep the last N runs' images". The rest is _jsonable over blob's list of dicts.
  • Two small fixes were still worth making. ToolContext.params used to dict()-copy on every access; it now copies once per context (a tool calls param() repeatedly). And _jsonable no longer recurses element by element through lists of scalars (histograms, profiles, point coordinates): a single type(v) in (float, int, str, bool, None) scan returns them directly. store.put never copied the image in the first place.

The conclusion: JPEG encoding at 1–2 ms was never the bottleneck. The bottlenecks were (1) INTER_AREA taking its general path when shrinking by less than half — 1280 → 1024 costs 2.3 ms in the resize alone, more than the encode — so INTER_AREA is now used only at a scale of 0.5 or below and INTER_LINEAR otherwise; and (2) the front end fetching the same image several times during one preview (the node card, the viewer, the outputs tab), so results are now cached by ref, max_side and format, 64 entries LRU, cleared when the ref is overwritten or evicted. PNG is still expensive at 23 ms — use fmt=png only when you need it lossless.

5. What each optimisation did, and why

The rule: a tool's key, params, ports, output shape and output values do not change. An algorithm was only swapped where the results are provably identical. The one exception is template_match's coarse pyramid pass, which was heuristic to begin with, and where the candidate generation changed.

5.1 blob: filter the noise mask with connected components first (detect._prefilter_small)

After a fixed threshold over the whole image, background noise produces tens of thousands of one- and two-pixel white specks. findContours takes 41 ms over 38k contours (each one a Python numpy object) and another 9 ms to call contourArea on each. Now: sample every eighth row to count the density of horizontal 0/255 transitions, and above 2% run connectedComponentsWithStats (6.5 ms) to clear components whose bounding-box area is below min_area out of the mask, then findContours (0.7 ms). Bounding-box area is an upper bound on contourArea even with holes, so anything cleared would have been filtered by min_area anyway — contours, areas, centres and bounding boxes all come out identical (the equivalence test compares them item by item on a noisy mask, a clean mask and an inverted mask across five parameter sets). A clean mask — the demo flow's, after median and open — never triggers it, so it never pays the 2.5 ms. The output mask is still ANDed with the original, preserving the previous behaviour.

5.2 intensity and histogram: every statistic from one histogram pass (measure._roi_hist, _hist_stats)

These used to flatten the ROI pixels into one dimension (boolean indexing for non-rectangular shapes) and then call mean/std/min/max/np.median — where np.median over 1.2M pixels sorts for 5 ms and bincount takes 4.6 ms. Now a native histogram computation with the ROI as a mask (0.5 ms) gives 256 bin counts, from which the mean is Σh·v/n, the standard deviation comes from a second pass (Σh·(v−mean)²/n, matching numpy's definition), the extremes are the non-zero bins, and the median is found by cumulative count, taking elements (n−1)//2 and n//2 and averaging them — which is what np.median does for an even count. The equivalence test: all six statistics agree to within 1e-9 over the whole image, a circle, a small rectangle and a polygon; every histogram bin is equal; and the median matches for both odd and even pixel counts.

5.3 find_circle, find_line and caliper: batched edge detection, vectorised RANSAC

  • locate.find_edges_rows(): R profiles (find_circle's remap already produces an R×L matrix) get one GaussianBlur((k,1)), one np.gradient(axis=1), non-maximum suppression and parabolic sub-pixel refinement in a single pass. Every step is independent per row, so the results are identical to calling find_edges_1d row by row (the equivalence test compares 60 real and random profiles across three polarities and three smoothing settings, including lengths 1 to 5). A single profile — a caliper — keeps the scalar version, because vectorisation costs 0.1 ms more in fixed overhead than it saves.
  • caliper_points(): the in-band average of each caliper now comes from a cumsum along the long axis (float64 integer sums are exact) computed once for every band, then handed to find_edges_rows. Point coordinates and intensities are identical to the old per-band mean().
  • fit_circle_ransac and fit_line_ransac: 200 iterations each doing an rng.choice and an np.linalg.lstsq (3.9 ms) became one draw of 200 index sets, a closed-form three-point circle (a 2×2 linear system) and a 200×n distance matrix, with a single lstsq refit over the best inlier set. The sampling sequence differs from before (it uses rng.integers and rejects duplicate indices), but the final result is determined by the inlier set: in the benchmark scenes the inlier counts and residuals are identical, and the tests pass within 1 px.
  • The caliper tool's profile now uses the native per-row mean at CV_64F precision, which matches numpy's mean over uint8 (the tests compare to one decimal place).

5.4 template_match: an unmasked coarse pass, a pruned fine pass

A masked matchTemplate(TM_CCOEFF_NORMED, mask=) is four times slower than an unmasked one (2.8 versus 0.65 ms on the quarter-size image; 2.6 versus 0.36 ms in the fine window). When searching rotations, each angle's enlarged template bounding box needs a mask. The fix:

  • The coarse pass shares one centred, axis-aligned rectangle that still falls entirely inside the valid pixels at the largest angle (_inscribed_half), and every angle matches only that central region, without a mask. Sharing one region is what makes the scores comparable between angles — with per-angle crops of different sizes, a smaller crop scores higher and can push the correct 0° candidate out, which happened during implementation and was fixed. Candidate coordinates have the crop offset added back, so they still refer to the top-left of the full rotated template.
  • Pruning: candidates are sorted by score and at most three angles are refined per position (positions within half the downscaled template size count as the same one), with the total still capped at max_matches×4. Previously five angles each got a refinement pass on the same target.
  • The fine pass, and the no-pyramid path, are unchanged (the full template with its mask, exact scores). Verified: with rotations of +10°, −7° and 0°, and a large template at +12°, −6°, 0° and +3°, both pyramid modes return the same positions, angles and scores.

5.5 Caching decoded asset images (locate.read_asset_image)

Every run used to np.fromfile and imdecode the template: 5.5 ms for a 1280×960 PNG, slower than most tools. Decoded results are now cached by (path, gray), 32 entries LRU, invalidated on file mtime and size (an os.stat costs about 10 µs). The returned array is shared, so tools must not modify it in place — the existing ones only resize, crop or blur into a new array. This alone takes 0.2 ms off every template_match and 5.5 ms off every defect_diff.

5.6 defect_diff: caching the Hanning window and the template pre-processing

createHanningWindow costs 1.5 ms and scaling, cropping, blurring and converting the template to float32 about 1.7 ms — identical every time for the same parameters. They are cached against (template size, crop position, sub-image size, blur kernel, alignment method), 16 entries, holding the original template array and comparing it by identity so that a new decode of an updated file invalidates automatically. The remaining 19 ms is phaseCorrelate doing three FFTs at 1280×960, which is the algorithm itself; to make it fast, shrink the ROI (the 640×384 ROI version takes 0.8 ms).

5.7 Smaller items

  • apply_mask: a bitwise AND (1.9 ms) became a masked copy (1.1 ms; a freshly allocated destination is zeroed first). When a fill value is set, the destination starts filled and is then copied into — pixel for pixel identical.
  • roi.mask_for(offset=) and crop(): a non-rectangular ROI's mask is now drawn into a window the size of the bounding box, rather than allocating a full-image mask and slicing it (pixel_count on a circular ROI went from 0.14 to 0.04 ms, and the gap is far larger on 4K images).
  • ImageStore.encode caching and thumbnail interpolation (see 4.3).
  • Engine: the ToolContext.params cache and the _jsonable scalar-list fast path (see 4.2).

5.7b Polar unwrap (new tool, measured on delivery)

1280×960 BGR, annulus r 200–300, auto angle step (1885×101 strip), same machine as above, 55 runs after 5 warm-ups: 0.23 ms median, 0.25 ms p95 with linear interpolation (0.07 ms nearest, 0.62 ms cubic). The budget in the specification was 3 ms. The remap maps are built once per ring geometry and cached as fixed-point maps (cv2.convertMaps), so a run is the bare cv2.remap cost; the first run on a new ring adds about 0.1 ms for the map. polar_restore on 12 points and 12 contours is under 0.05 ms.

5.7c Contour tool chain (new tools, measured on delivery)

Same machine, 1280×960 mask with 40 filled circles (29 outer contours after touching ones merge), 30 runs after 3 warm-ups: contour_find 2.8 ms median (3.0 p95, dominated by findContours plus one filled-pixel count per contour), contour_filter 0.7 ms (area, perimeter and convexity for every contour), contour_geometry 1.9 ms (all measures including convexity defects and Hu moments for 29 contours, about 65 µs per contour), contour_match 0.3 ms (29 Hu-moment comparisons; the template contour is re-extracted from the cached template image each run, about 0.1 ms). The synthetic 400×300 rectangle gives an area of exactly 120000 px, and a 30 px triangular notch is reported as one convexity defect of 31 px.

5.7d Combined regions (WP-08, measured on delivery)

A composite region costs one extra mask per part: mask_for draws the base and then ORs, ANDs or AND-NOTs each part into it inside the crop window only, so intensity on the 1280×960 plate rectangle minus its centre hole runs in the same time as on a circle ROI (about 0.3 ms), and region_combine itself — which only builds the dict and the display outline — is under 0.2 ms. The bench rows intensity (composite roi) and blob (composite roi) track it.

5.7e Shading correction (WP-12, measured on delivery)

1280×960 grey, white reference as an image asset: 1.7 ms median, 1.9 ms p95 for the flat-field mode (30 runs after 5 warm-ups) — one cv2.multiply of the 8-bit frame by the cached float32 gain map straight into float32, then convertScaleAbs back to 8-bit; the gain map is built once per reference (cached by the decoded reference object, which itself follows the asset's mtime and size), and the two level outputs use cv2.mean rather than ndarray.mean (0.1 ms instead of 0.5). The background-estimate mode blurs at quarter resolution and scales the background back up: 3.9 ms at σ=51 instead of 12 ms at full resolution, with the corrected image's standard deviation unchanged (0.66 on the synthetic vignette). A synthetic radial vignette that leaves 50% in the corners is corrected from σ=19.7 to σ=0.5 grey levels.

5.7f Statistical template comparison (WP-07, measured on delivery)

Building: 30 good images of 640×480 with phase alignment in 0.2 s. Comparing: defect_stat at 640×480 19 ms median, at 1280×960 35 ms (phase correlation is the bulk — two full-frame DFTs — then one warp, the deviation map, the compare and blob analysis); align=none roughly halves it. On the synthetic set (brightness jitter ±10, shifts ±3 px, noise σ 3): 0 of 20 new good parts flagged at 4σ, a Δ40 stain caught at 11σ; with the jitter raised to ±15, defect_diff against a single golden image flags good parts at a 20-level threshold while defect_stat still flags none and still catches the stain — the reason the tool exists. Found on the way: cv2.phaseCorrelate multiplies its inputs by the window in place when the frame is already a DFT-optimal size (640×480 and 1280×960 both are), which silently corrupted a cached template; the template is now copied before the call in defect_diff as well.

5.8 Looked at and left alone

  • color_range already runs inRange over all three HSV channels; the cost is in cvtColor(BGR2HSV).
  • draw_result converts colour space only for a grayscale input; for a colour input it must copy(), since it cannot write into the upstream image.
  • findContours already uses RETR_EXTERNAL with CHAIN_APPROX_SIMPLE (CCOMP only when external_only is off).
  • The np.ascontiguousarray in the crop tool stays: its output goes into the image cache, and keeping a view would pin the entire original image in memory.
  • save_image keeps the default PNG compression level — changing it would change the file contents.

6. Advice

  1. Crop to an ROI before computing. Almost every tool's cost is proportional to pixel count: blob is 9 ms over the whole image and 0.2 ms in an ROI; defect_diff 25 ms versus 0.8 ms; intensity 1 ms versus 0.1 ms. Use the tool's own region parameter, or put a crop node in front so everything downstream works on the small image (with fixture_roi following after a locate step).
  2. Resize large images first. 1280×960 → 640×480 makes almost everything four times faster. Locating and counting are usually accurate enough at half resolution; do the measuring back on the full image inside an ROI.
  3. Clean up after thresholding, before blob. The demo flow's median 5 plus open 5 leaves blob at 2.5 ms; running blob straight on a noisy threshold result still costs 9 ms even with the new pre-filter. Alternatively set a realistic min_area — the pre-filter only engages at min_area ≥ 4.
  4. For template_match, keep the pyramid on, keep the template ≥ 32 px, and do not make the rotation range or step too fine. Without the pyramid a full-image NCC is 23 ms. The cost is the number of angles times the per-angle cost: ±10° in 5° steps is five angles at 12 ms. An ROI on the search area halves it again.
  5. VISION_CV_THREADS. The default of 2 is the parallelism inside a single tool's algorithm. When the line runs one flow at a time, 4 is worth it (blur, canny and cvtColor at 1280×960 get another 1.5–2× faster). With several flows in parallel (a pool of 10), keep it at 2 or 1 so the algorithm threads do not fight over cores. Restart manage.py serve after changing it.
  6. Encoding only happens when somebody looks. The image cache defers JPEG encoding until a request arrives, so while continuous mode runs flat out, do not leave the editor's large viewer open (1.9 ms per image at 1600 px — though the second request for the same image is now free). Use PNG only when you need it lossless (23 ms).
  7. Turn off persistence and image retention you do not need. VISION_KEEP_RUN_IMAGES (8 by default) is how many runs' node images each flow keeps, and a 1280×960 flow produces 6–10 MB per run; set it to 1 or 2 when nobody is reviewing on the line, which cuts both memory and the release cost that dominates the engine's overhead. VISION_KEEP_RUN_ROWS and the background persister only write summaries and cost little, but on a slow disk SQLite still prefers a larger threshold or persistence turned off.
  8. Choose defect_diff's alignment. Phase correlation over a full 1280×960 image is 19 ms; with a fixed fixture and little movement, choose "no alignment" (0.8 ms), or align only inside an ROI.
  9. Scan only the area and the symbologies you need. QR detection over a whole image is 10 ms; give it an ROI and restrict the type to QR or to 1D.
  10. Save as JPEG or BMP. PNG compression at 1280×960 costs 6.4 ms (BMP is almost free, JPEG about 2 ms), and only_ng saves only the rejects.

6b. Capture client transfer (large frames)

Getting a camera image from a capture client into the server is measured separately by scripts/bench_capture.py. The headline: a 20-megapixel colour frame (59.9 MB) reaches 117 fps through shared memory on the same machine (2.7 ms per frame to copy on the server side), while across machines the network decides — about 18 fps on 10 GbE. The two things that matter are reusing the receive buffer (reallocating 60 MB costs 17 ms, reusing it 2.4 ms) and using np.copyto so the GIL is released. The full tables, the bandwidth comparison and the tuning options are in Capture client §7.
