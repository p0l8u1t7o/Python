Front-end / back-end contract

What the two halves agree on, so they can be worked on in parallel.

Back end (settled — do not change these interfaces)

  • Django 5.1 with django-ninja. manage.py at the root, settings in config/settings.py (the VISION dict).
  • Tool framework apps/vision/tools/base.py: Param, Port, flow_out(), ToolContext, Result, Tool, register(), catalogue().
  • ROI helpers apps/vision/tools/roi.py: crop(image, region, upright=) → Crop(image, x0, y0, mask, inverse), plus Crop.to_full(x, y), points_to_full(pts), region_overlay(region), mask_for() and transform_region().
  • Built-in tools live in apps/vision/tools/builtin/{source,preprocess,locate,measure,detect,dl,logic,output}.py; each module exposes TOOLS = [...].
  • The engine is apps/vision/engine.py (a dataflow DAG in topological order with branch gating); the Runner is apps/vision/runner.py (thread pool and the SSE bus).
  • The API is documented in the docstring at the top of apps/vision/api.py. SSE: GET /api/vision/flows/{id}/stream?since= and GET /api/vision/events.

The graph JSON

{
  "nodes": [{"id": "blob-1", "type": "blob", "label": "Find holes", "description": "", "enabled": true,
             "continue_on_error": false, "color": "", "params": {...}, "position": {"x": 0, "y": 0}}],
  "edges": [{"id": "e1", "source": "gray-1", "source_handle": "image", "target": "blob-1", "target_handle": "image"}]
}
  • source_handle is the output port key of the source step; target_handle is an input port key, or "_flow" for the control input.
  • An output handle of type: "flow" (if_number's true and false, for instance) may only connect to _flow.
  • type: "note" is a comment: it never runs and nothing can connect into it.

The ROI region (the value of a kind=roi parameter)

{"shape":"rect","x","y","w","h"} | {"shape":"rotated_rect","cx","cy","w","h","angle"} |
{"shape":"circle","cx","cy","r"} | {"shape":"annulus","cx","cy","r_inner","r_outer"} |
{"shape":"polygon","points":[[x,y],...]} | {"shape":"line","x1","y1","x2","y2"}

Coordinates are pixels of that step's input image, origin top left.

The overlay dict (Result.overlays, drawn in the step's input image coordinates)

kind: rect(x,y,w,h,angle?) / circle(cx,cy,r) / annulus / polygon(points) / polyline(points) / line(x1,y1,x2,y2) / point(x,y) / points(points) / text(x,y,text) / contours(contours=[[[x,y],...]]).

Shared fields: color as "#rrggbb", label, width, dash, fill.

Identity and the shape of an error

  • User token: Authorization: Bearer <token> on every endpoint, event streams and images included. Where a browser cannot set a header, ?token= works. Integrator key: X-API-Key or ?api_key=.
  • Every error is {"error": {"code": "…", "message": "…", "details": {…}}} — including 401 (unauthenticated). Branch on code; message gets reworded between versions.
  • The event streams /api/vision/events and /api/vision/flows/{id}/stream are text/event-stream and are not in the OpenAPI schema; their addresses come from GET /vision/integration/info.

The RunReport (returned by run and preview, and carried by the SSE run_finished event)

{id, flow_id, flow_version, trigger, status: ok|ng|failed, started_at, finished_at, duration_ms, error,
 outputs: {...named outputs},
 nodes: {node_id: {status: ok|ng|error|skipped, duration_ms, message, branch, outputs: {port: value}, overlays: [...], overlay_on, detail, logs}}}

An image output is {"ref": "runid:node:port" | null, "width", "height", "channels"}; fetch it from GET /api/vision/images/{ref}?max=1024&fmt=jpeg|png. When the run is no longer cached the endpoint falls back to the image archive, so an archived reject can still be opened days later.

Preview mode (POST /flows/{id}/preview with {graph, context?, reuse_image_ref?}) keeps every intermediate image, and detail._input_ref points at each step's input image.

Preview extras (used by the tool page)

  • POST /flows/{id}/preview also takes until_node (run only that step and its ancestors) and analysis: true (adds analysis: {input:{ref,histogram,stats}, output:{port,ref,histogram,stats}, series:{"blobs.area":{count,min,max,mean,values}}}).
  • POST /flows/{id}/scratch-image (multipart image) → {ref,width,height,name}: a scratch image that never enters the source library; pass it back as reuse_image_ref.
  • DELETE /flows/{id}/recent clears the in-memory history and statistics and emits the SSE event cleared.

Notes on Param.kind

  • range is a single number shown as a slider plus a number box (using minimum, maximum and step) — not two numbers.
  • code is a code string (accept names the language; only python so far, for the python_script tool). The editor renders it monospaced with line numbers, read-only for anyone who is not an administrator. Only code an administrator has saved is approved to run (apps/vision/scripts.py: POST/PATCH /flows and import register the sha256; anyone else sending unapproved code gets 403 script_not_approved). A recipe cannot override code, and the server adds _script_admin to the preview context itself — any _ key arriving from outside is dropped.
  • Every tool's outputs end with the implicit port {"key":"_overlays","type":"list","implicit":true} carrying that step's marks, ready to wire into draw_result.
  • Bit depth: an image port carries uint8 (the norm), uint16 (16-bit grey or RGB) or float32. A tool declares what it accepts through Tool.accepts; anything outside that is normalised to 8-bit by ToolContext.image() (u16 shifted right by 8, floats min-max scaled) without touching the input array. Convert explicitly with the convert_depth tool. See Inspection capabilities.
  • Every tool also has the implicit pass-through port {"key":"_image","type":"image","implicit":true}: the image goes on untouched, because marks are metadata and are never drawn into it. Tools with no image input (the logic ones) get a matching _image input, so a picture can travel through any step — including a disabled one. The pass-through ref appears in the run report only when something is wired to it: it is not an "after" result, and the viewer and the tool page's analysis both ignore _image.

Front-end skeleton (settled)

  • frontend/ is Vite with React 19, TypeScript, Tailwind v4, @xyflow/react, TanStack Query, react-router, lucide-react and i18next.
  • src/index.css holds the semantic palette (bg-surface, text-muted, bg-brand, text-critical and so on) and the component classes .btn-primary, .btn-secondary, .btn-ghost, .btn-icon, .input, .card.
  • src/lib/api.ts: api.get/post/postForm/patch/delete, imageUrl(ref, max), assetUrl, sourcePreviewUrl, streamUrl(flowId, since).
  • src/lib/types.ts holds every type (ToolTypeDef, Region, Overlay, GraphNode, Flow, RunReport and the rest).
  • The tool catalogue arrives in English and is the source of truth. src/lib/toolLocale.ts overlays a Chinese dictionary in one place, so no screen needs to know about it.

Deploying the two halves separately

The front end is a static SPA that talks to the back end only through frontend/src/lib/api.ts (HTTP) and lib/flowStream.ts (SSE). Every path is built on BASE_URL; page code never calls fetch directly.

ArrangementFront endBack end
Same origin (the default)npm run build, served by whitenoise from the API process, BASE_URL=/apimanage.py serve
DevelopmentVite dev server proxying /api to port 8000as above
Separate hostsbuild with VITE_API_BASE_URL=https://vision.example.com/api and put it on any static host or CDNset CORS_ALLOWED_ORIGINS=https://console.example.com in .env
  • Authentication: a user token goes in Authorization: Bearer, an integrator key in X-API-Key. Requests that cannot carry a header — <img> and EventSource — append ?token= or ?api_key= through withKey().
  • Each page is its own lazy chunk (App.tsx), so the first paint loads only the shell and the current page; the big shared libraries (React, React Flow, the charts) are split out so they cache.
  • Response shapes and error codes are in the sections above. A new endpoint that keeps to these schemas needs no front-end change.
