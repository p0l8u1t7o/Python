Capture client: drive the camera where it is, send the images to the server

Cameras are often attached to another PC on the line, or need a vendor SDK (Basler pylon, IDS peak) even on the same machine, while the server keeps its rule of one API process with no camera SDKs in it. The capture client is a Windows desktop program you download from the web interface: it drives webcams, Basler and IDS cameras on the PC they are attached to and connects out to the server's capture port (9100 by default) to register its name and its camera channels. Add an image source of kind "capture client camera", pick the client and the channel, and flows run. On the same machine images travel through shared memory with a control message as the event (one memcpy); across machines through a single persistent TCP connection with a fixed binary header, losslessly (raw or LZ4). The server parses nothing and hands the ndarray straight to the engine. Measured: 20 megapixels in colour (59.9 MB a frame) at 117 fps on one machine (see §7). After the server rebuilds the client, everyone already connected is told and can update themselves (see §2-5). The interface speaks English, 繁中 and 简中, in a dark or a light theme.

1. The idea and the architecture

the camera's PC (VisionSequenceCapture.exe)                 the server (one API process)
  cameras/  webcam | basler | ids | ueye | fake ──┐         apps/vision/capture/
  channel   one acquisition thread and a latest  ─┤ TCP:9100  hub.py     CaptureHub: listens, one ClientSession thread per client
            frame slot per channel                │           grabber.py CaptureGrabber(kind="capture") ← Runner._grab
  transport connect, reconnect, answer GRAB,     ─┼─────────▶ api.py     /vision/capture/* (clients, preview, stream, download)
            push streams                          │ + SHM
  shm       the shared-memory ring (same machine)─┘           shared protocol: vscapture/protocol.py (the server imports the same file)
  ui/       connection, channels, preview and ROI, parameters, delivery, log
  • Three parties: the capture client (drives the camera and sends images), the server hub (the registry, one reader thread per client, handing frames to the engine) and the web interface (configures the source, shows the state, turns streaming on, offers the download).
  • Two acquisition modes, per channel. On demand: the server sends a GRAB for each run and the client returns a frame taken after the request — the lowest latency and the least bandwidth, for triggered inspection. Continuous stream: the client pushes the latest frame up to an fps limit and a run uses whatever is current — for dashboards and continuous running.
  • Why the client connects outwards: the camera's PC is often behind NAT or a firewall and its address changes. The server opens one fixed port, the client owns reconnecting and re-registering, and the web interface only has to know a name.
  • The seam does not change: a flow's acquire step → ctx.grab() → grab_by_id → CaptureGrabber.grab() returns an ndarray, and the array handed to the engine is always exclusively owned (the raw receive buffer is the array, or the LZ4 output, or one copy out of a shared-memory slot).

2. Installing and connecting

2-1. Download and start

  1. "Download capture client" at the top of the Image sources page, or Integration ▸ Capture (which shows the version, size, SHA-256 and build time). The button is disabled until the server has built it; how to build is in §12.
  2. Unzip it anywhere (avoid very long paths; no administrator rights needed) and run VisionSequenceCapture.exe. The first time, Windows SmartScreen may say the publisher is unknown: choose "More info" then "Run anyway".
  3. Settings live in the menu bar: Settings ▸ Connection, Settings ▸ Camera channels and Settings ▸ Delivery each open their own small window, while the main window keeps what you watch while the line runs — the connection status card, the channel list with its state, the live preview, the camera parameters and the log.
  4. The Connection window (Settings ▸ Connection, or the Settings button on the status card): the server's hostname or IP, the port (9100 by default), the client name (what the web interface shows; reconnecting from the same machine replaces the old connection), the key (only needed when the server has VISION_CAPTURE_AUTH or VISION_API_KEY set), local mode (automatic, force shared memory, or always TCP) and whether to connect at start-up.
  5. Press Connect on the status card. The status bar shows connected, the round-trip latency, frames sent, the rate and the transport in use (shared memory or TCP).

2-2. Configuration, logs and headless mode

  • The configuration file is %APPDATA%\VisionSequenceCapture\config.json (VSCAPTURE_CONFIG overrides it): the connection (including auto_update, idle_stop_s and shm_max_mb), interface preferences (ui.language, ui.theme) and each channel's camera parameters, ROI and delivery settings. "File → Save settings" writes it, and closing with unsaved changes asks. Missing keys get defaults, unknown keys are ignored, and an invalid value is reported at start-up and replaced with the default.
  • The log is %APPDATA%\VisionSequenceCapture\logs\capture.log (rotating, 2 MB × 3); the Log panel at the bottom filters by level.
  • Headless: VisionSequenceCapture-console.exe --headless --connect (Ctrl+C to stop), suitable for Task Scheduler or a service wrapper. --list-cameras lists what is available; --server host:port, --name, --api-key, --config and --log-level DEBUG override the configuration; --minimized starts in the tray.
  • Closing the window minimises to the system tray (right-click for show, connect, disconnect, exit).

2-3. The interface: language and appearance

The top right of the window switches the language (English, 繁體中文, 简体中文 — the same three as the web interface) and the appearance (dark or light). Both take effect immediately without restarting and are saved with the settings (ui.language, ui.theme). The standard camera parameter names (exposure time, gain, frame rate, pixel format, width, height, offsets, trigger mode) are translated; a vendor's own parameters keep their SDK names, and a channel name is your own text and is never translated.

The layout: the connection status card and the channel list (with open, close, start and stop) on the left, the live preview and the ROI toolbar in the middle, the camera parameters on the right, and a collapsible log at the bottom. Adding, removing and renaming channels, choosing the camera kind and device, and the delivery settings live in their own windows under the Settings menu. When a new version exists, a banner appears at the top. The brand colour matches the web interface, and dark is the default.

The window resizes freely and the layout follows (the splitters between columns can be dragged too):

2-5. Automatic updates

After the server rebuilds the client (scripts/build_capture_client.ps1), every connected client finds out by itself — nobody has to walk the line reinstalling:

  1. WELCOME already carries the version the server holds, and after that every heartbeat compares against the manifest, pushing a notice only when it changes. Only a version newer than the client's own is announced.
  2. The installer is pulled down the same authenticated capture connection in 1 MiB chunks — no second port, no second key, and nothing to do with being signed in to the web interface. The download is checked against its SHA-256 and discarded entirely if it does not match.
  3. It is unpacked into %APPDATA%\VisionSequenceCapture\updates\staging-<version>\, and then the new version's console executable takes over: wait for the old process to exit, overwrite the installation folder, restart. The updater runs from the new folder, so it cannot overwrite itself, and the configuration and logs live in %APPDATA% and are untouched.

The connection window's automatic update setting has three values: off never checks, notify shows a banner and leaves the decision to you (the default), and auto downloads and installs by itself. The banner shows the version, the size and the download progress, and can be cancelled. "Help → Check for updates" asks at any time. In headless mode only auto actually updates (the others just write to the log). Running from source never overwrites in place; it downloads, unpacks and tells you.

Every failure is safe: an interrupted download, a SHA-256 mismatch or a locked file is logged, and the existing version carries on acquiring. The updater retries for 30 seconds while overwriting, in case an antivirus or a file handle is holding on. An older client (from before automatic updates existed) is unaffected by a newer server — it simply will not update itself, so download it again from the web interface.

3. Channels, preview and ROI

  • A channel is one camera: a name, a camera kind (kinds whose SDK is not installed are disabled with the reason), a device (found by "Scan", or typed in directly — a webcam index of 0, say), whether it is enabled (so the server may acquire from it) and whether to preview live. Four buttons — open, close, start, stop — and a status light: closed, opening, open, acquiring, error. Thirty consecutive failed grabs reopen the camera automatically.
  • Preview: the latest frame, downscaled, at the preview fps (15 by default), with a HUD showing the sequence number, fps, size and hardware ROI offset.
  • Drawing an ROI: drag on the preview to create it, eight handles to resize, drag to move, and X/Y/width/height fields that work both ways. "Clear ROI" returns to full frame, and nothing takes effect until "Apply ROI". With "use the camera's hardware ROI" ticked, cameras that support it (Basler, IDS, the simulator) read out only that region, giving a higher frame rate, and the coordinates are aligned to the camera's increment and written back; cameras that do not support it are cropped in software before sending. An ROI is always stored in full-sensor coordinates, and the frame's metadata carries roi_x/roi_y/full_w/full_h, while the flow still works in the coordinates of the image it received.
  • Snap one: shown when the trigger mode is software trigger, it fires the camera once.
  • The camera parameters tab presents everything as a tree, edited in place on the right. The standard parameters (exposure, gain, frame rate, pixel format, width, height, offsets, trigger mode) are under "Basic" and the rest under "Advanced"; an industrial camera's parameters follow the SDK's own categories (a category name containing "/" becomes several levels). The search box at the top filters by name or SDK name (matching groups expand automatically), and both the expansion state and the search text survive a reload. A change is applied 250 ms later and the actual value written back; a parameter that needs acquisition stopped (width, height, offsets, pixel format) asks first and resumes afterwards; "Save to settings" applies it again next start-up.
  • The delivery tab: the encoding (uncompressed, LZ4 or JPEG), the JPEG quality, convert to mono, downscale by 1/2 or 1/4, the mode (on demand or continuous stream) and the streaming fps limit, with the transmitted size and an estimate per frame. "Test send" transmits the current frame once and reports the round trip, the bytes, and the encode and server-side decode times. Changing the ROI, mono or downscale renegotiates the shared-memory segment (falling back to TCP meanwhile).

Server-side tools can also write camera parameters before a grab, drive camera output lines, and load or save a user set. The client advertises this with features.channel_set; servers do not send those messages to older clients. Parameter writes, line writes and user-set operations run through the channel command queue on the capture client, so the SDK object is still touched only from its own camera thread. A line pulse is restored by a timer on the capture client, not by a server-side sleep.

3-1. Idle power saving

Free-running acquisition burns CPU continuously (20 megapixels at 30 fps measured at about 13% of one core). When nobody wants images, acquisition stops:

  • What counts as wanting images: the interface being visible with live preview on for that channel, the server having a stream open, or the server having asked for a frame within the configured window.
  • When it stops: the window is minimised to the taskbar or the tray (nobody is watching the preview) and the server has not asked for a frame for longer than idle stop seconds (in the Connection panel, 60 by default; 0 disables it). Only acquisition stops — the camera stays open, with its parameters and ROI intact.
  • How it comes back: automatically when the server next asks for an image (costing one acquisition start-up), or when the window comes to the foreground. The channel list marks it "(idle)".
  • A channel the server is streaming is never paused — that means the server wants images continuously. Pressing Stop yourself is not an idle pause and will not be undone automatically.
  • Minimising also stops the preview repainting, saving the downscale and conversion work.

Measured (20 megapixels, 30 fps, the simulated camera): about 13% of one core while acquiring, 0% once paused.

5. Shared memory on one machine, TCP across machines

5-1. Shared memory (same machine)

  • The test: the connection comes from loopback (or one of the server's own addresses), the hostnames match, and the client's local mode is automatic or forced. WELCOME then returns local:true.
  • The client creates one multiprocessing.shared_memory segment (named vs_cap_<name>_<pid>_<random>): a 64-byte header (magic, canary, slot count, slot size) followed by K slots. One segment per connection, with the slot size the largest frame of any enabled channel (aligned to 4096) and K = 4 + 2 × the number of channels, capped at 16. SHM_OFFER → the server attaches and checks the canary → SHM_ACCEPT; a refusal simply stays on TCP.
  • The event is a FRAME message on the control connection (slot ≥ 0, empty payload): about 50–100 µs over loopback, carrying the sequence number and the metadata. The server does out = np.empty(...) then out.data.cast("B")[:] = buf[off:off+n], one copy (about 0.5–1 ms for 1280×960×3), and returns SLOT_FREE immediately.
  • Ownership: once FRAME is sent the slot belongs to the server, and SLOT_FREE gives it back. The client only writes free slots; in on-demand mode, if no slot comes free it sends the payload over TCP instead, and in streaming mode it drops the frame. A slot is only overwritten as an orphan when it is the oldest, its sequence is at least 2K behind, and it has been held for over a second — at which point the server has clearly not returned it. Frames not yet sent are dropped during renegotiation, because the old slot indices can no longer be used.

5-2. TCP (across machines)

  • A single persistent connection, with control and data multiplexed by req_id; TCP_NODELAY and 4 MiB socket buffers; at most one GRAB in flight per channel.
  • Receiving: raw goes through recv_into straight into an np.empty (the receive buffer is the array); lz4 goes into a session-level bytearray then lz4.block.decompress(uncompressed_size=raw_len); jpeg (lossy, only when explicitly chosen) is decoded and its size checked.
  • The "auto" encoding: raw on the same machine, LZ4 across machines when both ends have it, raw otherwise. Bandwidth measures in order of value: convert to mono (÷3), crop to an ROI, LZ4 (typically 1.5–3×), a streaming fps limit, and downscaling.
  • Back pressure: the client keeps only the latest frame per channel with one in flight, and the server keeps only the latest per channel. The heartbeat: a PING after two idle seconds, and after three heartbeats with no reply the connection drops and reconnects with exponential backoff (up to 30 seconds; a fixed 30 after an authentication failure). After a server restart the client reconnects and re-sends its streaming settings.

7. Performance and bandwidth

The target: 20 megapixels in colour (5472×3648×3 = 59.9 MB a frame) reaching the server at 60 fps. That is 16.7 ms a frame and 3.59 GB/s of movement — a rate only shared memory on one machine can reach (see §7-3 for the network limits).

7-2. Four things that matter for large frames

  1. Reuse the receive buffer (the biggest single factor). A 60 MB np.empty asks the operating system for fresh pages every time and faults them in on first write — measured, allocating and filling costs 17 ms while reusing an existing buffer costs 2.4 ms, seven times better. The server pools per channel and the client per camera, and only a buffer the pool is the sole holder of is reused (decided by reference count), so a frame already handed to the engine or still being published can never be overwritten. The pool needs at least three: the published latest frame, the one being sent, and the one being written — with fewer it falls back to allocating every frame. This one change took on-demand capture from 38.7 to 117.6 fps.
  2. Copy in a way that releases the GIL. Assigning through a memoryview slice holds the GIL for the whole copy (a background Python thread drops to 39% speed); np.copyto releases it (99%). The server is a single API process, and 60 fps × 60 MB holding the GIL would drag the whole machine down — so reading out of shared memory uses a temporary ndarray view plus np.copyto, and the view is discarded the moment the copy is done (never keep an ndarray view on shm.buf, or close() raises BufferError).
  3. Send an uncompressed frame with no copies. It used to be tobytes() once and joining the header and payload once more, 17 ms each. RAW now sends the array's memoryview directly, with the header and payload as two sendall calls and no copying at all.
  4. The shared-memory segment must be large enough, but bounded. The slot size is the largest channel's frame (60 MB for 20 MP colour) and the slot count is 4 + 2 × channels, converged with a total cap (512 MB by default) — one channel with six slots is 360 MB. The first pass of writes brings the pages into physical memory, and after that each frame costs 2.3 ms.

So 20 MP colour at 60 fps means running the capture client on the server machine — the camera on the server, the SDK installed there. To go across machines and still keep the frame rate, in order of value: convert to mono (÷3), crop to an ROI and send only what is needed, downscale by 1/2 (÷4), LZ4 losslessly (typically 1.5–3×, and better on the flat backgrounds of industrial images), JPEG (lossy, only when the bandwidth genuinely is not there), and lower the fps limit. For example, 20 MP mono with an ROI taking half of it plus LZ4 exceeds 60 fps on 10 GbE.

7-4. Downstream on the server

Once the client hands the image over, the cost is the flow itself: 60 fps means the inspection must finish inside 16.7 ms (see the performance report; a tool costs roughly 16 times as much at 20 MP as at 1280×960, so downscale first or work only inside an ROI). The image cache also defaults to 1024 MB (VISION_IMAGE_CACHE_MB) and keeps the last eight runs' images per flow (VISION_KEEP_RUN_IMAGES) — one 20 MP frame is 60 MB, so at high frame rates lower both, or keep images only for rejects.

7b. When a frame does not arrive in time

A camera that misses its trigger should not look like a broken flow. The acquire step has an On timeout setting:

  • Report an error (default, and what earlier versions always did): the run fails and the step is marked with the reason.
  • Judge NG: the step returns NG and takes its timeout branch, so the line can react to a missed part the same way it reacts to a bad one. Combine it with the flow setting “stop when a step judges NG” and the run ends cleanly as NG rather than as an error.

Only a genuine timeout takes that path. A capture client that is not connected at all, or a channel that does not exist, is still reported as an error, because those are setup problems rather than production events.

Reconnecting. A streaming source notices when the capture client has dropped and come back as a new connection: it asks for the stream again and starts counting frames from scratch. Without that, the source would sit waiting for a frame number the new connection is never going to reach, and the symptom on the line is a camera that never produces another picture until the server is restarted.

8. Troubleshooting

  • It will not connect: check the server was started with manage.py serve (runserver does not open the capture port), that the firewall allows 9100, and that the address is one the client can reach. The Integration information bar says whether the capture port is listening.
  • auth_failed: the server has VISION_CAPTURE_AUTH or VISION_API_KEY set and the client's key must match. A failure waits a fixed 30 seconds before retrying.
  • name_taken: another machine is already connected under that name. Reconnecting from the same machine replaces the old connection automatically.
  • protocol_unsupported: download the client again from the web interface so it matches the server.
  • The web interface says "capture client offline": the program is closed or disconnected; it comes back within five seconds of reconnecting. A run meanwhile fails with "capture client <name> is not connected".
  • Timeouts: the camera is not acquiring, there is no trigger in trigger mode, or the exposure exceeds timeout_ms. Check on the client that the state is "acquiring" and the preview is live.
  • too_large: raise VISION_CAPTURE_MAX_FRAME_MB, or downscale or crop on the client.
  • Shared memory was not accepted: the log gives the reason and the program stays on TCP. Setting local mode to "always TCP" forces it.
  • A webcam is not found by scanning: another program has it (close the conferencing software), or the USB port cannot power it. Typing the index 0 or 1 directly also works.
  • The frame rate suddenly drops, or the first frame is slow: this may be the first acquisition after an idle pause, which has to start the camera again. On a line where that delay is unwelcome, set idle stop to 0 or use continuous streaming.
  • No update appears: the server has to have built one (build_capture_client.ps1) and its version must be higher than the client's. Nothing is announced when automatic update is set to off. Version 0.1.0 has no update mechanism at all — download it again.
  • An update failed: the log gives the reason (an interrupted download, a SHA-256 mismatch, a locked file). The existing version keeps acquiring, and you can always download the zip and overwrite by hand. When antivirus software holds the executable, the updater retries for 30 seconds.
  • An SDK is missing: only the SDKs present at build time are packaged. Rebuild on the server with -WithBasler or -WithIds, and install the vendor's runtime or driver on the client PC.

9. The protocol (v1, vscapture/protocol.py)

Little endian. Every message is ENVELOPE(16 B) | header(hlen) | payload(plen), where ENVELOPE = "<HBBIII": magic 0x5643, version 1, type, req_id (0 means it is not a request), hlen, plen. Control messages use a JSON header; hot-path messages use a fixed struct. Limits: hlen ≤ 1 MiB, plen ≤ MAX_FRAME, at most 32 channels, and names matching [A-Za-z0-9_\-.]{1,64}.

The server validates a FRAME: the channel is in range, the dtype and channel count are legal, stride == width × channels × itemsize, raw_len == stride × height ≤ the limit, raw implies plen == raw_len, and shm implies slot < slots with raw_len ≤ slot_bytes. Anything else is ERROR(malformed) and the connection drops — a partially read stream cannot be resynchronised safely. Changing the protocol means changing vscapture/protocol.py, apps/vision/capture/hub.py and this section together.

10. Security

  • The registration key is compared with hmac.compare_digest, and a failed attempt waits half a second before replying, as a throttle. An empty key means no check at all, which is only advisable on an isolated production network.
  • Nothing is processed before HELLO; every message has a size limit; names and channel fields are validated against an allow-list; and anything oversized or malformed drops the connection immediately.
  • Shared memory is only negotiated over loopback with matching hostnames, and the segment name contains a random component with a canary that is checked.
  • The web-facing preview, stream and download endpoints use the platform's own identity (a sign-in token or an API key), and the streaming switch returns 423 while the engine is locked.

11. Acceptance checklist with real cameras

  1. A webcam at 1080p MJPG reaching 25 fps or better; manual and automatic exposure both taking effect; reopening after being unplugged and replugged.
  2. Basler USB3 and GigE: Mono8 and BGR8 conversion correct; the hardware ROI aligned to the increment with the coordinates written back; software trigger latency; hardware trigger on Line1; the PYLON_CAMEMU=1 emulated camera.
  3. IDS peak: acquisition still works after changing the pixel format (the buffers are reallocated); Line0 trigger; the hardware ROI.
  4. A clean PC: with and without each vendor runtime, the disabled camera kinds give the right reason, and the support listed in the zip's README matches reality.
  5. Same machine: the CPU and latency of shared memory versus "always TCP"; status.shm === true.
  6. On a LAN: two channels streaming at 10 fps each plus concurrent on-demand grabs; the bandwidth of LZ4 against raw.
  7. Reconnecting automatically after a server restart and after 30 seconds with the network cable out, with the streaming settings restored.
  8. Running the console build permanently under Task Scheduler or a service wrapper; connect, disconnect and exit from the tray.
  9. "Reload settings" after editing the configuration file while running rebuilds the channels and reconnects.
  10. Automatic update: the banner appears after the server rebuilds, the download shows progress, and it overwrites and restarts into the new version; "download and install automatically" also updates in headless mode; an interrupted download and a SHA-256 mismatch are both logged without disturbing acquisition.
  11. The interface: all three languages switch instantly (the standard camera parameter names included), dark and light both switch, and both survive a restart.
  12. The parameter tree: the category levels are right for a real camera (Basler, IDS), search filters, the expansion state is kept, and changing a parameter still applies and writes back.
  13. Power saving: minimised to the taskbar with the server idle, the channel shows "(idle)" and the CPU drops; the next server request resumes it and returns a correct frame; a streaming channel is never paused.
  14. Window resizing: all three layouts, the ROI toolbar folding, and the minimum size still usable.
