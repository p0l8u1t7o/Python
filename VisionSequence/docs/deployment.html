Deployment and operations

How to put VisionSequence on a customer's PC and keep it running: the setup wizard, the folder layout, HTTPS, the client PCs that only run a browser, plugins and the deep-learning add-on on site, backup, upgrade and rollback. Everything is Windows, which is what the machines on a line run. The station needs no internet connection: the release carries its own Python and every package, and plugins and the deep-learning pack install from files.

1. What you are installing

One machine, one API process, one station. Engine state, the image cache and the event bus live inside that process, so a station is one PC running one copy of the platform. Browsers on other PCs, equipment and camera PCs all talk to that one process.

C:\VisionSequence\                 (the install root)
├─ app\1.0.0\      the release tree: python\, apps\, config\, frontend\dist\, docs\, scripts\, tools\ (never edited)

├─ data\           database, assets, image archive, logs, backups, downloads (the capture client), run\serve.pid

Several stations do not share one server. Each station is its own install; an MES or dashboard polls them all for one yield overview (§14).

2. Requirements

  • Server PC: Windows 10/11 or Windows Server 2016+, 64-bit. Nothing else to install — the release brings Python 3.12 and, if missing, the Microsoft Visual C++ runtime. 2 GB of disk for the program, plus the image archive (capped by VISION_ARCHIVE_MAX_GB) and run history; 4 GB of memory for classic inspection, 16 GB when frames are 20 MP.
  • GPU (optional, deep-learning tools only): NVIDIA with a driver that supports CUDA 12.8; the add-on pack (§12) brings everything else.
  • Client PCs: only a browser — Chrome or Edge 111+, Firefox 128+, Safari 16.4+. Older browsers see a plain notice instead of a blank page (§7).
  • Network: the station's ports reachable from the line's subnet (§5). No internet is required at any point; with internet available, vsctl plugins deps -Online can fetch plugin dependencies from PyPI.
  • Camera PCs: whatever the camera vendor's SDK needs, plus the capture client (its own page).

The last page shows the web address, and the summary in the log (data\logs\ is not there yet; see the console the installer opens) names the keys. Unattended installs for many stations:

VisionSequence-Setup-1.0.0.exe /VERYSILENT /SUPPRESSMSGBOXES /DIR=C:\VisionSequence /STATIONID=ST01 ^
    /HOSTNAMES=vision-st01,192.168.1.10 /SUBNET=192.168.1.0/24 /HTTPS=internal /ADMINUSER=admin /ADMINPASSWORD=********

The installer is not code-signed, so SmartScreen shows "Windows protected your PC" the first time: choose More info › Run anyway. Running a newer setup on an installed station is an upgrade (§10); running the same version again repairs the files and keeps the data.

What the script does, in order: checks the tree and the VC++ runtime → creates the folders → writes .env only if it does not exist (DEBUG=0, a random SECRET_KEY, random API, capture and TCP keys, absolute DATA_DIR and VISION_PLUGIN_DIR) → puts the tree at app\<version> and points current at it → migrate → creates the administrator if there are no accounts → publishes the capture client into data\downloads → writes the Caddyfile → firewall rules → installs and starts the services → waits for /healthz → doctor → prints the summary. Re-running is safe.

Everything on site goes through C:\VisionSequence\vsctl.cmd (it always runs the version current points at):

The API runs as the Windows service VisionSequence through NSSM (shipped in tools\): delayed automatic start, restart five seconds after any exit, service.log rotated at 20 MB, and a Ctrl-C stop with a fifteen-second grace period so uvicorn shuts down cleanly — the Modbus slave closes its port, the database checkpoints, event streams end. Use the Services console or vsctl interchangeably.

A camera on the server PC itself. A vendor SDK usually needs a signed-in desktop session, which a service does not have. Install with -Mode task -Interactive -User PLANT\vision -Password …: a scheduled task that starts when that user signs in, with the platform in their session. Keep the PC signed in (automatic sign-in) or the platform is not running after a reboot. Cameras on other PCs, through the capture client, are unaffected by this choice.

6. HTTPS

Browsers on other PCs should reach the station over HTTPS: a plant LAN is rarely a trusted network, and company policy usually says so anyway. The proxy is Caddy, shipped in tools\ and run as the service VisionSequenceProxy. Three modes:

ModeCertificateOn each client PC
internal (default)Caddy runs its own certificate authority and issues a certificate for every host name and IP you listed; leaf certificates renew themselvesImport the CA root once: C:\VisionSequence\certs\root.crt, exported by the installer (vsctl certs export refreshes it). Copy it to the client PC and either double-click it › Install certificate › Local Machine › Trusted Root Certification Authorities, or run certutil -addstore -f Root root.crt from an elevated prompt (vsctl certs import -File root.crt does the same from the station's own scripts). Firefox needs Settings › Privacy › Certificates › Import or the enterprise-roots policy.
customA certificate from your IT department for those host names (-Cert fullchain.pem -Key private.key; copied to certs\)Nothing, if the issuer is already trusted in the company
noneNo proxy; the API listens on 0.0.0.0:8000 in plain HTTPNothing — acceptable only on an isolated line network

The generated Caddyfile is short, and you may edit it (vsctl proxy restart applies it; vsctl proxy configure regenerates it):

vision-st01, 192.168.1.10, localhost, 127.0.0.1 {
    tls internal                     # or: tls "certs\server.crt" "certs\server.key"
    request_body { max_size 256MB }  # image uploads, dataset imports
    reverse_proxy 127.0.0.1:8000 { flush_interval -1 }   # SSE: results arrive as they happen
}

With HTTPS on, the API binds 127.0.0.1 and .env has BEHIND_HTTPS_PROXY=1, so the platform trusts the proxy's X-Forwarded-Proto and X-Forwarded-Host headers. HTTP/2 through the proxy also removes the browser's six-connections-per-host limit, which matters with several dashboards open.

Only at the root. The web interface, /api, /assets and /docs are absolute paths: a station can be https://vision-st01/ or https://plant.example.com:8443/, never https://plant.example.com/st01/. Distinguish stations by host name or port. If you front the station with your own nginx or IIS instead of Caddy, keep the same three rules: do not buffer responses (SSE), allow large bodies, forward X-Forwarded-Proto, and install with -Https none then set BEHIND_HTTPS_PROXY=1 and bind the service to loopback (vsctl service install does that when a Caddyfile exists; otherwise pass -BindHost 127.0.0.1 to scripts\service.ps1).
# nginx equivalent
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_read_timeout 300s;
    client_max_body_size 256m;
}

7. Client PCs and browsers

Anyone on the line uses the station from a browser; nothing is installed on their PC. What to know when several people and several PCs use one station:

  • Address: any host name or IP given at install (-HostNames) works, and the certificate covers all of them. A name typed that is not in the list is refused by the platform (ALLOWED_HOSTS) — add it with vsctl env set ALLOWED_HOSTS=… and vsctl proxy configure -HostNames …, then vsctl restart.
  • Browsers: Chrome or Edge 111+, Firefox 128+, Safari 16.4+ (the interface relies on modern CSS). An older browser gets a plain-text notice naming those versions instead of an empty page; the fix is to update the browser on that PC, not the station.
  • How many tabs a station serves: every open dashboard, flow editor or integration page holds one live event stream; the station allows VISION_SSE_MAX_STREAMS of them (64) and answers "too many streams" beyond that, at which point a page falls back to polling. A tab in the background releases its stream after fifteen seconds and reconnects when it is shown again, so the practical limit is the number of pages people are looking at, not the number they have open.
  • Language and theme follow the account: what a user picks in Settings is stored with their account and applied on every PC they sign in from. Before sign-in the browser's language decides.
  • Shared PCs: signing out (or a session expiring) clears the assistant conversation, the TCP command history and any API key from that browser; the theme and layout preferences stay with the PC. Sessions expire after AUTH_TOKEN_TTL_HOURS (default 336, two weeks) — set it short on a shared operator station.
  • Operator stations / kiosks: give the line an operator account (it can run, change over and touch on-site parameters but not edit flows), open the dashboard with msedge.exe --kiosk https://vision-st01/dashboard/1 --edge-kiosk-type=fullscreen if the PC should show nothing else, and on a touch screen the interface enlarges buttons and inputs automatically.
  • Two engineers editing the same flow: the last save wins and the other editor sees the flow list refresh. Agree on who owns a flow while it is being tuned, or use recipes for the parameter differences.
  • Camera PCs are not browsers: they run the capture client from the Integration › Capture page and connect to port 9100 with VISION_CAPTURE_AUTH; see the capture-client page.
Kiosk Auto Load. Sign in once as the operator account in a dedicated Edge or Chrome profile on the kiosk PC, then set Windows startup or Task Scheduler to open msedge.exe --kiosk https://vision-st01/dashboard/1?autostart=1 --edge-kiosk-type=fullscreen --user-data-dir=C:\VisionSequenceKiosk\Edge. The browser profile stores the normal VisionSequence bearer token under that Windows user profile; no administrator token is involved, and the server still checks the operator's flows.run permission before starting continuous mode for the flows used by that dashboard. This is a stored credential on the machine: anyone who can use or copy that Windows profile can act as that operator until the token expires. To revoke it, disable or delete the operator account on the Users page, shorten AUTH_TOKEN_TTL_HOURS for kiosk stations, sign out from the kiosk browser, or delete the dedicated browser profile folder and sign in again with a fresh account.

8. Accounts and keys

  • People sign in with a user account. Three roles: administrator (accounts, permissions, system settings), engineer (flows, sources, models, tuning), operator (run, change over, on-site parameters). What each role may do is adjustable on the Users page. The first administrator is created by the installer; give the line an operator account, not a shared administrator one.
  • Integrators (MES, HMI, PLC gateways) send X-API-Key; the key is vsctl env get VISION_API_KEY. An integrator can always run, even while the engine is locked, so treat the key as a production credential and rotate it (vsctl env set VISION_API_KEY=…, vsctl restart) when contractors change.
  • Equipment on the TCP port sends AUTH <key> first (VISION_TCP_AUTH); an empty value disables the check. Camera PCs use VISION_CAPTURE_AUTH.
  • Every change is recorded in the audit trail (administrators; CSV export). Executions are in each flow's statistics, not the audit trail.
  • Forgotten administrator password: vsctl admin create admin resets it from the console.

9. Backup and restore

vsctl backup                                  # data\backups\visionsequence-<stamp>.zip
vsctl backup -Out \\nas\vs\st01.zip --with-images --with-wheels --with-client

A backup contains the database (copied through SQLite's backup API, so a backup taken while the line runs is consistent), assets, .env (the keys — --no-env to leave it out of a shared location), the plugins folder (without its wheels\ unless --with-wheels) and the capture-client manifest (--with-client adds the zip). Archived inspection images are the bulky part and come only with --with-images.

vsctl restore \\nas\vs\st01.zip               # stops the service, restores, migrates, starts

Restoring overwrites the database, assets and plugins. The previous database is kept beside the new one as vision.sqlite3.before-restore-<stamp>; a restored .env is written as .env.from-backup for you to merge, never over the live one. A nightly backup to a share, keeping fourteen:

$a = New-ScheduledTaskAction -Execute "C:\VisionSequence\vsctl.cmd" -Argument "backup -Out \\nas\vs\$(hostname)-$(Get-Date -f yyyyMMdd).zip"
Register-ScheduledTask -TaskName "VisionSequence backup" -Trigger (New-ScheduledTaskTrigger -Daily -At 2am) -Action $a -User SYSTEM -RunLevel Highest

9a. Data retention and automatic clean-up

Every store has a keep-by date, set on the Settings page (administrators) and saved in the database, so it takes effect without a restart. The defaults keep a year of run detail, audit trail and measurements; archived pictures and user file outputs keep their own 90 days and 20 GB caps, because files are what actually fill a disk. Hourly totals are never deleted, so yield curves survive any clean-up. Zero in any field means "keep for ever".

SettingDefaultWhat it controls
Run detail365 daysFlowRun rows: the per-node timings, outputs and picture references behind the run list (KEEP_RUN_ROWS per flow is still the backstop)
Audit trail365 dayscore.AuditLog: who changed which flow, recipe, account or lock
Measurements365 daysMeasurementLog: one row per numeric named output per run, what SPC reads
Archived pictures90 days / 20 GBThe image archive on disk; whichever limit bites first
File outputs90 days / 20 GBDATA_DIR\file_outputs by default: CSV/TXT rows from Write log and pictures from Save
Backups kept10Backup zips in data\backups and pre-restore database copies, newest first, each kind counted separately
Maintenance window03:00The hour in which backups are trimmed, unreferenced pictures dropped and the database compacted (VACUUM)

Why it never gets in the way of inspection: the clean-up runs on the thread that already writes run history, and only in the gaps between runs. It deletes in batches of 500 rows and checks before each batch whether anything is queued, running or in continuous mode — if it is, it stops and picks up later. The heavy jobs (trimming backups, dropping pictures nothing refers to, VACUUM, which locks the whole database for a few seconds) wait for the maintenance window and for a full minute of idleness. Nothing runs on the engine thread, and the settings are cached in memory, so a run never waits on a database read for them.

"Clean up now" on the Settings page does the same work immediately, whatever the hour. On the command line:

vsctl manage purge --dry-run                  # what would go
vsctl manage purge --pictures                 # also drop fixed pictures nothing refers to
vsctl manage purge --runs 90 --backups 5      # override the saved settings for one run
vsctl doctor                                  # "retention" and "backups" lines: settings, last clean-up, sizes

The API is GET /api/vision/retention (settings, last clean-up, usage), PATCH with any of the fields above, and POST /api/vision/retention/sweep to run it now — administrators only, and every change is audited.

9b. File outputs for QA and traceability

The Write log tool writes one CSV row or TXT line per inspected part. The Save tool writes the selected image. Both are user-configured outputs under DATA_DIR\file_outputs by default, or under VISION_FILE_OUTPUT_DIR when the station is configured with a separate disk. A tool's path is always a relative folder below that root; daily folders use yyyyMMdd, and filenames may use the same placeholders as Format a reply, such as {station}, {date}, {lot} and {run_id:.8}.

These files are not the image archive. The archive is controlled by each flow's archive policy and exists so the statistics and run-history pages can show source or result pictures later. File outputs are for plant-side QA, traceability and hand-off to another system. They are queued in memory and written by a background thread; when the queue is full the platform drops that output and keeps inspecting. Preview runs and batch sandbox runs do not write files.

Retention covers the file-output tree with the saved file_output_days and file_output_max_gb settings, defaulting to VISION_FILE_OUTPUT_DAYS=90 and VISION_FILE_OUTPUT_MAX_GB=20. The same idle clean-up thread trims old files by age first, then by total size.

10. Upgrading and rolling back

vsctl update VisionSequence-1.1.0-win64.zip   # or run VisionSequence-Setup-1.1.0.exe on the station

What happens, in order — and what stops it:

  1. The zip is checked against SHA256SUMS.txt if that file sits beside it.
  2. A backup is taken: data\backups\pre-update-1.0.0-to-1.1.0.zip. This is the rollback point.
  3. The new tree is unpacked to app\1.1.0.partial and renamed to app\1.1.0 only when complete.
  4. While the old version is still running, the new Python installs the plugins' dependencies (from their wheels\, plugins\_wheels\, or PyPI with -Online) and reinstalls the deep-learning pack recorded in DL-PACK.json from packs\. Every version has its own site-packages, so the old tree is untouched.
  5. The service stops, the new version runs migrate. If that fails the new tree is renamed .failed, the old version starts again and the command exits 1 — nothing has changed for production.
  6. A newer capture client shipped in the release is published to data\downloads (camera PCs update themselves over their existing connection).
  7. current is switched, the service starts, /healthz must answer with the new version, doctor runs, a line goes into updates.log, and versions older than the previous one are removed (-Keep).
vsctl versions                                # installed trees, which is current, which is the rollback target
vsctl rollback                                # back to the previous version (the tree is still there)
vsctl rollback 1.0.0 -RestoreDb               # also restore the pre-update backup when the database was migrated since

A rollback only switches the junction and restarts; the old version's packages, plugins and deep-learning pack are exactly as they were. It warns when the database was migrated after that version (the update log records the migration count) — then use -RestoreDb, which restores the pre-update backup first. Migrations only add columns and tables, so running an older version on a newer database usually works but is not guaranteed.

11. Plugins on site

Plugins live in C:\VisionSequence\plugins\, outside the version trees, and are loaded as the package plugins whichever version is current. To hand a plugin to a customer, ship a zip laid out like the folder it lands in:

my_plugin.zip
└─ my_plugin\                 (or: my_plugin.py + my_plugin.requirements.txt for a single-file plugin)
   ├─ __init__.py
   ├─ requirements.txt
   └─ wheels\                 every dependency as a wheel for Python 3.12 / win_amd64
      ├─ somepkg-1.2-py3-none-any.whl
      └─ other-3.4-cp312-cp312-win_amd64.whl

The author produces wheels\ on any PC with internet: pip download -r requirements.txt -d wheels --platform win_amd64 --python-version 3.12 --only-binary=:all:. Wheels shared by several plugins can go to plugins\_wheels\ instead. Then on the station:

vsctl plugins install my_plugin.zip           # copies it in, installs dependencies offline, restarts the service
vsctl plugins install my_plugin.zip -Online   # allow PyPI when wheels\ is incomplete and the station has internet
vsctl plugins list                            # every file in plugins\ and whether it loaded (the same as the Plugins page)
vsctl plugins deps [my_plugin] [-Online]      # (re)install dependencies, e.g. after copying a folder by hand
vsctl plugins rescan                          # mount new files without a restart (changed files still need vsctl restart)

The Python version is fixed at 3.12: wheels must be cp312 or py3-none-any. A plugin that needs another Python, or dependencies that conflict with the platform's, runs as a sidecar as described on the plugins page. vsctl doctor lists plugins that failed to load, with the reason.

12. The deep-learning add-on pack

Deep-learning tools (network training and inference, SAM labelling, GPU ONNX inference) need torch, ultralytics and onnxruntime-gpu — about 3 GB that most stations do not need and that must match the GPU driver. They ship separately as VisionSequence-DL-cu128-<version>.zip (NVIDIA, CUDA 12.8 — required for RTX 50, fine for older cards) or -cpu- (no GPU), with the stock detection and SAM2 weights included so nothing is downloaded on site:

vsctl dl install VisionSequence-DL-cu128-1.0.0.zip -Predict   # installs into the current version, copies the weights, runs one inference
vsctl dl check -Predict                                       # later: torch/CUDA, kernel architectures, ORT providers

The pack is kept in packs\ and recorded in the version tree's DL-PACK.json, so vsctl update reinstalls it into the new version automatically. The GPU driver is the customer's: nvidia-smi must show a driver that supports CUDA 12.8 or the pack falls back to CPU. Details and the traps are on the deep-learning page.

12a. Silent warmup

Some tools are slow the first time after a service start: deep-learning models load, CUDA or ONNX sessions are built, and script modules may initialise caches. Silent warmup runs selected flows once in the background after /healthz is already answering. It uses the same direct execution path as batch testing, then drops the image cache for that run, so it does not create run history, change live statistics, emit run SSE events or store variables.

SettingDefaultWhat it does
VISION_WARMUPoffoff disables startup warmup, commissioned warms enabled flows that have been commissioned on the teach page, and all warms every enabled flow.
VISION_WARMUP_TIMEOUT_S30Per-flow execution deadline used by the warmup run.
VISION_WARMUP_FLOWSemptyOptional comma-separated flow id list. When set, only those flows are considered.

Keep the default off for classic OpenCV-only stations or while commissioning a line. Enable commissioned on stations with DL inference or expensive script tools so the first production part does not pay the cold-start cost. Warmup never grabs a live camera frame on startup: a flow that depends on image_source is warmed only when a recent source image is already in memory; otherwise it is reported as skipped. Operators can run the same path manually with vsctl manage warmup --flows 1,2 or vsctl manage warmup --all.

14. More than one station

Each station is independent, which keeps the engine simple and the failure of one line from taking out another. Give every station its own VISION_STATION_ID (the installer's station page; the silent switches make a mass rollout a one-line script per station). To see several stations together, poll GET /api/vision/summary on each from your own dashboard or MES: it answers with the station id, version, lock state and today's totals per flow, straight from the hourly roll-up. Nothing is pushed to a station; mark how old each number is.

15. Disaster recovery

What happenedWhat to do
Service keeps restartingvsctl logs has the traceback. Common causes: a port already taken (the connection status names it), a database from a newer version (rollback with -RestoreDb), a broken .env edit (vsctl env list).
Browsers show a certificate warningThe client PC has not imported certs\root.crt, or the address typed is not among the host names: vsctl proxy configure -HostNames … then vsctl proxy restart.
Disk fullvsctl purge --dry-run to see what would go, then run it; lower VISION_ARCHIVE_MAX_GB and VISION_KEEP_RUN_DAYS; vsctl versions prune removes old trees.
Database corruptvsctl restore the last backup. SQLite in WAL mode survives a power cut, not a failing disk.
Whole PC deadInstall the same version on new hardware (§3), vsctl restore the backup (§9) — it brings .env, plugins and keys — reinstall the DL pack, reconnect the cameras. The station id keeps the history continuous.
Forgotten administrator passwordvsctl admin create admin
A PLC cannot connect to a Modbus slaveThe connection status names the reason; a port taken by another program is the usual one, and the firewall rule for that port may be missing (vsctl firewall -Ports 5020).
An upgrade went wrongvsctl rollback; the pre-update backup is in data\backups.

16. Security notes

  • The installer writes DEBUG=0, a random SECRET_KEY, random API, capture and TCP keys and a narrow ALLOWED_HOSTS; vsctl doctor fails when any of these is back at an insecure value.
  • Behind the proxy the API is loopback only; the public surface is 443, 9000 and 9100, each authenticated, and the firewall rules limit them to the line's subnet.
  • User tokens are stored as SHA-256 hashes and expire (AUTH_TOKEN_TTL_HOURS); tokens and API keys are masked in the access log.
  • Responses carry X-Content-Type-Options: nosniff, a same-origin referrer policy and X-Frame-Options: SAMEORIGIN; HSTS is deliberately not set so a station can fall back to HTTP when a certificate expires.
  • Python script tools run in the engine process. Only code an administrator has saved is approved to run, imports are allow-listed and a watchdog applies, but treat the ability to save scripts as shell access on the station.
  • The image archive holds pictures of your product with no separate access control: put data\ on a volume with the permissions you want, and remember it when you decommission a machine.

Three scripts produce everything a customer receives; they run on a development PC with internet the first time, and from build\cache afterwards:

Prepare a build PC once with scripts\setup_prereqs.ps1 -Release: it installs whatever is missing through winget (Python 3.12, Node.js LTS, Git, Inno Setup 6) and then sets up the development environment.
