Deployment and operations

How to put VisionSequence on a factory PC and keep it running: install, start at boot, back up, upgrade, monitor, recover. Everything here assumes Windows, which is what the machines on a line normally run; the platform itself is plain Python and Django and runs on Linux with the same steps minus the scheduled task.

1. What you are installing

One machine, one API process, one station. Engine state, the image cache and the event bus all live inside that process, so a station is a single server with a single copy of manage.py serve. That one command serves the web interface, the HTTP API, the TCP command port and the capture-client port.

PieceWhat it isWhere it lives
API processWeb UI, HTTP API, SSE, TCP commands, capture hub, Modbus connectionsmanage.py serve (uvicorn, one worker)
DatabaseFlows, recipes, run history, users, audit traildata\vision.sqlite3 (SQLite, WAL)
AssetsTemplate images, models, dataset versions, batch imagesdata\assets\
Image archiveKept inspection images (off by default)data\archive\ or VISION_ARCHIVE_DIR
Capture clientOptional desktop program on the camera PCIts own machine; connects out to port 9100
Several stations do not share one server. Each station runs its own copy, and an external system can poll them all for a single yield overview (see §10).

2. Requirements

  • Windows 10/11 or Windows Server 2019+, 64-bit. Linux works too; only the scheduled task in §4 is Windows-specific.
  • Python 3.12 (the version the virtual environment is built with).
  • Node.js 20+ only if you intend to rebuild the web interface; a shipped build does not need it.
  • Disk: 2 GB for the program, plus whatever you allow the image archive (default cap 20 GB) and the run history (a run row is roughly 1.5 KB).
  • Memory: 4 GB is enough for classic inspection. The image cache holds the last few runs per flow in RAM; a 20 MP colour frame is 60 MB, so a station running large frames wants 16 GB.
  • GPU: optional, only for deep-learning tools. NVIDIA with CUDA 12.8 drivers; see the deep-learning page for the install order, which matters.

3. First install

git clone <your copy> C:\VisionSequence
cd C:\VisionSequence
.\scripts\dev.ps1 -Setup          # creates .venv, installs requirements, migrates, seeds demo data

Then create the first administrator and the settings file:

.venv\Scripts\python.exe manage.py create_admin --username admin
copy .env.example .env            # edit it: see the table below

The settings that matter on a new station:

SettingDefaultWhy you would change it
VISION_STATION_IDST01Stamped on every run; make it the real station name so reports and roll-ups are readable.
SECRET_KEYdev valueAlways change it. Session and token signing depend on it.
DEBUG1Set to 0 in production: no stack traces to the browser.
ALLOWED_HOSTS*Narrow it to the station's own name and IP.
VISION_API_KEYemptySet it so integrators authenticate with X-API-Key. Empty means the HTTP API accepts any logged-in user only.
VISION_ARCHIVE_DEFAULToffSet to ng to keep reject images for every new flow on this station.
VISION_KEEP_RUN_DAYS30How long run detail is kept. The hourly yield rollup is kept forever regardless.
DATA_DIRdata\Move the database, assets and archive to a data disk.

Check the result before going further:

.venv\Scripts\python.exe manage.py doctor

4. Starting at boot

scripts\dev.ps1 is for development — it opens windows and dies with your session. On a station, register the scheduled task instead. Run PowerShell as administrator:

.\scripts\install_service.ps1                       # runs as SYSTEM on port 8000
.\scripts\install_service.ps1 -User "PLANT\vision" -Password "…" -Port 8000
.\scripts\install_service.ps1 -Uninstall

The task starts at boot with no login, restarts the process a minute after any exit, never runs two copies, and rotates data\logs\service.log at 20 MB keeping the last ten. Inspect or stop it from Task Scheduler like any other task.

A camera opened by the capture client on another PC is unaffected by this account choice. A camera plugged into this PC through a vendor SDK may need a real user session — if the camera cannot be opened under SYSTEM, install the task under a dedicated user account instead.

5. Ports, firewall and reverse proxy

PortWho connectsSetting
8000Browsers and HTTP integrators--port
9000Equipment sending one-line TCP commandsVISION_TCP_PORT
9100Capture clients connecting out from camera PCsVISION_CAPTURE_PORT
5020…PLC masters, when the platform acts as a Modbus slavePer connection

Open only what you use, and only to the line's subnet:

New-NetFirewallRule -DisplayName "VisionSequence API" -Direction Inbound -LocalPort 8000 -Protocol TCP -Action Allow -RemoteAddress 192.168.1.0/24

For HTTPS, put IIS or nginx in front and proxy to 127.0.0.1:8000. Two things must be right or the live view breaks: do not buffer the event stream, and allow long-lived connections.

# nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_buffering off;              # SSE: results must arrive as they happen
    proxy_read_timeout 300s;
}

6. Accounts and keys

  • People log in with a user account. Three roles: administrator (accounts, connections, system settings), engineer (flows, sources, models, tuning), operator (run, change over, on-site parameters). Give the line an operator account, not a shared administrator one.
  • Machines use VISION_API_KEY and send X-API-Key. An integrator can always run, even while the engine is locked, so treat the key as a production credential and rotate it when staff change.
  • Every change is recorded in the audit trail (Audit trail page, administrators only), and can be exported as CSV. Executions are not recorded there — they are in each flow's statistics.

7. Backup and restore

.venv\Scripts\python.exe manage.py backup                       # data\backups\visionsequence-<stamp>.zip
.venv\Scripts\python.exe manage.py backup --out D:\bak\vs.zip --with-images

The database is copied through SQLite's own backup API, so a backup taken while the line is running is consistent. Assets are included; archived inspection images are not unless you ask, because they are the bulky part.

Restoring overwrites the database and assets, so stop the station first:

Stop-ScheduledTask -TaskName VisionSequence
.venv\Scripts\python.exe manage.py restore D:\bak\vs.zip --yes
.venv\Scripts\python.exe manage.py migrate
Start-ScheduledTask -TaskName VisionSequence

The database that was there is kept beside the new one as vision.sqlite3.before-restore-<stamp>.

A sensible schedule is a nightly backup to a network share, keeping fourteen:

$t = New-ScheduledTaskTrigger -Daily -At 2am
$a = New-ScheduledTaskAction -Execute "C:\VisionSequence\.venv\Scripts\python.exe" `
     -Argument "manage.py backup --out \\nas\vs\$(hostname)-$(Get-Date -f yyyyMMdd).zip" `
     -WorkingDirectory "C:\VisionSequence"
Register-ScheduledTask -TaskName "VisionSequence backup" -Trigger $t -Action $a -User SYSTEM -RunLevel Highest

8. Upgrading and rolling back

  1. Back up first — manage.py backup. This is the rollback.
  2. Stop the task: Stop-ScheduledTask -TaskName VisionSequence.
  3. Update the code (git pull, or replace the folder keeping data\ and .env).
  4. .venv\Scripts\pip.exe install -r requirements.txt then manage.py migrate. Migrations only add; no release so far removes data.
  5. Start the task, then manage.py doctor and open the web interface once.
  6. Check the version in the sidebar footer matches what you installed.

Rolling back: put the old code back and restore the backup taken in step 1. Restoring an old database under new code is fine; new code under an old database is not, because the migrations will be missing.

Capture clients update themselves over their existing connection when a newer build is published on the server — see the capture-client page. Clients older than 0.2.0 predate that feature and must be downloaded again.

An integration engineer debugging equipment should use the commands and results panel on the integration pages instead of the log: while that page is open every command and reply on the interface is listed live.

10. More than one station

Each station is independent, which is what keeps the engine simple and the failure of one line from taking out another. Give every station its own VISION_STATION_ID so its runs and its hourly roll-up are identifiable.

To see several stations together, poll GET /api/vision/summary on each of them from your own dashboard or MES: it answers with that station's id, version, lock state and today's totals per flow, straight from the hourly roll-up, so the numbers match what the station itself shows. Nothing is ever pushed to a station, so a roll-up cannot affect production; do mark how old each number is, because a stale figure that looks live is worse than no figure.

11. Disaster recovery

What happenedWhat to do
Process keeps restartingdata\logs\service.log has the traceback. Common causes: a port already taken (the connection status names it), a missing .env, a database from a newer version.
Disk fullmanage.py purge --dry-run to see what would go, then run it. Lower VISION_ARCHIVE_MAX_GB and VISION_KEEP_RUN_DAYS.
Database corruptRestore the last backup. SQLite in WAL mode survives a power cut, but not a failing disk.
Whole PC deadInstall on new hardware (§3), restore the backup (§7), reconnect the cameras. The station id in .env keeps the history continuous.
Forgotten administrator passwordmanage.py create_admin --username admin --password … resets it from the console.
PLC cannot connect to a Modbus slaveThe connection status names the reason; a port taken by another program is the usual one. manage.py doctor lists connections with errors.

12. Security notes

  • The API binds 0.0.0.0 so the line can reach it. On a plant network that is normally right; on anything routable, put it behind a proxy and a firewall rule.
  • SECRET_KEY and VISION_API_KEY belong in .env, which is not in version control. Rotate the API key when integrators change.
  • User tokens are stored as SHA-256 hashes and expire after fourteen days.
  • Python script tools run in the engine process. Only code an administrator has saved is approved to run, and imports are allow-listed with a watchdog — but treat the ability to save scripts as equivalent to shell access on the station, and keep the administrator role to the people who should have it.
  • The image archive holds pictures of your product. It is a folder on disk with no separate access control: put it on a volume with the file permissions you want, and remember it when you decommission a machine.
