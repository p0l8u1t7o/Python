06 · REST API 參考

ExpAnalysis 的所有功能都經由這組 REST API 提供；內建的網頁介面只是它的第一個客戶端。 這份文件逐一說明每個端點的參數、回應與實際呼叫範例，並解釋哪些端點會觸發重運算、 快取怎麼運作、以及錯誤該怎麼讀。

1. 基本資訊

項目值
預設位址http://127.0.0.1:8848（可用 EXPA_HOST / EXPA_PORT 覆寫）
API 前綴/api
互動式文件/api/docs（FastAPI 自動產生的 Swagger UI）
OpenAPI schema/api/openapi.json
編碼一律 UTF-8，回應不做 ASCII 轉義（中文直接輸出）
認證無。這是綁在 127.0.0.1 的單機離線工具。
/api/docs 是最快的探索方式 FastAPI 依據 Pydantic 模型自動產生完整的互動式介面，可以直接在瀏覽器裡填參數送出請求、 看到真實回應。這份文件補的是自動文件給不了的東西：為什麼這樣設計、 哪些端點很慢、以及回應中的關鍵欄位怎麼判讀。兩份搭配著看。
沒有認證，所以不要對外開放 預設監聽 127.0.0.1，只有本機能連。如果為了讓同事存取而改成 0.0.0.0， 等於把「清空資料庫」這個端點公開給整個網段。要多人使用，請在前面架一層反向代理 並自行加上認證。

2. 回應約定

2.1 成功：直接回傳資料

2xx 的回應直接就是資料本身，沒有 {"data": ...} 外層包裝。 列表端點回傳陣列，單一物件端點回傳物件。 

GET /api/analysis/keff?element=Cu
→ 200
[
  {"batch_id": "IN-2501", "element": "Cu", "k_eff": 0.083, ...},
  {"batch_id": "IN-2502", "element": "Cu", "k_eff": 0.112, ...}
]

2.2 失敗：統一的錯誤外層

所有 4xx / 5xx——包含未預期的例外——都會被例外處理器轉成同一個形狀。 不會有裸的 traceback 流到前端。 

→ 404
{
  "ok": false,
  "data": null,
  "error": {
    "code": "HTTP_404",
    "message": "找不到批次 IN-9999",
    "detail": ""
  }
}

所以客戶端的判斷邏輯只有一條：HTTP 狀態碼 >= 400 就讀 error， 否則直接用 body。不需要每次都檢查 ok 欄位。

2.3 NaN / ±Inf 會被轉成 null

所有回應都經過一層清理，把 NaN、+Inf、-Inf 換成 JSON 的 null，遞迴處理巢狀的 dict 與 list。

為什麼需要這一層 NaN 在數值計算中是合法的「算不出來」訊號——批次數不足時的 R²、 bootstrap 失敗時的信賴區間、只有一個樣本時的標準差，都會是 NaN。 但 NaN 不是合法的 JSON。若不處理，序列化會直接丟 ValueError 變成 500，使用者只會看到「伺服器錯誤」，完全不知道真正的意思是「這個數字算不出來」。 轉成 null 之後，前端顯示為「—」，語意正確。

兩個推論，客戶端要記得：

  • 數值欄位隨時可能是 null，不要假設它一定是數字。 典型例子：k_lo / k_hi（bootstrap 失敗）、 yield_stats.std（只有一批）、model_r2（GP 擬合失敗）。
  • null 的語意是「這個值無法計算」，不是「值為零」。 在 UI 上請顯示為「—」或「不適用」，不要顯示 0。

2.4 回應標頭

所有 /api/ 回應都帶 X-Response-Time-Ms，記錄伺服器端處理耗時。 超過 3000 ms 的請求會另外寫進日誌（慢請求 ...），方便事後追查效能問題。

3. 錯誤碼表

HTTPerror.code意義典型觸發情境
400HTTP_400請求語意錯誤 資料庫沒有批次資料就呼叫 /optimize/suggest； speed_min ≥ speed_max；尚未建立參數映射就呼叫 /simulate； 上傳的檔案無法解析成表格
404HTTP_404找不到資源 查詢或刪除不存在的 batch_id
413HTTP_413上傳檔案過大 匯入的檔案超過 20 MB
422VALIDATION_ERROR參數驗證失敗 Pydantic 的型別或範圍檢查沒過，例如 n_passes = 0（下限為 1）、 speed_mm_hr = -1（必須 > 0）
500INTERNAL_ERROR未預期的例外 完整 traceback 寫進日誌，回應的 detail 只有例外類型與訊息，不含堆疊

422 的 message 會標出出錯的參數路徑，方便直接定位：

{
  "ok": false, "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "參數驗證失敗：body → n_passes Input should be greater than or equal to 1",
    "detail": "[{'type': 'greater_than_equal', 'loc': ('body', 'n_passes'), ...}]"
  }
}

4. 批次資料端點

前綴 /api/batches。這組端點是唯一會寫入的一組，因此也是唯一會讓分析快取失效的一組。

4.1 GET /api/batches

列出所有批次，附帶依模型算出的 6N 得料率。

參數：無。

回應：批次物件的陣列，依 run_date 再依 batch_id 排序。 每個物件是批次的全部欄位，外加兩個衍生欄位：

欄位型別說明
zone_len_fracfloatzone_len_mm / ingot_len_mm，物理模型真正使用的無因次量
yield_fracfloat | null該批的 6N 得料率（0~1）。該批沒有可用擬合結果時為 null
 
curl http://127.0.0.1:8848/api/batches
[
  {
    "batch_id": "IN-2501", "run_date": "2025-01-14",
    "ingot_len_mm": 500.0, "zone_len_mm": 50.0, "zone_len_frac": 0.1,
    "speed_mm_hr": 2.0, "temp_c": 175.0, "n_passes": 8,
    "atmosphere": "Ar", "head_crop_frac": 0.03,
    "analysis_method": "GDMS", "operator": "", "notes": "",
    "feed_purity_note": "",
    "yield_frac": 0.612
  }
]
效能注意 yield_frac 是每批各自算的：先取該批完整資料、再依擬合的 k_eff 重建濃度分布、再算純度視窗。批次數多時這是一個 N+1 的查詢模式。 而且第一次呼叫會觸發完整分析（見第 8 節）。50 批以內感覺不出來， 數百批時這個端點會變成整個 UI 最慢的地方。

4.2 GET /api/batches/template.csv

下載匯入用的 CSV 範本，含兩列示範資料。回應是 text/csv; charset=utf-8，並帶 Content-Disposition: attachment。 內容開頭加了 BOM，讓 Excel 直接雙擊開啟時不會把中文變成亂碼。 

curl -O -J http://127.0.0.1:8848/api/batches/template.csv

4.3 GET /api/batches/{batch_id}

單一批次的完整分析資料包——這是「批次詳情」畫面的唯一資料來源。

路徑參數：batch_id（字串）。找不到回 404。

回應重點欄位：

欄位型別說明
batchobject批次條件（含 zone_len_frac）
element_specsarray各元素的 c0_ppm、spec_ppm、 c0_measured。c0_measured = false 代表 C0 是推估值，UI 必須標示
elementsarray該批有量測資料的元素
x_normarray[240]模型曲線的 x/L 格點，所有元素共用
curves.{元素}object疊圖所需的全部資料，見下表
total_ppmarray[240]各元素模型曲線的逐點總和
windowobject純度視窗計算結果，見下表
anomaliesarray該批的異常偵測結果

curves.{元素} 的內容

欄位說明
x_model / y_model模型預測曲線（240 點）
x_obs / y_obs實測點
y_pred_at_obs模型在實測點位置的預測值，畫殘差線用
censored布林陣列，標記哪些實測點是設限值——畫圖時要用向下箭頭而不是圓點， 因為那些點的真值在標記位置以下
residuals標準化的對數殘差
fit完整的 KeffFit：k_eff、k_lo／k_hi（bootstrap 95% 區間）、 k_se、c0_ppm、c0_fitted、sigma_log、rmse_log、 n_points、n_censored、converged、interpretation（白話判讀）、note

window 的內容

欄位說明
yield_frac得料率：從頭端切除點算起連續合格的長度佔全錠比例
head_cut_frac / tail_cut_frac合格區的起點與終點（x/L）
threshold_ppm本次判定使用的總雜質門檻
max_total_in_window_ppm合格區內的最高總雜質——用來看餘裕有多少。 若非常接近門檻，代表這個得料率很脆弱，量測誤差就足以讓它掉下來
limiting_element決定切點的元素（誰先超標）。製程改善應該針對這個元素
concentrate_start_frac雜質濃縮區起點（總雜質 > 5 倍門檻處）
per_element_at_cut切點處各元素的濃度

4.4 DELETE /api/batches/{batch_id}

刪除單一批次。外鍵的 ON DELETE CASCADE 會連同該批的量測值與元素規格一起刪掉。 找不到回 404。成功後分析快取失效。 

curl -X DELETE http://127.0.0.1:8848/api/batches/IN-2501
→ {"deleted": "IN-2501"}

4.5 POST /api/batches/import

匯入 CSV 或 Excel。這是把資料送進系統的主要入口。

參數位置型別預設說明
filemultipart form檔案— 必填。副檔名 .xlsx / .xls 走 Excel 讀取器，其餘當 CSV （先試 UTF-8，失敗自動退回 Big5）。上限 20 MB
dry_runqueryboolfalse true 時做完整稽核但不寫入資料庫，也不讓快取失效

回應（ImportReport）：

欄位說明
okfalse 代表有 error，整份檔案都沒有寫入（全有全無）
batches / measurements / censored解析出的批次數、量測點數、設限點數
elements / batch_ids解析出的元素與批號清單
errors會擋下匯入的問題，每則都帶試算表列號
warnings不擋匯入但需要注意的問題
 
# 先稽核（強烈建議每次拿到新檔案都先跑這個）
curl -F "file=@客戶資料.csv" \
     "http://127.0.0.1:8848/api/batches/import?dry_run=true"
{
  "ok": false,
  "batches": 3, "measurements": 96, "censored": 14,
  "elements": ["Cu", "Fe", "Ni", "Sn"],
  "batch_ids": ["IN-2501", "IN-2502", "IN-2503"],
  "errors": [
    "第 47 列：歸一化位置 2.0000 超出 [0,1]。常見原因是 x_mm 與錠長單位不一致。"
  ],
  "warnings": [
    "批次 IN-2503 的 Sn 只有 2 個取樣點，擬合 k_eff 至少需要 3 點、建議 6 點以上。"
  ]
}

完整的欄位定義與驗證規則見 03 · 資料規格書。

大小限制是在讀完檔案之後才檢查的 目前的實作先把整個上傳讀進記憶體，再比對 20 MB 上限。所以送一個超大檔案仍然會 消耗等量的記憶體才被拒絕。本機單人使用沒有問題，但如果哪天要對外開放， 這裡需要改成串流式檢查。

4.6 POST /api/batches/seed-demo

產生合成資料集，供展示與方法驗證使用。合成資料有已知真值，所以可以用來回答 「模型到底準不準」這種在真實資料上無法直接驗證的問題。

參數（body）型別範圍預設說明
n_batchesint4 ~ 20020要產生幾批
seedint—20250114亂數種子，固定值可重現同一份資料
rel_noisefloat0 ~ 10.12乘法性量測誤差的對數標準差 （0.12 約等於 ±12% 的相對誤差，接近 GDMS 的實際水準）
n_sample_pointsint3 ~ 408每支錠的取樣點數
inject_anomaliesbool—true是否植入已知的異常批次， 用來測試異常偵測層抓不抓得到
clear_existingbool—true 預設會清空現有資料庫。對著客戶的真實資料誤按這個會很尷尬
 
curl -X POST http://127.0.0.1:8848/api/batches/seed-demo \
     -H "Content-Type: application/json" \
     -d '{"n_batches": 24, "inject_anomalies": true}'
{
  "n_batches": 24,
  "injected_anomalies": [
    {"batch_id": "SYN-07", "kind": "reversed_positions", "element": "Cu"}
  ],
  "element_truth": {"Cu": {"k0": 0.06, "beta_v": 0.21, ...}},
  "disclaimer": "本資料集為合成資料，用於方法驗證與 demo，非實際製程量測結果。"
}
disclaimer 必須顯示出來 所有畫面在使用合成資料時都要標示。給客戶看 demo 時，把合成資料誤認成他自己的資料 是最容易造成誤解、也最傷信任的事。

4.7 DELETE /api/batches

清空整個資料庫（四張表全清）。沒有二次確認、沒有軟刪除。 UI 上這個動作應該要有明確的確認對話框。 

curl -X DELETE http://127.0.0.1:8848/api/batches
→ {"cleared": true}

5. 分析端點

前綴 /api/analysis。全部是唯讀的 GET，但會觸發重運算—— 真正的成本在這一組。

5.1 GET /api/analysis/overview

儀表板首頁的資料來源，一次給出整個資料集的全貌。

參數：無。

欄位說明
emptytrue 代表資料庫是空的，其餘欄位不存在。客戶端要先檢查這個旗標
n_batches / n_measurements / n_censored資料量統計
elements所有有擬合結果的元素
keff_summary.{元素}median / min / max / n； bps（BPS 線性化模型的係數）；gp_used（該元素是否成功用了高斯過程， false 代表退回線性模型）；removable（白話分級： 易去除 / 中等 / 困難 / 偏析法無效）
yield_stats得料率的 mean / median / min / max / std。只有一批時 std 為 null
anomaly_counts{high, medium, low} 三級的異常計數
speed_range / temp_range / pass_range [min, max]。這定義了模型的可信賴區間；超出這個範圍的模擬是外插
threshold_ppm目前使用的 6N 判定門檻
warnings分析過程的警告，例如「已排除 N 組高嚴重度異常後重新擬合映射」
analysis_duration_s本次完整分析耗時（秒）——可以拿來判斷快取有沒有生效
 
curl http://127.0.0.1:8848/api/analysis/overview
{
  "empty": false, "n_batches": 24, "n_measurements": 768, "n_censored": 121,
  "elements": ["Cu", "Fe", "Ni", "Sn"],
  "keff_summary": {
    "Cu": {"median": 0.091, "min": 0.052, "max": 0.183, "n": 24,
           "gp_used": true, "removable": "易去除"}
  },
  "yield_stats": {"mean": 0.583, "median": 0.601, "std": 0.087},
  "anomaly_counts": {"high": 1, "medium": 3, "low": 5},
  "speed_range": [1.02, 5.94], "temp_range": [165.3, 204.1],
  "threshold_ppm": 1.0,
  "warnings": ["參數映射已排除 1 組高嚴重度異常資料後重新擬合（SYN-07/Cu）。..."],
  "analysis_duration_s": 3.412
}
第一次呼叫需要數秒 這個端點會觸發完整分析：擬合所有 (批次 × 元素) 的 k_eff、每組跑 300 次 bootstrap、擬合 GP 參數映射、跑異常偵測、（若偵測到高嚴重度異常）排除後再擬一次映射、 訓練殘差修正器。24 批 4 元素大約 3~5 秒。之後只要沒有寫入，都是快取命中（毫秒級）。

5.2 GET /api/analysis/keff

所有 (批次 × 元素) 的 k_eff 擬合結果表——這是整個系統的核心產物。

參數位置型別預設說明
elementquerystring無只回傳該元素的列。大小寫敏感

回應：陣列，依 (element, speed_mm_hr) 排序。每列的關鍵欄位：

欄位說明
k_eff有效分配係數。越低代表偏析純化效果越好
k_lo / k_hi / k_sebootstrap 95% 信賴區間與標準誤。 bootstrap 失敗時為 null。區間寬度是判斷這個數字能不能信的主要依據
speed_mm_hr / temp_c / n_passes該批的製程條件
c0_ppm擬合使用的進料濃度
sigma_log對數殘差標準差。可以直接跟實驗室的複驗差異比對： 遠大於分析誤差代表模型缺了東西，遠小於則可能過擬合
rmse_log對數空間的均方根誤差
n_points / n_censored該擬合用了幾點、其中幾點是設限值
interpretation白話判讀，例如「偏析效果好，此元素容易以區域熔煉去除」
note擬合過程的備註（收斂問題、C0 被一併擬合等）
 
curl "http://127.0.0.1:8848/api/analysis/keff?element=Cu"

5.3 GET /api/analysis/mapping

(v, T) → k_eff 參數映射的視圖資料：實測散點加上 GP 預測曲線與信賴帶。 這是回答「速率對純化效率的影響有多大」的那張圖。

參數：無。

回應：{elements, models, warnings}。每個 models.{元素} 包含：

欄位說明
v_curve速率格點（60 點，比觀測範圍向兩側外推一些）
temp_used畫這條曲線時固定使用的溫度（所有批次溫度的中位數）
k_curve / k_lo / k_hi預測的 k_eff 與信賴帶
z_curve / z_stdBPS 線性化空間的預測與標準差。 在這個空間裡關係是直線，比較容易看出資料到底支不支持模型
bpsBPS 模型的係數與線性度註記
gp_usedfalse 代表 GP 擬合失敗、已退回 BPS 線性模型
kernelGP 核函數的字串表示（除錯用）
points各批次的實測散點，含 z（線性化後的值）與信賴區間
v_range_observed[min, max] 實際觀測到的速率範圍。 畫圖時應把這個範圍以外的曲線畫成虛線，明確區分內插與外插

5.4 GET /api/analysis/anomalies

資料稽核結果：哪些 (批次 × 元素) 看起來有問題。

參數位置型別說明
severityqueryhigh | medium | low 只回傳該嚴重度。其他值會被 422 擋下（有正規表示式驗證）
回應欄位說明
batch_id / element出問題的組合
severity嚴重度三級
reasons人看得懂的理由清單，例如「殘差呈結構性形狀（前半全正、後半全負）」
metrics支持這個判斷的數值指標
suggested_action建議的處理方式
exclude_recommendedtrue 且 severity = high 時， 這組資料會被自動排除在參數映射之外（但仍保留在資料庫中）
異常偵測不參與預測，只保護準確度 系統的做法是兩階段：先用全部資料擬一個映射，此時異常批次會把回歸線整條拉歪； 接著把「高嚴重度且建議排除」的資料拿掉後重擬，再重新偵測一次。 如果排除後某個元素剩不到 4 筆，就寧可留著髒資料並在 warnings 標示—— 資料太少比資料有點髒更危險。原始資料永遠不會被刪除。 
curl "http://127.0.0.1:8848/api/analysis/anomalies?severity=high"

5.5 GET /api/analysis/validation

留一批交叉驗證（Leave-One-Batch-Out, LOBO）：每次拿掉一整批，用剩下的批次重建 整條分析管線，再去預測被拿掉的那批。這是回答「模型到底多準」與 「AI 有沒有真的幫上忙」的端點。

參數位置型別預設說明
use_aiquerybooltrue 是否同時評估「物理 + L1 殘差修正」這條路徑
回應欄位說明
n_batches / n_points參與驗證的批次數與預測點數
physics_mae_ppm / physics_max_ppm / physics_mae_log 純物理模型的誤差
ai_mae_ppm / ai_max_ppm / ai_mae_log 物理 + AI 的誤差。批次數不足時為 null（原始值是 NaN）
ai_better / improvement_pctAI 有沒有比較好、好多少
gate_passed關鍵欄位：L1 殘差修正是否通過護欄。 只有通過才會在模擬中被啟用；沒通過就永遠只用純物理
per_batch / per_element逐批、逐元素的誤差明細
verdict / notes白話結論與附註
這是最慢的端點 它要跑 N 次完整的「重建映射 + 重訓修正器 + 預測」循環。24 批大約十幾秒， 批次數再多會更久。結果有獨立快取（同樣以資料版本為鍵），所以第二次呼叫是即時的。 在 UI 上呼叫這個端點時務必顯示進度指示，不要讓使用者以為當掉了。

5.6 GET /api/analysis/censoring-study

設限處理方式的對照實驗：同一份資料、同一個模型，只改變 LOD 的處理方式， 看 k_eff 會偏移多少。三種方式是 Tobit（正確做法）、當成 0、當成 LOD。

參數：無。資料庫為空時回 400。

回應：三種方法各自的 k_eff 統計。用合成資料跑時還能算出對真值的相對偏差。

這是說服客戶最有力的一張圖 「我們用了 Tobit likelihood 處理左設限資料」對客戶是空話； 「同一批資料，把測不到當成 0 會讓 k_eff 低估 30%，當成 LOD 會高估 25%， 換算成得料率的差異是 8 個百分點」——這才是他聽得懂而且在意的。

5.7 GET /api/analysis/pass-advice

純化次數的飽和分析：做到第幾次之後就白做了。這是 P1 階段就能交出去、 能立刻省錢的結論——如果客戶現在跑 15 次而模型指出第 9 次之後純度不再進步， 那就是直接砍掉 6 趟的設備時間。

參數位置型別範圍預設說明
n_passes_maxqueryint5 ~ 6025 最多模擬到第幾次

模擬條件取自現有批次的中位數（速率、溫度、熔區長度比），沒有擬合結果時回 400。

回應欄位說明
recommended_passes報告裡該寫的那個數字：達到可達最大得料率 95% 所需的最少次數
saturation_pass最後一次仍能讓得料率增加 0.5 個百分點的 pass。 這之後每一趟都幾乎白跑
ultimate_pass分布形狀數學上收斂到極限分布的次數。通常比前兩者晚
yield_by_pass每一次 pass 後的得料率，畫飽和曲線用
marginal_gain_by_pass每次的增量
head_total_by_pass每次 pass 後頭端的總雜質
passes_saved_vs_max相對於模擬上限可以省下的趟數
conditions本次模擬使用的條件與各元素 k_eff，讓結論可追溯
note一句話總結，可直接貼進報告

6. 模擬與最佳化端點

前綴 /api。這組全部是 POST，參數走 JSON body。

6.1 POST /api/simulate

正向模擬：給一組製程條件，預測濃度分布與得料率。

參數型別範圍預設說明
speed_mm_hrfloat> 0, ≤ 200—必填。熔區移動速率
temp_cfloat0 ~ 1000—必填。熔區溫度。 注意下限是 0，所以物理上不可能的低溫不會被擋下
n_passesint1 ~ 60—必填。純化次數
zone_len_fracfloat | null0 < x < 1各批中位數 熔區長度比 l/L
head_crop_fracfloat0 ≤ x < 0.50.03頭端固定切除比例
threshold_ppmfloat | null> 0系統設定值（1.0） 6N 判定門檻（總雜質）
c0_ppmobject | null—各元素中位數 {"Cu": 8.5, "Fe": 4.2}。用來試算「如果進料更乾淨會怎樣」
use_aibool—false是否套用 L1 殘差修正

回應：{physics, ai, dual_track}。

永遠雙軌顯示 physics 是純物理模型的結果，永遠存在。ai 只在 use_ai = true 且修正器可用時才有值。這個設計是刻意的：使用者必須隨時能看到 「不用 AI 的答案是什麼」，才有辦法判斷 AI 到底調整了什麼、調整得合不合理。 dual_track 則直接給出兩者的比較與是否採納的建議。

physics 與 ai 的結構相同：

欄位說明
x_norm / profiles.{元素} / total_ppm預測的濃度分布
k_eff / k_ci該條件下各元素的預測 k_eff 與信賴區間
yield_nominal得料率的中央估計
yield_optimistic / yield_pessimistic 用 k_eff 信賴區間兩端算出的得料率。報告請寫這個區間，不要只寫單一數字
window純度視窗細節（同 4.3 節）
in_training_range關鍵旗標：條件是否落在歷史批次涵蓋範圍內
warnings外插警告等
外插時 AI 會被自動停用 當 in_training_range = false，殘差修正器不會被套用，且會加上警告： 「查詢條件落在歷史批次涵蓋範圍之外。此處為外插，模型不確定度大幅上升； 已自動停用 AI 修正、僅顯示物理模型結果。建議先安排一批實驗驗證。」 理由很簡單：物理模型外插有依據（方程還是那個方程），殘差修正器外插沒有依據 （它學的是訓練範圍內的偏差模式）。

6.3 POST /api/optimize/suggest

貝氏最佳化：建議接下來該跑哪幾批實驗。這與 6.2 節的網格掃描不同—— 網格掃描是「在目前模型下最好的條件」，這裡是「跑哪一批最能改善模型或找到更好的點」。

參數型別範圍預設說明
n_suggestint1 ~ 103要建議幾批
speed_min / speed_maxfloat | null> 0 觀測最小值 × 0.6（至少 0.3）／最大值 × 1.3搜尋範圍
temp_min / temp_maxfloat | null— 觀測範圍 ± 5 °C搜尋範圍
pass_choicesarray[int] | null— 資料中出現過的值可選的純化次數

資料庫沒有批次資料時回 400。

回應欄位說明
suggestions每筆含 rank、speed_mm_hr、temp_c、 n_passes、predicted_yield、predicted_std、 expected_improvement、rationale
n_observations用了幾筆有效觀測
best_observed_yield目前歷史最佳得料率
model_r2GP 對真實觀測的擬合度。失敗時為 null
notes附註
少於 4 批就不給建議 回應會是空的 suggestions 加一則說明：「目前只有 N 批可用資料， 少於 4 批時貝氏最佳化沒有意義。建議先用涵蓋速率範圍的篩選性實驗（screening DOE） 跑 5~6 批，再切換到序列最佳化。」這是刻意的拒絕，不是錯誤—— 在 3 個點上做貝氏最佳化只是在放大雜訊。

每筆建議的 rationale 會明說這一批的價值在哪：不確定度高於中位數的點 「主要價值在縮小模型的未知區，即使結果不如預期也很有資訊量」； 不確定度低的點則「主要價值在確認最佳點」。多筆建議之間用 kriging believer 策略避免三個建議擠在同一個位置。

  ],

6.4 POST /api/optimize/doe-comparison

在「虛擬產線」上實際跑一遍全因子 DOE 與貝氏最佳化，比較兩者各需要幾批才能找到 同樣好的條件——把「省多少批」實際算出來，而不是嘴上說。

參數型別範圍預設說明
factorial_speedsint2 ~ 84全因子設計的速率水準數
factorial_tempsint2 ~ 83溫度水準數
pass_choicesarray[int] | null—資料中的前 3 種pass 水準
bo_budgetint4 ~ 6012貝氏最佳化的批次預算
seed_nint2 ~ 205貝氏最佳化的起始隨機批次數
cost_per_batchfloat≥ 0100000單批成本，用來換算省下的金額

batches_saved / cost_saved省下的批次數與金額
notes附註與前提說明
這是模擬，不是實測 「虛擬產線」是用目前的模型當成真值來回答查詢。所以這個對比展示的是 在模型描述的世界裡貝氏最佳化能省多少批。它是一個有說服力的示意， 但不能當成對真實產線的保證。跟客戶說明時要講清楚這個前提。 內部錯誤會被包成 500 HTTP_500（訊息為「DOE 對比失敗」）。

7. AI 助理端點

前綴 /api/assistant。

LLM 不參與任何計算 這是整個架構最重要的一條界線。助理層（L5）能做的只有：呼叫既有的分析工具、 拿到工具算出來的數字、把它組織成人話。它不會自己算 k_eff、 不會自己估得料率、不會發明任何數字。所以「換一個模型」不會改變任何分析結論。

7.1 GET /api/assistant/status

anthropic_key_present / openai_key_present金鑰有沒有設定（布林，不回傳金鑰本身）
model使用的模型名稱；模板模式時為 null
degradedtrue 代表正在用本地模板模式
note白話說明目前狀態與如何切換
沒有金鑰也能完整運作 未設定 API 金鑰時自動退回本地模板模式：介面照常運作、數字完全正確， 只是措辭比較制式。這代表可以在完全離線、無外網的客戶端上部署整套系統。 在 .env 填入 EXPA_ANTHROPIC_API_KEY 或 EXPA_OPENAI_API_KEY 即可切換。

9. 效能與快取

9.1 為什麼需要服務層快取

一次完整分析的組成成本大致是：擬合 80 組 k_eff 約 2~3 秒（含每組 300 次 bootstrap）、GP 參數映射約 1 秒、LOBO 交叉驗證十幾秒。 如果每個 HTTP 請求都重算，UI 會卡到不能用。

9.2 快取怎麼運作

以「資料版本」為鍵 服務層維護一個內部版本號。任何寫入操作都會讓版本前進，所有快取立刻失效。 所以不會出現「改了資料但畫面還是舊數字」這種問題，也不需要手動清快取。

會讓快取失效的操作：

  • POST /api/batches/import（dry_run=false 且匯入成功時）
  • POST /api/batches/seed-demo
  • DELETE /api/batches/{batch_id}
  • DELETE /api/batches

快取分兩層：主分析結果（k_eff 擬合、映射、異常、殘差修正器）一份， LOBO 驗證結果另一份。兩者都以同一個版本號為鍵。 重算在鎖內進行，所以兩個並行請求不會同時觸發同一份昂貴計算—— 第二個會等第一個算完直接拿結果。

一致性保證 所有端點共用同一份分析結果。這代表使用者在不同頁面之間切換，不會看到兩組不同的數字—— 儀表板上的 k_eff 中位數與 k_eff 表格裡算出來的一定一致。 這聽起來理所當然，但如果每個端點各自重算，浮點運算與隨機種子的差異會讓數字對不起來， 而客戶一定會發現。

9.4 前端的建議做法

  1. 啟動時先打 /api/config 與 /api/health。兩者都很快， 可以立刻決定要不要顯示「資料庫是空的」引導畫面。
  2. 把第一次的重運算擺在一個明確的位置。例如進入儀表板時就呼叫 /api/analysis/overview 並顯示載入狀態，之後所有頁面都是快取命中。 不要讓使用者在一個看起來很輕的操作上等 5 秒。
  3. 寫入之後主動重取。匯入成功後快取已經失效，下一次查詢會重算—— 請顯示載入狀態，不要讓畫面靜止不動。
  4. /api/analysis/validation 與 /doe-comparison 一定要有進度指示， 而且不要在頁面載入時自動觸發，改成使用者主動點擊。
  5. 看 X-Response-Time-Ms。開發時把它印在 console，很容易發現 哪個操作意外觸發了重運算。

10. 已知限制與注意事項

項目說明
無認證設計前提是單機 127.0.0.1。改綁 0.0.0.0 等於公開所有寫入端點
無速率限制連續呼叫重運算端點會把 CPU 吃滿
上傳先讀後檢20 MB 上限是在整個檔案讀進記憶體之後才檢查的
temp_c 下限為 0/api/simulate 接受 0 °C，但銦熔點是 156.6 °C。 參數合法不代表結果有物理意義
pass-advice 的頭端切除寫死 0.03沒有沿用各批的實際 head_crop_frac
keff_cache 資料表未被使用資料庫有這張表、資料存取層也有讀寫方法， 但服務層走的是記憶體快取。重啟服務後第一次分析必然要重算
序列化的兜底JSON 序列化時遇到未知型別會直接轉成字串（default=str）， 不會報錯。所以如果看到某個欄位莫名其妙變成字串，是這裡吃掉的
健康檢查的例外捕捉不完整資料庫檢查只捕捉 RuntimeError 與 OSError，但 sqlite3 的例外兩者皆非。資料庫檔案損毀時， /api/health 會回 500 而不是預期的「ok: false 加上錯誤說明」
本系統為離線決策輔助工具，所有端點都只讀寫本機資料與計算模型， 不參與任何設備控制。任何參數建議都必須經過製程工程師確認後才進產線。
