03 · 資料規格書

這份文件定義 ExpAnalysis 吃什麼資料、怎麼檢查、存在哪裡，以及——最重要的—— 開案前一定要跟客戶問清楚哪些事。本專案的成敗有八成落在這份規格上， 不在模型上。請把這頁當成與客戶開第一次資料會議時的檢查清單。

1. 為什麼資料規格比模型重要

在偏析純化這種「物理有解析解、批次數只有幾十批」的題目上，模型其實不是瓶頸。 區域熔煉（zone refining）的濃度分布有 Pfann 方程可算，整條曲線只用一個參數 k_eff 就能描述。把 k_eff 擬出來是毫秒級的事，程式碼不到兩百行。

真正會讓專案翻車的是資料本身。P1 階段最常見的失敗模式不是「模型不準」，而是 「資料根本對不齊」：

  • 取樣位置用 mm 記錄，但每批錠長不一樣，於是「距頭端 50 mm」在不同批次代表完全不同的物理位置。
  • 頭尾切除量沒記錄，客戶送驗的「頭端第一點」其實已經是切掉 30 mm 之後的位置。
  • 進料濃度 C0 沒量，於是曲線沒有基準線，k_eff 與 C0 一起浮動、彼此補償。
  • 低於檢測極限的測值被人工填成 0 或空白，頭端看起來完美無瑕。
這些錯誤最可怕的地方是「不會報錯」 資料照樣能算，圖照樣能畫，k_eff 照樣會出現一個好看的數字。錯誤會一路無聲地 傳到最佳化建議，最後變成一句「建議把速率降到 1.2 mm/hr」交給產線——而那個建議是錯的。 所以匯入層必須寧可擋下來，也不要猜。

本系統的匯入策略是 「寬鬆輸入、嚴格檢核」：欄位名稱可以是中文、英文、大小寫混雜、 帶底線或空格，系統會盡量認出來；但單位與物理一致性一律嚴格檢查，不合格就明確擋下， 並告訴你哪一列、為什麼。

2. 資料的形狀：長格式表格

系統接受 長格式（long format） 表格，一列代表一個取樣點的一個元素。 如果一支錠上取 8 個位置、每個位置驗 4 種元素，那就是 32 列。

為什麼不用寬格式？ 實驗室報告常見的寬格式是「一列一個取樣點，Cu / Fe / Ni / Sn 各佔一欄」。這種格式 在元素數量改變時整張表的結構就得跟著改，而且沒有地方擺「這個元素的 LOD 是多少」。 長格式讓每一筆量測都自帶完整脈絡（哪批、哪個元素、什麼位置、LOD 多少），程式與人 都好處理。從寬格式轉長格式在 Excel 是一次樞紐分析的事，值得做。

一列中同時包含兩種層級的資訊：

  • 批次層級（ingot_len_mm、zone_len_mm、speed_mm_hr、temp_c、 n_passes、atmosphere、head_crop_frac…）：同一個 batch_id 的每一列都必須填一樣的值。系統會檢查，不一致就擋下。
  • 取樣層級（x_norm 或 x_mm、element、value_ppm、 lod_ppm、censored、c0_ppm）：每列各自不同。

批次層級欄位重複填寫看起來很冗贅，但這是刻意的：它讓一個 CSV 檔就是一份自足的資料集， 不需要另外維護一張「批次條件表」再靠 join 對起來——而 join 對不起來正是資料出錯的 主要來源之一。

3. 完整欄位表

run_date字串ISO 8601選填"" 實驗日期，只取前 10 個字元（YYYY-MM-DD）。用於排序與趨勢檢視，不參與計算。 常見錯誤：Excel 把日期存成序號 45678；匯出 CSV 前請先設成文字格式。

speed_mm_hr浮點mm/hr必填— 熔區移動速率 v，必須為正。常見錯誤：填 mm/min 或 mm/s。差 60 倍或 3600 倍 不會被自動抓出來（數值仍然是正的），只會讓 (v, T) → k_eff 的映射整個偏掉。 請在匯入前確認單位。
temp_c浮點°C選填0.0 熔區溫度 T。注意：系統對此欄不做範圍檢查，沒填就是 0 °C，而 0 °C 會被 當成一個合法的實驗條件送進參數映射。銦熔點 156.6 °C，任何低於它的值都不合物理， 請務必填寫。另見第 12 節關於「量的是加熱器設定值還是熔體溫度」的討論。
n_passes整數次選填1 熔區通過次數（pass）。必須 ≥ 1。常見錯誤：把「跑了 3 天」記成 3； pass 次數是熔區從頭掃到尾的完整趟數。
atmosphere字串—選填Ar 氣氛：Ar / Vacuum / N2 / Air。目前不參與計算， 但會保留下來供異常分析時對照——氧化皮夾帶雜質是 In 純化的已知風險，見第 12 節。
head_crop_frac浮點比例選填0.0 頭端固定切除比例，範圍 [0, 0.5)。例如 500 mm 錠固定切掉頭端 15 mm 就填 0.03。直接影響得料率計算：得料率是「從頭端切除點算起連續合格的長度 佔全錠比例」，沒記錄這個數字，得料率就會系統性高估。
analysis_method字串—選填GDMS 分析方法：GDMS / ICP-MS。不同方法的 LOD 差一個數量級以上， 混用而不標註會讓設限點的處理失去意義。

3.2 取樣層級欄位

欄位型別單位必填說明與常見錯誤
x_norm浮點無因次 擇一 歸一化取樣位置 x/L，0 = 頭端（先凝固、最乾淨）， 1 = 尾端（雜質濃縮區）。必須落在 [0, 1]。 x_norm 與 x_mm 至少要有一個；兩欄都有時 以 x_norm 為準，x_mm 只在 x_norm 空白時才用。

5. 取樣位置一律正規化成 x/L

系統內部只認 x_norm（x/L），x_mm 進來就立刻換算掉。理由有三個：

5.1 物理方程本身就是無因次的

Pfann 的區域熔煉解描述的是「凝固分率」與濃度的關係。方程裡出現的是 x/L 和 l/L，不是 mm。用 mm 表達等於在方程外面掛一個隨批次變動的換算因子，只會製造錯誤。

C(x)/C₀ = 1 − (1 − k) · exp( −k · x / l ) 單趟熔煉的 Pfann 解（x 為距頭端距離、l 為熔區長度）。整條曲線只由一個參數 k 決定； 把 x 與 l 都除以 L 之後，方程完全無因次化。這正是「一條曲線壓成一個可解釋參數」 之所以可行的原因。

5.2 批次之間才可比較

試量產階段錠長常常會變（500 mm 試片、800 mm 正式錠）。用 mm 記錄的話， 「距頭端 100 mm」在 500 mm 錠是 x/L = 0.2、在 800 mm 錠是 0.125，物理意義完全不同。 歸一化之後，所有批次的曲線可以疊在同一張圖上直接比較。

5.3 單位錯誤會自己現形

匯入器檢查 0 ≤ x/L ≤ 1。如果客戶把錠長填成 cm 而取樣位置填成 mm， 算出來的 x/L 會是 10 之類的值，當場被擋下並提示「常見原因是 x_mm 與錠長單位不一致」。 這個檢查抓到的錯誤比它擋掉的合法資料多得多。

頭端的定義 x/L = 0 是先凝固的那一端，也就是最乾淨的那一端；x/L = 1 是 最後凝固的尾端，雜質濃縮在這裡。如果客戶的取樣編號是從尾端開始編的，請在匯入前轉換， 不要靠模型「自己看出來」——雖然異常偵測層確實抓得到（殘差會出現前半全正、後半全負 的結構性形狀），但那是最後一道防線，不是第一道。

6. 左設限資料（LOD）的三種寫法

在 6N 純度（總雜質 < 1 ppm）的世界裡，很多測值會是「< 0.05 ppm」—— 儀器測不到。這不是一個數字，是一個不等式。統計上稱為左設限（left-censored）資料： 真值落在 [0, LOD] 區間內，你只知道它比 LOD 小，不知道小多少。

給軟體工程師的類比 就像 log 裡寫 response_time: TIMEOUT (>30s)。統計平均值時把它當成 30 秒會低估， 當成 0 更荒謬——你只知道「至少 30 秒」。設限資料是同一回事，方向相反。

三種常見的處理方式，只有一種是對的：

處理方式後果評價
當成 0頭端看起來完美無瑕，擬合出來的 k_eff 被低估（純化效果看起來比實際好）錯
當成 LOD頭端看起來偏髒，k_eff 被高估（純化效果看起來比實際差）錯
Tobit likelihood告訴擬合程式「這點的真值落在 [0, LOD] 之間」，讓它自己算機率正確

系統一律採用第三種。/api/analysis/censoring-study 端點會用同一份資料把三種 做法各跑一次，把偏移量實際算給你看——這是說服客戶（以及說服工程師自己） 最有力的證據之一。

6.1 三種輸入寫法

三種寫法在系統內完全等價，會被標記成同一件事（censored = true 並保留 lod_ppm）：

寫法 A：字串帶小於號（最推薦）

batch_id,x_mm,element,value_ppm,lod_ppm
IN-2501,25,Cu,<0.05,0.05

最貼近實驗室報告原貌，也最不容易在傳遞過程中失真。允許小於號後面有空白 （< 0.05 也可以）。

寫法 B：數值 + censored 旗標

batch_id,x_mm,element,value_ppm,lod_ppm,censored
IN-2501,25,Cu,0.05,0.05,1

適合從 LIMS 系統匯出、旗標本來就是獨立欄位的情況。 censored 欄接受 1 / true / yes / y / t / 是。

寫法 C：數值 ≤ LOD（自動判定）

batch_id,x_mm,element,value_ppm,lod_ppm
IN-2501,25,Cu,0.03,0.05

只要有填 lod_ppm 且 lod_ppm > 0，系統就會檢查 value_ppm ≤ lod_ppm，成立就自動標記為設限。

寫法 C 的邊界行為 判定條件是 ≤ 而不是 <，所以一個「剛好等於 LOD」的真實測值 也會被判成設限。實務上這個差別可以忽略（測值恰好等於 LOD 本來就代表在偵測邊緣）， 但如果你的資料裡這種情況很多，請改用寫法 A 或 B 明確標註。

6.2 沒填 LOD 會怎樣

如果某列被標記為設限（不論用哪種寫法）但 lod_ppm 是空的或 0，系統會：

  1. 拿該列的 value_ppm 當作 LOD；若連 value_ppm 也是 0，退而使用 0.001 ppm。
  2. 發出警告：第 N 列：標記為低於檢測極限但未提供 lod_ppm，以測值 X ppm 作為 LOD。建議補上實際 LOD。

這是降級行為，不是正確答案。LOD 決定了設限點在 likelihood 中的權重，猜錯會直接 影響 k_eff。請跟實驗室要每個元素、每種分析方法的實際 LOD，這通常是一張現成的表。

7. C0（進料濃度）：推估方式與它的偏差

C0 是純化前的進料濃度，是整條曲線的基準線。物理模型算的是 C(x)/C0 這個比值，沒有 C0 就沒有比值。

7.1 沒提供時怎麼辦

匯入時若某批某元素沒有 c0_ppm，系統會用一個物理論證來推估： 偏析純化不會消滅雜質，只是把它重新分布——熔區掃過去，雜質被推向尾端， 但總量守恆。所以全錠平均濃度 ≈ C0。

Ĉ₀ = [ ∫ C(x) dx ] / (xmax − xmin) 實作為取樣點之間的梯形積分，再除以取樣點涵蓋的長度。注意分母不是全錠長度 1， 而是實際取樣涵蓋的區間——這正是偏差的來源。

推估出來的 C0 會被標記 c0_measured = false，UI 上會明確顯示為推估值。

7.2 為什麼這個推估一定會低估

兩個原因疊在一起，方向相同：

  • 取樣點不涵蓋尾端尖峰。尾端是雜質濃縮區，濃度可能比頭端高兩三個數量級。 而尾端通常已經切掉不送驗（合成資料的預設是最後 8% 不取樣），所以積分漏掉了 貢獻最大的那一段。
  • 取樣點通常偏向頭端。工程師關心的是「合格區有多長」，自然在頭端多取幾點。 加權平均因此偏向低濃度區。

低估 C0 的後果是：模型會認為「進料本來就沒那麼髒」，於是把觀測到的純化效果 歸因於較差的偏析能力，k_eff 被高估。更麻煩的是，在擬合時 C0 與 k 有部分共線性（兩者都能讓曲線上下平移），擬合器雖然允許 C0 在 [1/3, 3] 倍的範圍內浮動來補償，但這只是把不確定度攤開，不會憑空生出資訊。

C0 必須量，這件事沒有替代方案 一批進料取一個代表性樣品送驗，成本相對於一次純化實驗微不足道，但它決定了整批資料 能不能用。請在開案時就把「每批進料留樣送驗」寫進 SOP。如果客戶說「進料都是同一批 回收料，應該一樣」——請他至少量三次確認批間變異，實務上回收料的變異通常不小 （合成資料模型假設的批間變異係數是 10%）。

8. 完整的驗證規則清單

匯入器把問題分成兩級。這個分級的原則是：會讓結論錯掉的是 error， 會讓結論變弱的是 warning。

8.1 Error — 擋下整份匯入

只要有任何一個 error，整份檔案都不會寫入資料庫。 這是刻意的「全有全無」語意：部分匯入會留下一個半殘的資料集，比完全沒匯入更難除錯。 報告會列出所有 error（不是只有第一個），方便一次修完。
#檢查訊息與理由
E1缺少必要欄位 batch_id、element、value_ppm 三者缺一即中止，連逐列檢查都不做。
E2沒有取樣位置 x_norm 與 x_mm 都沒有 → 中止。沒有位置的濃度值無法擬合曲線。

10. SQLite 資料庫 schema

10.1 為什麼是 SQLite

這是單機離線分析工具，批次數以百計、量測點以萬計。SQLite 綽綽有餘，而且零維運—— 沒有服務要啟動、沒有帳號密碼要管、整個資料庫就是一個檔案，客戶要備份就複製一份。

不要為了「未來可能需要」就在單機情境直接上 PostgreSQL 那會替客戶引入一個他不會維護的元件。而且退路是通的：SQLite 檔案可以被 DuckDB 直接查詢，未來若真要跨機集中，遷移成本很低。

10.2 連線設定

PRAGMA值理由
journal_modeWAL Write-Ahead Logging：讀與寫不互相阻塞。本系統的典型情境是「使用者在 UI 上瀏覽 分析結果（一直在讀）的同時，背景正在匯入新批次（在寫）」。用預設的 rollback journal，寫入會鎖住整個資料庫，UI 會卡住。WAL 直接消除這個問題。
synchronousNORMAL 比 FULL 少一次 fsync，寫入明顯變快。代價是作業系統當機時可能損失 最後幾筆交易——在有 UPS 的辦公環境是合理取捨，何況原始 CSV 都還在。
foreign_keysON SQLite 預設是關閉的，而且必須每個連線都開。沒開的話 ON DELETE CASCADE 不會生效，刪批次會留下孤兒量測值。

連線是執行緒區域（thread-local）的：FastAPI 的同步端點跑在 threadpool， 而 sqlite3 的連線物件不可跨執行緒共用，所以每條執行緒各自持有一條連線。

10.5 schema 版本管理

schema 變更一律走版本化的 migration 腳本，用 SQLite 內建的 PRAGMA user_version 記錄目前版本（現為 1）。啟動時自動套用缺少的 migration。 如果開啟的資料庫版本高於程式支援的版本，會直接拒絕啟動並要求更新程式—— 用舊版程式寫新版資料庫是資料損毀的經典路徑。

已知落差：keff_cache 目前是空的 資料存取層有完整的 get_keff_cache / put_keff_cache 方法，資料表也建好了， 但目前的服務層走的是記憶體快取（以資料版本為鍵），從來沒有寫入這張表。 實務影響是：重啟服務後第一次分析必須重算（數秒），不會從資料庫回填。 這張表目前只有「被清空」的行為（任何寫入都會清掉它）。

11. 匯入流程與 dry-run

匯入有兩條路徑，行為完全一致：

  • UI：在「資料」頁拖曳 CSV / Excel 檔。
  • API：POST /api/batches/import（multipart/form-data）， 詳見 06 · REST API 參考。
# 只稽核不寫入 —— 拿到新客戶資料時的第一件事
curl -F "file=@客戶資料.csv" "http://127.0.0.1:8848/api/batches/import?dry_run=true"

# 確認沒問題之後才真的寫入
curl -F "file=@客戶資料.csv" "http://127.0.0.1:8848/api/batches/import"
養成先跑 dry-run 的習慣 dry_run=true 會做完全部檢查、回傳完整報告，但一個 byte 都不寫入資料庫。 拿到客戶的新檔案時，先 dry-run，把 error 和 warning 整理成一封信寄回去問清楚， 比自己猜著修資料快得多，也專業得多。

其他行為細節：

  • 檔案格式：副檔名 .xlsx / .xls 走 Excel 讀取器，其餘當 CSV。 CSV 先試 UTF-8，失敗自動退回 Big5（台灣客戶的 Excel 匯出很常是 Big5）。
  • 上傳上限：20 MB。以長格式來說這是幾十萬列，遠超實務需求。
  • 重複匯入同一批次：語意是整批取代。同一個 batch_id 再次匯入時， 該批的舊量測值會先全部刪掉再寫新的，不會殘留舊點。這讓「修正資料後重新匯入」 成為安全操作。
  • 快取失效：成功寫入後，服務層的分析快取立刻失效，下一次查詢會重算。

12. 開案前一定要跟客戶問清楚的資料問題

這一節是本文件最重要的部分。以下每一題都直接決定「這個專案能不能做、要怎麼做」。 建議印出來，在第一次資料會議上逐題問完再報價。

Q1. 歷史批次總共有幾批？每批有幾個取樣點？

少於 15 批，就不要接「分析既有資料」的案子 改成「設計實驗」的案子。理由很直接：k_eff 是每批擬出一個，再用這些 k_eff 對 (v, T) 做回歸。10 批就是 10 個回歸樣本點，而且這 10 批的 速率很可能全擠在 2~3 mm/hr 這個窄帶裡（因為那是產線現在的做法）—— 回歸線的斜率會由雜訊決定，外插到 1 mm/hr 的預測毫無意義。

建議的判斷標準：

批次數該做什麼
< 8 批只能做單批診斷（每批的 k_eff 與得料率），不做參數映射，不給最佳化建議。 直接進入 DOE 設計。
8 ~ 15 批可以建映射，但要明確標示外插區。同時規劃 5~6 批篩選性實驗補齊速率範圍。
> 15 批，且速率範圍涵蓋 3 倍以上可以做完整的分析 + 最佳化 + 貝氏建議。

另外要問速率的分布而不只是批數：20 批全部跑 2.0 mm/hr，在回歸上等同於 1 個點。

Q2. 溫度量的是加熱器設定值，還是實際熔體溫度？

這題幾乎每次都會問出問題。加熱器設定 180 °C 不代表熔體是 180 °C——中間隔著 石英管、氬氣層、以及熱電偶的位置。更根本的是：

溫度只是代理變數，真正的物理變數是熔區長度 l 在 Pfann 方程裡，溫度根本不出現。溫度之所以「有效」，是因為它透過熱場決定了 熔區有多長，而 l/L 是方程的參數。溫度還會透過對流強度影響 邊界層厚度（BPS 模型裡的 δ），但那是二階效應。

所以這題要問三層：

  1. 記錄的是設定值還是量測值？如果是量測值，熱電偶裝在哪裡？
  2. 有沒有量過熔區長度 l？怎麼量的？
  3. 不同批次之間 l 有沒有變？（如果溫度有變，l 幾乎一定跟著變）
如果客戶沒量 l，這是整個專案投報率最高的補量測項目 量 l 的方法可以很土：熔區移動時用相機側拍、或在錠上預先做位置標記後觀察熔融區 兩端的界面。做一次就能建立「加熱器設定 → l」的對照表，之後所有歷史批次都能回填。 成本是幾小時的工，換來的是把一個代理變數換成真正的物理變數。 如果只能爭取到一項額外量測，選這個。

Q3. 分析方法是 GDMS 還是 ICP-MS？各元素的 LOD 是多少？

  • 方法要標註在每一批。GDMS 與 ICP-MS 的 LOD 常常差一個數量級以上， 混用而不標註，設限點的處理就失去意義。
  • 要一張「元素 × 方法 → LOD」對照表。這在實驗室是現成的文件，開口就有。 有了它，所有 lod_ppm 欄都能填滿，不必走 6.2 節的降級路徑。
  • 要問前處理。ICP-MS 需要溶解樣品，酸的純度會引入背景；GDMS 是固體直接 分析但對表面狀態敏感（見 Q7）。這會影響你對離群點的解釋。
  • 要問複驗政策。同一個樣品驗兩次的差異有多大？這個數字可以直接拿來檢查 擬合出來的 sigma_log（對數殘差標準差）合不合理——如果模型算出來的 殘差遠大於分析誤差，代表模型缺了東西；遠小於則代表過擬合。

Q4. 各批的取樣位置一致嗎？

問法要具體：

  • 取樣位置是固定的 mm（每批都取 25/100/200/300/420 mm）還是固定的比例 （每批都取 5%/20%/40%/60%/84%）？如果錠長會變，這兩者完全不同。
  • 位置是從哪一端量的？是從原始錠的頭端，還是從切除頭端之後的新端面？ 這個差別會讓整條曲線平移，是 head_crop_frac 存在的理由。
  • 有沒有尾端資料？很多產線把尾端當廢料直接回爐，根本不送驗。但尾端是 雜質濃縮區，缺了它，C0 的質量守恆推估會嚴重低估（見第 7 節）， 曲線右半段也只能靠外插。至少爭取每隔幾批就完整取樣一次。

Q5. 頭尾切除量有沒有記錄？

得料率的定義是「從頭端切除點算起，連續合格的長度佔全錠比例」。沒有切除量的記錄， 這個數字就沒有基準。而且切除量常常是操作員憑經驗決定的（「看起來髒就多切一點」）， 不是固定值——那就更要每批記錄。

這題還有一個延伸：切下來的頭料和尾料去哪了？如果尾料回爐當下一批的進料， 那批次之間就不是獨立的，C0 會有序列相關性。這件事會影響你怎麼看批間變異。

Q6. 每批的 C0 有沒有測？

見第 7 節。這題的標準回答是「進料都是同一批回收料，沒有每批測」。 請爭取：至少留樣，至少測三批確認變異。如果連留樣都沒有，那就要在報告裡 把「C0 為推估值」這件事寫成明確的限制條款，並說明它會讓 k_eff 系統性高估。

Q7. 6N 得料率的判定規則是什麼？

這題經常是「大家以為有共識、其實沒有」的地雷。要釐清：

  • 是總雜質 < 1 ppm，還是個別元素都要達標？系統預設用總雜質門檻 （可透過設定調整），但也支援個別元素規格上限。兩種判定會給出不同的切點。
  • 總雜質怎麼加總？只加追蹤的那 4 個元素？還是實驗室報告上的全部元素總和？ 如果有元素沒在追蹤名單裡但含量不低（例如 Pb、Tl、Cd），得料率會被高估。
  • 設限值怎麼算進總和？「< 0.05」在計算總雜質時要算 0 還是 0.05？ 業界常見做法是算 LOD/2，但這只是慣例不是真理。務必先講定，並寫進報告—— 這個選擇會直接改變得料率的數字。
  • 合格區必須連續嗎？系統的定義是「從頭端算起連續合格」， 因為實務上你要切一段出來賣，不能東切一塊西切一塊。確認客戶的認知一致。

Q8. 氣氛與氧化皮怎麼處理？

銦很容易氧化，而氧化膜會夾帶雜質 這是本製程一個容易被忽略、但可能主導結果的因素。表面氧化膜會在物理上把雜質 「黏」在原位，讓它無法隨熔區被推向尾端——結果就是曲線比純物理預測「髒」， 擬合出來的 k_eff 偏高，而且這個偏差不是隨機的、是系統性的。

要問的具體問題：

  • 氣氛是什麼？Ar / N₂ / 真空 / 大氣？氧含量與露點有沒有監測記錄？
  • 每批的氣氛條件一樣嗎？如果有幾批是在氣氛系統故障期間跑的，那幾批要標記出來。
  • 船皿（boat）材質是什麼？石英、石墨、還是塗層？有沒有與熔體反應的疑慮？
  • 取樣時有沒有把表面氧化皮刮掉？如果沒有，GDMS 的表面敏感性會讓測值偏高。 這個問題在頭端最嚴重（因為頭端本體最乾淨，氧化膜的相對貢獻最大）—— 而頭端正是決定 k_eff 的關鍵區域。
  • 錠的表面有沒有目視紀錄？「這批表面特別霧」這種定性觀察，在解釋離群批次時極有價值。
