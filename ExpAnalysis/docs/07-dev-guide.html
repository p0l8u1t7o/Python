07 · 開發者指南

接手這個專案要知道的一切：模組怎麼切、為什麼這樣切、哪裡不能亂動、 以及每一個看起來奇怪的設計背後「不這樣做會怎樣」。 這份文件假設你會寫 Python 與 JavaScript，但不預設你懂冶金或統計—— 所有領域概念第一次出現時都會用工程師的語言解釋。

先記住這一條，其他都是細節

物理模型是骨架，AI 分層疊在外面，每一層都可以獨立關閉並退回物理基準。
任何一個上層模組（GP 映射、殘差修正、貝氏最佳化、LLM）被砍掉之後， 系統都必須仍然完整可用。如果你寫的程式碼破壞了這個性質，那就是寫錯了。

1. 開始之前

1.1 環境

.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux

pip install -r requirements.txt
pip install -e ".[dev]"         # 需要 pytest 時

沒有任何前端建置流程。web/ 底下是可以直接被瀏覽器載入的原生 ES module， 沒有 node_modules、沒有 bundler、沒有 transpile 步驟。理由見第 5.8 節。

1.2 十分鐘搞懂整個專案

按這個順序讀，會比從 app.py 開始讀快得多：

  1. src/expanalysis/physics/multipass.py 的模組 docstring —— 這是整個系統的核心計算。
  2. src/expanalysis/physics/bps.py 的模組 docstring —— 這解釋了「為什麼小資料也能做事」。
  3. src/expanalysis/fitting/__init__.py —— 三行講完全專案的降維策略。

3. 分層相依規則

上層可以依賴下層，反之絕對不可。這條規則沒有例外。

  L5  assistant/     ← 只呼叫 service，不碰任何計算模組
       │
  L4   ml.bayesopt   ← 呼叫 optimize / physics
  L3   ml.anomaly    ← 讀 fitting 的結果，不寫回去
  L2   ml.gp_map     ← 呼叫 physics.bps
  L1   ml.residual   ← 只知道「物理預測值」與「觀測值」，不知道物理怎麼算的
       │
       optimize/     ← 呼叫 physics
       │
       fitting/      ← 呼叫 physics
       │
  L0   physics/      ← 不依賴任何上層。只依賴 numpy / scipy
       │
       data/         ← 只依賴 logging_setup（physics 與 data 互不相依）
       config.py, logging_setup.py

3.1 為什麼這條規則不能破

因為「可以關掉 AI」這個承諾是靠它撐住的。

如果 physics/ 裡有一行 from ..ml.gp_map import ...， 那客戶要求「先只交付物理模型」時，你就必須動手術而不是刪一行設定。 更糟的是驗收：第 11 節的留一批交叉驗證要能公平地比較「純物理」與「物理 + AI」， 前提就是純物理那條路徑真的不含任何 ML。有一處循環相依，這個保證就破了。

3.2 實務上的三條檢查

  • physics/ 的 import 區塊只能有 numpy、scipy、 以及 physics/ 內部的相對匯入。唯一的例外是 multipass.find_ultimate_pass() 在函式內部延遲匯入 .yield_calc——那是為了避開模組層級的循環匯入，屬同層。
  • service.py 是唯一允許 import 所有層的地方。它就是為了這件事而存在。
  • assistant/tools.py 不准有任何計算邏輯。它只能呼叫 service 的方法， 確保 LLM 路徑與 UI 路徑看到的是同一份數字。有人在那裡寫了個 np.mean(...)，就是這條規則被破的開始。

整條鏈上最重要的一步是「降維」。

一批實驗是 8 個測點 × 4 個元素 = 32 個數字。擬合之後變成 4 個 k_eff。 40 批就變成「每個元素 40 個 k_eff」，一個 40 筆資料、2 個自變數的小問題—— 高斯過程或線性回歸都綽綽有餘。

對照組：直接把 32 個原始數字餵給 XGBoost，有效參數數以百計，在 40 批的資料量下 必然是背答案；而且學到的東西無法外插——問它沒跑過的速率，它只會回傳最接近的訓練值。 1 個有物理意義的參數則綽綽有餘，且外插有依據。

5. 關鍵設計決策

每一項都附「不這樣做會怎樣」。這些不是風格偏好，是踩過的坑。

5.1 為什麼要有 ProfileGrid 查表快取

關鍵觀察：整個區域熔煉的離散模擬對濃度是線性的。

profile(c0, k, …) = c0 × profile(1.0, k, …) 凝固帶走 k·C_L、熔化帶入 C_in，全部是線性運算。 所以只要以 c0 = 1 對一組 k 值先算好曲線，之後任何 c0、任何 k（在對數空間線性內插）都能立刻取得。

快取的鍵是 (zone_len_frac, n_passes, n_cells, k網格規格)， 行程層級、有鎖保護、上限 128 筆（滿了就整個清空——重建只要十幾毫秒， 寫 LRU 反而是過度工程）。

不這樣做會怎樣

每次 likelihood 評估都要重跑一次多次 pass 模擬：8 passes × 240 cells ≈ 1900 次迴圈。 擬合一個 k 要評估上百次，bootstrap 300 次重抽再乘上去——單一批次單一元素就要 0.5 秒以上， 80 個組合就是 40 秒。UI 完全不能互動，「拉滑桿即時看結果」這個功能直接不存在。

有了查表，實測數字是：建表一次 15.6 ms，之後每次取一條完整曲線 20 µs。

再往上還有一層 PositionSlice：擬合迴圈會對同一組取樣位置評估數萬次不同的 k， 而位置內插只跟 x 有關、與 k 無關。先把查表在取樣位置上切好， 單次評估從約 260 µs 降到 24 µs。

5.2 為什麼單格更新用解析積分，不用前向 Euler

連續形式的質量守恆是一條 ODE：

l · dC_L/dx = C_in(x + l) − k · C_L(x)

在單一 cell 內把熔入濃度 C_in 視為常數，這條 ODE 有解析解：

C_L(h) = C_in/k + (C_L(0) − C_in/k) · exp(−k·h/l) 該格凝固出的溶質量 = C_in·h − l·(C_L(h) − C_L(0))，除以 h 得到該格的平均濃度—— 這正好對應實際取樣時切一片下來測到的值，而不是某一點的瞬時值。
不這樣做會怎樣

前向 Euler（C_liq += (C_in − k·C_liq)/m）在 k·h/l 不夠小時會有 系統性偏移，而且偏移量隨格數 N 改變。後果是：你把 n_cells 從 240 調到 300， 擬出來的 k_eff 就變了。這對一個要交付給客戶的分析工具是災難——同一份資料、 不同的內部參數，給出不同的答案，而且沒有人說得清楚哪個才對。

解析積分的版本在均勻輸入時與 Pfann 解析解逐點吻合（誤差只來自 cell 平均 vs 點值）， 所以 n_cells 只影響解析度，不影響答案。

5.3 為什麼終端凝固要用 Scheil 的格內積分平均

主掃描掃到尾端後，剩下一個熔區長度沒有新固體可熔，改為正常凝固（Scheil）。 這裡不能沿用主掃描的更新式，也不能直接對 Scheil 方程取點值，而要用格內積分平均：

C_j = m · C_L0 · [ (1 − j/m)^k − (1 − (j+1)/m)^k ] 對 j 從 0 到 m−1 求和，恰好等於 m · C_L0。
不這樣做會怎樣

質量不守恆。沿用主掃描的更新式，最後一格會殘留 (1−k)·S 的溶質憑空消失； 直接取 Scheil 的點值則因為 (1−g)^(k−1) 在 g → 1 時發散，最後一格會噴出離譜的數值。

質量守恆不是潔癖，它是這個模型唯一的免費驗證條件。 simulate_passes() 每次都會算 mass_error，正常應該在 1e-12 量級。 這個數字一旦跑掉，就代表模擬邏輯被改壞了——它是最靈敏的迴歸偵測器。

5.4 為什麼 GP 的目標變數是 z = ln(1/k − 1) 而不是 k

三個理由，缺一不可：

  1. 值域無限制，適合高斯過程與線性模型；k 本身被關在 (0,1) 裡， GP 的常態假設在邊界附近完全不成立。
  2. 反變換天然保證合法：k = 1/(1+exp(z)) 恆在 (0,1)， 模型不可能吐出不合物理的值——不需要事後夾住，也就不會出現「夾住之後不確定區間變形」的問題。
  3. 對速率 v 是線性的，符合 BPS 理論。所以 GP 只需要學「偏離直線的部分」， 而不是從零學一條曲線。
不這樣做會怎樣

直接對 k 建模，GP 會在 k 接近 0 的地方（易去除的元素，正是我們最在乎的）預測出負值。 你被迫在輸出端 clip 到 0，於是不確定區間變成 [0, 0.08] 這種畸形的東西， 而且 clip 掉的機率質量無處可去，區間的覆蓋率也就不再是 95%。 更根本的是：對 k 建模時 GP 要學一條指數衰減曲線，需要的資料量比學一條直線多得多—— 在 20 批的資料量下，這個差別就是「能用」與「不能用」。

5.5 為什麼 GP 以 BPS 直線當均值函數

sklearn 的 GaussianProcessRegressor 假設先驗均值為 0 （或 normalize_y=True 時為訓練資料的平均值）。 本專案的做法是：先用 fit_bps_linear() 擬出物理直線， GP 只建模 z − z_BPS 這個殘差。

不這樣做會怎樣

離資料遠的地方，GP 會平滑地回歸到先驗均值——也就是 0， 換算回 k 空間就是 k = 0.5。這是一個沒有任何物理意義的常數。 於是模型會告訴你「速率放到 0.1 mm/hr 時，Cu 的 k_eff 大約是 0.5」， 而物理上它應該趨近 k₀ ≈ 0.045。這種預測拿去給製程工程師看，這個工具的信譽就沒了。

用 BPS 直線當均值函數之後，外插時 GP 自然回歸到物理直線， 既有物理依據又保留了不確定度會擴大的正確行為。 這就是 physics-informed（灰箱）做法的具體樣貌，不是一個口號。

配套細節：每點的量測不確定度來自 bootstrap 的 SE，經一階近似 （dz/dk = −1/(k(1−k))）轉到 z 空間後餵給 GP 的 alpha。 擬得準的批次權重高，擬得糊的權重低——這是線性回歸做不到的。 SE 有 0.08 的下限：bootstrap 只涵蓋量測雜訊，涵蓋不到批間的未建模變異 （氧化程度、舟的狀態、進料微量差異）。pass 次數多的批次 SE 可以低到 1e-4， 直接採用會讓 GP 把每一點都當成鐵律去內插，等於過擬合。這個下限是保守的工程判斷， 寫在程式註解裡也寫在這裡。

5.6 為什麼 bootstrap 預設是參數式而不是 case

方式做法涵蓋哪些不確定性
parametric（預設） 從擬合好的模型重新生成資料：y* = C_pred · exp(σ·ε)， 依各點的 LOD 重新判定設限，再重擬合 量測雜訊 ✅　設限造成的資訊損失 ✅
case 直接重抽既有的觀測點（可重複） 量測雜訊 ❌（只是在同一組點裡換權重）　設限損失 ❌
不這樣做會怎樣

本專案的取樣點常常只有 8 個、其中一半以上低於檢測極限。實測下來，case bootstrap 在這種 情況下會給出 SE ≈ 2e-5 的信賴區間——但同一批的 k_eff 對真值其實偏了 40%。 也就是說它會告訴客戶「這個數字準到小數第五位」，而它根本是錯的。 一個過度自信的信賴區間比沒有信賴區間更危險，因為它會被拿去做決策。

case 模式仍然保留：當你懷疑模型設定本身有誤（例如取樣位置可疑）時， case bootstrap 對模型誤設較不敏感，可以拿來交叉檢查。兩者差很多就代表模型設定有問題。

順帶一提：bootstrap 是全向量化的，不是迴圈

天真寫法是「for 每次重抽 → 呼叫最佳化器」。這裡改成：把所有重抽的所有 k 網格點 一次算完（(K, D, n) 三維陣列），在 k 軸取最小值，再用三點拋物線內插 取得次網格精度。同樣的工作量從 0.5 秒降到 38 ms， 而且結果與逐次最佳化在 1e-4 以內一致。有 max_cells 參數做記憶體保護， 超過就自動分塊。

5.7 為什麼服務層要有以資料版本為鍵的快取

AnalysisService 持有一個 _version 整數與一個 AnalysisBundle。任何寫入操作都呼叫 invalidate()， 版本 +1、bundle 清空、LOBO 快取清空。

不這樣做會怎樣

一次完整分析要 5.2 秒（擬合 2.4 s + bootstrap 2.0 s + GP 0.6 s + 異常偵測）。 如果每個 HTTP 請求都重算：切一次頁 5 秒、拉一次滑桿 5 秒——UI 直接報廢。

更隱蔽也更嚴重的問題是數字不一致：總覽頁說 Cu 的 k_eff 是 0.0787， 切到批次頁重算了一次卻顯示 0.0791（Nelder-Mead 的收斂路徑受浮點順序影響）。 客戶看到兩個不同的數字，這個工具就完了。共用同一份 bundle 是「數字一致」的唯一保證。

執行緒安全：FastAPI 的同步端點跑在 threadpool，所以所有重算都在 RLock 內進行， 避免兩個請求同時觸發同一份昂貴計算。SQLite 連線是 threading.local() 的 （sqlite3 的連線物件不可跨執行緒共用）。

5.8 為什麼前端不用任何框架

  • 只有九個畫面，每個畫面就是一個 async function(host) 回傳一個 DOM 節點。 React 的元件模型在這個規模下沒有任何收益。
  • 部署環境離線。引入 bundler 就等於引入 node_modules、 lock 檔、建置步驟、以及「為什麼在客戶那台機器上 build 不起來」的一整類問題。
  • 交付物必須是「複製資料夾就能跑」。原生 ES module 讓 web/ 可以直接被 StaticFiles 掛載，也可以直接被 PyInstaller 打包成資源。
  • 圖表也是自己寫的 SVG（charts.js，六種圖，532 行）。 引入 Chart.js 或 D3 會多出幾百 KB 的資產、CDN 相依、以及主題切換時的顏色同步問題—— 自己寫反而直接讀 CSS 變數，明暗主題自動跟著走。
不這樣做會怎樣

最實際的後果：交接。這個專案的後續維護者可能是客戶端的工程師。 「打開資料夾、看 views/dashboard.js、120 行、看完就懂」 跟「先 npm install、然後理解 build 設定、然後找出這個元件在哪裡被 render」 是兩種完全不同的維護成本。

反過來說，如果畫面數成長到二十個以上、或出現複雜的跨畫面共享狀態，這個決定就該重新評估。 現在的 state 只有四個欄位（config / overview / elements / theme），還撐得住。

6.2 如果要再快

依投報率排序，目前還沒做的優化：

  1. fit_all() 用 concurrent.futures.ThreadPoolExecutor 平行化。 每個 (batch, element) 完全獨立，而且熱點在 numpy 裡（會釋放 GIL）。預期 3~4 倍。
  2. _simulate_one_pass_array() 的主掃描迴圈改用 numba.njit。 這是唯一一段真正的 Python 熱迴圈，但會多一個相依，對離線部署是負擔。
  3. scan_parameter_grid() 的 compute_purity_window 向量化。 目前是 1920 次 Python 呼叫，改成一次 (n_v·n_t, N) 的批次運算可以省掉大半。
  4. suggest_next_batches() 降低 n_restarts_optimizer， 或在 kriging believer 迴圈裡沿用上一輪的超參數而不完全重擬。

不要先做第 2 項。它最有技術含量，但收益最小——建表只佔完整分析的 0.3%。

9. 如何新增一個 API 端點

以「新增一個回傳每批次質量守恆誤差的端點」為例：

① 在服務層加方法（計算邏輯只能寫在這裡）

# src/expanalysis/service.py
def mass_balance_report(self) -> list[dict]:
    """每批次的質量守恆檢查。"""
    b = self.bundle()
    out = []
    for d in self.repo.all_details():
        res = simulate_passes(...)      # 呼叫 physics
        out.append({"batch_id": d.batch.batch_id,
                    "mass_error": res.mass_error})
    return out

② 需要輸入參數的話，在 schemas.py 定義

# src/expanalysis/api/schemas.py
class MassBalanceRequest(BaseModel):
    n_cells: int = Field(240, ge=60, le=1200)

所有輸入驗證都在這一層。router 與服務層不該再寫 if n_cells < 60: raise ...——Pydantic 的錯誤會被 validation_exc 轉成統一格式，訊息還會指出是哪個欄位錯。

③ 在 router 加端點（薄薄一層）

# src/expanalysis/api/routers/analysis.py
@router.get("/mass-balance")
def mass_balance():
    svc = get_service()
    if not svc.repo.count():
        raise HTTPException(status_code=400, detail="資料庫沒有批次資料")
    return svc.mass_balance_report()
router 只做三件事：取服務、檢查前置條件、回傳。

把計算寫在 router 裡的代價是：AI 助理的工具（assistant/tools.py） 呼叫不到它，於是 LLM 路徑與 UI 路徑會看到不同的數字。第 3.2 節那條規則就是為了這個。

④ 在前端 api.js 加一行

massBalance: () => request('/api/analysis/mass-balance'),

⑤ 錯誤處理是自動的

  • HTTPException → {ok:false, error:{code, message, detail}}
  • Pydantic 驗證失敗 → 422 + 指出欄位
  • 任何未預期的例外 → 500，完整 traceback 寫進日誌， 回給前端的訊息不含堆疊細節
  • NaN / ±Inf → null（由 SafeJSONResponse 消毒）
為什麼要有 NaN 消毒

NaN 在數值計算裡是合法的「無法計算」訊號（批次數不足時的 R²、 bootstrap 失敗時的信賴區間），但不是合法的 JSON。不處理的話序列化會直接丟 ValueError 變成 500——使用者只會看到「伺服器錯誤」， 完全不知道真正的意思是「這個數字算不出來」。轉成 null 之後， 前端的 num() 顯示 —，語意正確。

11. 測試策略

現況

tests/ 目錄已建立但目前是空的。程式碼中有數處 docstring 提到 tests/test_physics.py 的驗證結果（質量守恆到 1e-12、與 Pfann 解析解逐點吻合）， 那些性質是實際成立的，但對應的測試檔尚未提交。 接手的第一件事應該是把它們補上——下面列的就是該寫的內容。

11.1 核心方法：用合成資料做閉環驗證

這是整個測試策略的骨幹，也是唯一能真正檢驗「方法對不對」的做法：

已知的真實 k₀、δ/D　→　生成資料　→　整套流程反解　→　檢查能不能還原 還原不了就代表方法有問題。這比在真實資料上「看起來合理」可靠得多—— 真實資料沒有標準答案，你永遠不知道模型是對的還是剛好。 
from expanalysis.data.synthetic import SyntheticConfig, generate_dataset, true_keff
from expanalysis.fitting.fit_keff import fit_batch

def test_keff_recovery():
    """反解出的 k_eff 應該接近生成時用的真值。"""
    cfg = SyntheticConfig(n_batches=12, rel_noise=0.05, inject_anomalies=False)
    details, truth = generate_dataset(cfg)

    for d, row in zip(details, truth["batches"]):
        fits = fit_batch(d)
        for el, f in fits.items():
            k_true = row["true_keff"][el]
            # 設限點多的元素容差要放寬，這是資訊損失，不是 bug
            tol = 0.35 if f.n_censored > f.n_points * 0.5 else 0.15
            assert abs(f.k_eff - k_true) / k_true < tol, \
                f"{d.batch.batch_id}/{el}: 擬合 {f.k_eff:.4f} vs 真值 {k_true:.4f}"

11.4 兩個容易踩的坑

  • 測試不能共用行程層級的單例。get_db() 與 get_service() 都是全域單例。fixture 裡要用 reset_db_singleton() 與 reset_service()， 並把 EXPA_DB_PATH 指到 tmp_path，否則測試會污染開發用的資料庫。
  • 不要對浮點做精確比較。Nelder-Mead 的收斂路徑受平台浮點行為影響， k_eff 在不同機器上可能差在小數第五位。用相對容差，並在容差裡寫清楚它代表什麼 （例如「15% 是量測雜訊下可接受的還原誤差」，而不是一個憑感覺挑的數字）。

12. 日誌與例外處理約定

12.1 日誌分級

級別用途例子
DEBUG單點擬合細節。預設關閉， 呼叫端要用 if log.isEnabledFor(logging.DEBUG) 保護 （避免無謂的字串格式化成本）每次 likelihood 評估的 k 與 NLL
INFO狀態轉換，不是進度 服務啟動、批次匯入完成、schema migration、分析完成與耗時
WARNING可恢復的異常——系統已經降級處理了， 但你該知道LLM 退回模板模式、單批擬合不收斂、GP 擬合失敗退回線性、 bootstrap 無有效重抽
ERROR需要人介入 資料庫寫入失敗、schema 版本高於本程式支援、未處理的例外

輸出同時到 stderr 與輪替檔案（logs/expanalysis.log，5 MB × 5 份）， 避免長時間執行把磁碟塞爆。uvicorn 自帶的 handler 會被清掉並改為 propagate， 否則每一行都會印兩次。

12.2 例外處理原則

只捕捉你知道怎麼處理的例外類型。

全專案的 except 都指名具體型別： except (ValueError, np.linalg.LinAlgError)、 except (TypeError, ValueError)、except httpx.HTTPError。

except Exception 只允許出現在最外層的守護迴圈，而且必須記錄完整 traceback。 全專案只有一處：api/app.py 的 unhandled_exc。 

# api/app.py —— 唯一允許的 except Exception
@app.exception_handler(Exception)
async def unhandled_exc(request: Request, exc: Exception):
    log.error("未處理的例外 %s %s\n%s", request.method, request.url.path,
              traceback.format_exc())
    return _error(500, "INTERNAL_ERROR",
                  "伺服器內部錯誤，詳細內容已寫入日誌。",
                  f"{type(exc).__name__}: {exc}")

另外兩處 bare except 是刻意的，且都有註解說明：

  • run.py 開瀏覽器失敗 —— 開不了瀏覽器不該擋住服務啟動。
  • 前端讀 localStorage —— 私密瀏覽模式下存取本身就會丟例外。

12.3 降級路徑的三條規則

  1. 降級要有聲音。每一次退回（LLM → 模板、GP → 線性、AI → 純物理） 都要 log.warning，而且要在 API 回應的 warnings 或 note 欄位裡告訴使用者。安靜地降級比失敗更危險—— 使用者會以為他看到的是完整功能的結果。
  2. 降級不能丟資訊。退回純物理時，數字仍然是對的，只是少了修正。 不能因為 AI 掛了就整個端點回 500。
  3. 單一批次失敗不能讓整批失敗。fit_batch() 對個別元素的擬合失敗 只記警告並略過；bundle() 的 bootstrap 失敗只是讓那個 k_eff 沒有信賴區間 （前端顯示 —），不影響其他批次。

13. 打包與離線部署

13.1 最簡單的做法：複製資料夾

如果客戶端可以裝 Python，最省事的交付方式就是把整個資料夾（含 .venv）複製過去。 沒有原生擴充需要重編，numpy / scipy / scikit-learn 的 wheel 在同架構同 Python 版本下可以直接搬。

13.2 PyInstaller 打包

pyinstaller --onedir --name ExpAnalysis run.py \
  --add-data "web;web" \
  --add-data "docs;docs" \
  --hidden-import uvicorn.logging \
  --hidden-import uvicorn.loops.auto \
  --hidden-import uvicorn.protocols.http.auto \
  --hidden-import uvicorn.lifespan.on \
  --collect-all sklearn \
  --collect-all scipy

（Windows 用 ; 分隔 --add-data，macOS / Linux 用 :。）

13.3 路徑：唯一真正的陷阱

唯讀資源與可寫入資料必須走不同的路徑解析。

PyInstaller 打包後，sys._MEIPASS 指向一個解壓縮出來的臨時目錄。 資源檔（web/、docs/）在那裡，但程式結束時整個目錄會被清掉。 把資料庫寫進去的結果是：使用者匯入了資料、關掉程式、下次打開什麼都沒了， 而且完全找不到原因。

config.py 已經處理好這件事，改動時務必保持：

def _project_root() -> Path:
    """可寫入資料的基準：exe 旁邊（絕不是 _MEIPASS）。"""
    if getattr(sys, "frozen", False):
        return Path(sys.executable).resolve().parent
    return Path(__file__).resolve().parents[2]

def resource_path(rel: str) -> Path:
    """唯讀資源的基準：打包時是 _MEIPASS，開發時是專案根目錄。"""
    base = Path(getattr(sys, "_MEIPASS", _project_root()))
    return base / rel
用途用哪個打包後實際位置
web/、docs/（唯讀）resource_path() _MEIPASS/web（臨時，會被清掉——沒關係，是唯讀的）
data/expanalysis.db（可寫）SETTINGS.db_path ExpAnalysis.exe 旁邊的 data/
logs/（可寫）SETTINGS.log_dir exe 旁邊的 logs/
.env（讀取）_project_root() / ".env" exe 旁邊

13.4 其他離線注意事項

  • 不要引入任何 CDN 資源。前端目前完全沒有外部請求——沒有字型、沒有圖示庫、 沒有分析腳本。這個性質要守住，客戶端的網路很可能是完全封閉的。
  • 檢查 --collect-all sklearn。sklearn 有大量動態匯入， 少了它打包後會在第一次擬合 GP 時炸掉，而且錯誤訊息很難懂。
  • 首次啟動會慢。--onedir 比 --onefile 快很多 （後者每次啟動都要解壓縮上百 MB）。除非客戶堅持要單一檔案，否則用 --onedir。
  • 防毒軟體。PyInstaller 產物常被誤判。交付前先在客戶端環境測一次， 必要時提供程式碼簽章或請客戶加白名單。
  • 連接埠衝突。打包版建議在 run.py 加上「8848 被佔用時自動往上找」的邏輯， 一般使用者不會加 --port。

14. 已知限制與後續可做的事

14.1 已知限制

限制影響目前的處置
熔區長度 l 靠溫度代理 溫度只是 l 的間接指標。溫度→l 的關係隨爐體、裝料量、氣氛而變， 跨爐體時模型不可轉移 異常偵測會在批次層級同向偏移時主動建議客戶實測 l。 這是整個專案投報率最高的補量測項目
各元素獨立處理 假設元素之間沒有交互作用。高濃度下這不成立 （共晶、金屬間化合物形成） 在 ppm 級是合理近似。若客戶進料是 3N 級（千 ppm），這個假設要重新檢視
per_element_ppm 未接到服務層 compute_purity_window() 支援個別元素規格上限， 但 service.simulate() / optimize() 沒有把它傳下去， 目前一律只看總雜質 資料層的 ElementSpec.spec_ppm 已經存了，接起來只是幾行
L1 殘差修正要先跑過驗證才會啟用 corrector.enabled 只在 service.lobo() 裡被設定。 使用者若沒開過「模型驗證」頁就勾雙軌，會看到「未套用」 已在使用者手冊第 8.2 節說明。 更好的做法是在 _recompute() 結尾非同步觸發一次 LOBO
6N 門檻在前端硬寫成 1.0 batches.js / simulate.js 傳給 profileChart 的 threshold 是常數 1.0， 沒有讀 /api/config 的 purity_threshold_ppm。 客戶若改門檻，綠區（後端算的）會對，但虛線標籤（前端畫的）會錯 應改為讀 state.config.purity_threshold_ppm
best_robust / best_throughput 的樂觀值不是真的樂觀值 grid_search.py 裡這兩個建議的 yield_optimistic（與 best_throughput 的 yield_pessimistic）被直接填成名目值，沒有用 k_lo / k_hi 重算 UI 上「悲觀 xx%」對 best_throughput 會誤導，應補算
沒有身分驗證 綁 127.0.0.1 時沒問題，但用 --host 0.0.0.0 就是全網段可存取，且可以刪資料 定位是單機離線工具。要多人共用必須先補認證
合成資料無法附加 seed_database() 預設 clear=True， 會清空既有資料 API 有 clear_existing 參數，但前端固定傳 true
說明文件尚未寫齊 docs/assets/docs.js 的 PAGES 列了 8 篇， 指向尚未撰寫的檔案時側欄連結會 404。更嚴重的是缺 docs/index.html： run.py 啟動時印出的「說明文件 → .../docs/」與前端側欄的「說明文件」按鈕 都指向 /docs/，而 StaticFiles(html=True) 找不到 index 會拋出未被攔截的 404，最後變成 500 補上 docs/index.html（總覽頁）即可同時解決兩件事； 其餘篇章待補

14.2 後續可做的事（依投報率排序）

  1. 把測試補齊。第 11.2 節的清單。這是接手後的第一優先—— 沒有測試，上面任何一項改動都是在賭。
  2. 接上熔區長度 l 作為直接輸入。資料模型已經有 zone_len_mm，只要客戶開始實測，把它從「設定值」換成「實測值」 就能立刻提升模型可轉移性。這是不用寫多少程式碼、但效果最大的一項。
  3. 個別元素規格上限接到服務層。幾行的事，但對有特殊規格要求的客戶價值很高。
  4. 修掉 14.1 的三個小 bug（前端門檻硬寫、樂觀／悲觀值、AI 啟用時機）。
  5. fit_all() 平行化。完整分析從 5.2 秒降到約 2 秒， 第一次載入的體感差很多。
  6. 批次比較檢視。目前只能一次看一批。並排看兩批的疊圖與殘差， 是工程師實際查問題時最常做的動作。
  7. 報告匯出（PDF / Word）。客戶會需要把結論放進正式文件。 目前只能截圖。
  8. 多次 pass 的中途取樣支援。Measurement.pass_index 欄位已經存在但沒有被使用。如果客戶在第 4 次與第 8 次 pass 後都取樣， 這些資料可以大幅提升擬合的可辨識性。
  9. 元素間交互作用建模。只有在客戶進料濃度升到千 ppm 級時才需要。 現在做是過度工程。
改任何東西之前，先問這三個問題
  1. 這個改動會不會讓 physics/ 依賴到上層？（會的話，重新設計）
  2. 關掉所有 AI 層之後，系統還完整可用嗎？（不是的話，重新設計）
  3. 這個數字在 UI 路徑與 LLM 路徑上會不會不一樣？（會的話，計算邏輯放錯層了）
