# 系統邏輯總覽

這份文件描述系統**目前實際的行為規則**，不看程式碼也能理解。

設計提案在 [device-classification.md](device-classification.md)；那份寫的是
「應該長什麼樣」，這份寫的是「現在是什麼樣」。文件末尾列出兩者的差距。

---

## 1. 設備分類怎麼判定

分類分成三個各自獨立的問題，**不要用其中一個推導另一個**。

### 1.1 「這是什麼」 → `category`

在 blueprint（`DeviceType`）上，11 種：

`battery`、`pcs`、`generation`、`meter`、`load`、`generator`、`ev_charger`、
`controller`、`sensor`、`gateway`、`other`

**「純量測設備」由 category 判定**，不是由能力旗標推導：只有 `meter` 與
`sensor` 算是量測設備。一盞不可控的照明四個能力旗標全是 `False`，但它是
**負載**，不是電錶。

### 1.2 「能做什麼」 → 四個能力旗標

| 旗標 | 意義 |
| --- | --- |
| `can_charge` | 能在命令下吸收電能 |
| `can_discharge` | 能在命令下輸出電能 |
| `can_export` | 允許把電送回市電側 |
| `is_dispatchable` | 接受任何「調度類」命令 |

**生效值的解析順序**：

1. `Device` 上的覆寫（`null` 代表未覆寫）
2. blueprint 的預設值
3. 沒有 blueprint → **全部視為 `True`**（寬鬆），但 API 回傳
   `capabilities_unchecked: true`，console 會顯示「未指定型號，未做能力檢查」

第 3 點是刻意的：讓沒有 blueprint 的既有設備繼續運作，但把這個缺口顯示出來，
而不是變成一個令人意外的失效。

**blueprint 的預設值依 category 決定**（由 `manage.py bootstrap` 寫入）：

| category | 充 | 放 | 逆送 | 可調度 |
| --- | --- | --- | --- | --- |
| `battery` / `pcs` | ✓ | ✓ | ✓ | ✓ |
| `generation` | ✗ | ✓ | ✓ | ✓ |
| `generator` | ✗ | ✓ | ✗ | ✓ |
| `ev_charger` | ✓ | ✗ | ✗ | ✓ |
| `meter` / `sensor` | ✗ | ✗ | ✗ | **✗** |
| `load` | ✗ | ✗ | ✗ | ✗ |
| `controller` / `gateway` / `other` | ✗ | ✗ | ✗ | ✓ |

**可控負載**（例如可遠端關閉的冰水機）不需要新旗標：`category=load` 加上
`is_dispatchable=True` 就是它，與純被動負載的差別只在那一個旗標。

### 1.3 「在這個場域扮演什麼」 → `EnergyAsset.role`

六種：`grid_meter`、`load_meter`、`pv`、`battery`、`ev_charger`、`generator`。

這回答的是「這台設備的哪個 metric 供應能量平衡中的哪一條流」，**不是設備
類型**。同一台雙向 PCS 在不同場域可以扮演不同角色。

### 1.4 「它自稱是什麼」 → `DeviceDeclaration`（不可信）

見第 4 節。

### 1.5 設備身分與「類別不可變更」政策

**營運政策：設備的類別永遠不會被修改。** 硬體真的換成不同的東西時，做法是
**建立一台新設備**、把舊的退役——不是把舊那筆資料編輯成新的東西。這樣每一個
歷史數字都還歸屬於實際產生它的那台設備。

**識別碼是完整的 Sparkplug 位址**：`(group_id, edge_node_id, device_id)`。

- `group_id` 是組織代碼，`edge_node_id` 是一條 MQTT 連線，`device_id` 是掛在
  那條連線下的設備
- `device_id` 只在**同一個 edge node 內**唯一，不是全平台唯一。前兩層已經把
  設備定位了，再要求全域唯一等於不准兩個客戶都把電錶叫 `METER-01`
- MQTT 帳號 `node-{group_id}-{edge_node_id}` 全平台唯一——因為它認證的是連線
- 這些唯一性都是**資料庫層級約束，不看退役狀態也不看 soft delete**

所以**接替設備必須在同一個節點下換新的識別碼**。現場作業要多一步：把新的
`device_id` 寫進替換硬體的設定。建議命名慣例例如 `ZQS-BESS-0001` →
`ZQS-BESS-0001-R2`（替換精靈預設就這樣填）。

替換時連線本身怎麼處理，取決於舊設備掛在哪裡：掛在網關上的，新設備沿用同一個
節點（換的是設備，不是連線）；自己直連的，會拿到一個以新 id 命名的新節點與新
帳密。

**`serial_number` 沒有唯一性約束**，目前只是自由文字，不能拿來當識別碼。

### 1.6 邊緣節點：一條連線，不是一台設備

平台遵循 Sparkplug B，位址因此有三層而不是兩層。`EdgeNode` 就是中間那層，代表
**一條 MQTT 連線**。

它為什麼必須是獨立的一層，而不是設備上的一個欄位：Sparkplug 把序號（`seq`）、
生死序號（`bdSeq`）、metric 別名表全部綁在連線上。這些狀態沒有一個屬於單一設備
——一台網關前置十二顆電錶時，十二台設備共用一個 `seq`。放在設備上就得複製十二
份並保持同步，那是不可能維持正確的。

| 情況 | 模型 |
| --- | --- |
| 網關前置多台設備（常見） | 一個 `EdgeNode`，底下多個 `Device` |
| 設備自己講 MQTT | 一個 `is_implicit=True` 的 `EdgeNode`，底下一個 `Device` |

直連設備也走同一條路徑，不另開一套。理由很實際：另一套等於 birth、death、
sequencing 各有兩份實作，而第二份永遠會腐爛。隱含節點在 console 上預設隱藏，
操作者看不到自己沒要求過的東西。

**MQTT 憑證掛在節點上**，因為憑證認證的是連線。停用一台掛在網關上的設備不會動
到憑證（會把鄰居一起弄下線）；停用一台直連設備則會停用它自己那個隱含節點的憑證。

### 1.7 別名表：連線狀態，但存在資料庫裡

Sparkplug 允許 DATA 訊息只帶 `alias=7` 而完全不帶名稱，這是它省頻寬的主要來源。
代價是別名表變成連線狀態：弄丟它，之後每一則讀值都無法解讀。

`MetricAlias` 把它存進資料庫，所以 worker 重啟、或第二個 worker 副本，仍然可以
解讀一段在它啟動之前就開始的資料流。

BIRTH 進來時是**整表覆寫**，不是逐筆更新。出生宣告的定義是「完整清單」，沒被列到
的別名就是退役了；留著它會讓舊的對應去解讀新的訊息，把讀值記到錯誤的 metric 上。

遇到查不到的別名時，平台會發出重生要求（見 §1.8），不會猜。猜錯的代價是把一筆
真實讀值寫進錯誤的序列，那比丟掉它更糟。

### 1.8 重生（Rebirth）：唯一的復原路徑

`seq` 出現缺號，代表有訊息遺失；別名表可能已經不再對應發布端以為的東西。規範
給的唯一補救就是要求節點重新宣告一次。

平台在三種情況要求重生：序號缺號、收到查不到的別名、操作者手動按下。同一個節點
有 **30 秒冷卻**，所以一連串亂序訊息只會換來一次要求而不是風暴。

重生要求是廉價的——節點只是重發一次 BIRTH——所以平台偏向多問。跑多個 worker 副本
時，同一個節點的訊息確實可能被亂序檢視，這時多問一次仍然是對的處理。

### 1.9 設備類別：照「做什麼」命名

類別描述的是這台設備**做什麼**，不是它**怎麼做到的**。

`generation`（產電單元）涵蓋太陽能、燃料電池、風力、汽電共生——任何為場域產生
電力的東西。取名叫「PV 變流器」的話，之後每一種新技術都得被歸進一個描述不了它的
名字底下；等到這件事變得明顯時，錯的標籤上已經掛著歷史資料了。

`generator`（備援發電機）刻意分開：它燒燃料，所以每一度電都有運轉成本、有自己的
成本模型。那是**行為上的差異**，不是命名上的差異。

`load`（用電設備）是為了看見耗電量而登記的設備：冰水主機、空壓機、產線。它只回報、
不接受命令，所以沒有任何可用命令——這是誠實的答案，不是漏掉了。

> 登記一台用電設備**不會**改變場域的能量平衡。它是被觀察的對象，不是被計入的
> 流量；重複計算的規則見 §2。

### 1.9A 節費基準線與運轉限制是可以設定的

`savings_baseline` 與 `enforce_limits` 兩個欄位在 model 上、在表單上，但**曾經
不在 API schema 裡**——所以 console 上的控制項看起來會動，實際上值送不進伺服器、
也讀不回來。一個會默默忽略你的設定，比一個根本不提供的設定更糟。

現在兩者都在 `StoragePlanIn`／`StoragePlanOut` 裡，
`tests/test_storage_plan.py` 釘住了雙向往返。

`SavingsBaseline` 也從三個散落的字串變成一個列舉——它的欄位註解本來就寫著
「見 :class:`SavingsBaseline`」，那個類別只是一直沒被寫出來。

### 1.10 即插即用：目錄從出生宣告長出來

DBIRTH 已經列出這台設備提供的每一個 metric、每一個的資料型別，而本平台的 profile
還讓它帶上單位。那就是 metric 目錄需要的全部資訊，所以一台從來沒有人設定過的設備
可以**把自己描述進系統**：圖表有了座標軸標籤，合理性檢查有了型別，console 不再顯示
生硬的 key。

推論規則與 property 清單見 device-protocol.md §5.1.1。這裡只講兩條界線，因為它們
是這個便利功能不會變成漏洞的原因：

- **永遠不覆蓋。** 操作者已經定義過的 key 保留原定義，一律如此。否則一次韌體更新
  就能悄悄改掉一堆告警規則所依賴的 metric。
- **只建立組織層級的定義。** 內建 metric 由所有租戶共用，不會被碰到；租戶自己的
  複本會讓一個共用 metric 的定義分裂成兩份。

**註冊一個 metric 是註冊一個標籤，不是授予一項能力。** 能力、額定值與分類仍然走
`DeviceDeclaration`，等人在 console 上接受。信任邊界沒有改變。

### 1.11 工作流程：畫出來的控制邏輯

`apps/workflows` 讓操作者在畫布上畫控制流程：條件判斷、下命令、計時、跳轉。
流程是**被觸發**的——編輯器的按鈕、另一個流程、儲能規劃、或外部 API——不是排程
輪詢，所以一次執行是有位置、有狀態的長生命物件。

幾個設計決定，每一個都有具體理由：

**並行是「畫」出來的，不是設定出來的。** 一張圖可以有多個起點，一個輸出可以拉出
多條線；每一條就是一個並行分支。引擎用 token 建模——一次執行持有多個 token，各自
停在某個節點上——而不是用執行緒，這是流程能在行程重啟後繼續的原因：位置在資料庫
裡，不在某個 Python 呼叫堆疊上。

**並行上限是伺服器設定（`WORKFLOW_MAX_CONCURRENT_RUNS`，預設 5），不是租戶設定。**
操作者在上限內自由增減流程，但不能調高上限，因為它保護的是大家共用的那台機器。
超過就**拒絕**而不是排隊：排隊會累積一份看不見的待執行命令清單，直到執行那一刻
才爆出來。**計數單位是執行緒（並行分支／token），不是 run**：兩個起點的圖占兩
個名額，啟動時以「現有分支數＋這張圖的起點數」檢查。容量端點會列出**是誰在占
用**（工作流程名、狀態、分支數），因為「我都停了為什麼還是 1/5」必須答得出來
——通常是一筆停在計時節點上的舊執行。

**讀值不可信就不判斷。** IF 節點遇到沒有讀值、或讀值太舊（預設 180 秒）的情況，
走「No reading」分支而不是猜。把「沒讀到」當成 0 會讓 `power < 100` 對一台停止
回報的設備成立——這與安全聯鎖想要的正好相反。

**IF-End Timer 是重複取樣的，不是睡過去的。** 條件要**連續**成立 N 秒才走成立
分支，中途掉下來就重新計時。睡到時間到才看一眼分不出「一直成立」和「中間掉過又
回來」，那正是這個節點存在要濾掉的東西——跟 PLC 的 on-delay timer 同一個道理。

**Jump 讓出當前 tick。** 往回跳就是迴圈，全速執行的迴圈是 busy-wait：幾秒內燒光
步數預算、灌爆記錄、重複讀一個幾秒才變一次的值。改成每 tick 走一輪，語意也正好
是操作者畫的「持續檢查」。防護仍在：每次執行有步數上限（預設 10,000），用步數
而不是時間計，因為緊迴圈燒的是步數不是牆鐘。

**抵達即合流。** 分支移動到「同一次執行已有分支停駐」的節點時,併入既有分支
而不重複。沒有這條規則,Jump 跳回一個會分岔的節點就會每圈重新分岔——分支數
2、4、8 翻倍成長,直到步數上限把執行殺掉(實測 12 圈爆到 472 個 token)。一個
節點同時只有一個分支,是這張圖的 PLC 讀法;分岔後再匯聚的圖,共用尾段也因此
只執行一次。有測試釘住。

**每執行步數上限預設為無上限(0)。** 「守住設定值直到條件解除」本來就是永不
終止的合法控制迴圈,固定步數上限殺掉的恰恰是引擎存在要服務的流程。每次呼叫
的步數上限(per-call)仍然生效,綁住的是每個 tick 的工作量;要限制總步數可自
行設定 `WORKFLOW_MAX_STEPS_PER_RUN`。

**分支之間輪流推進。** 每個 token 每一「輪」走一步，一輪走完才開下一輪——限制在
「輪」而不是「每次呼叫」是刻意的：後者公平但慢到直線五個節點要五個 tick。

**測試執行（dry run）是執行的欄位，不是參數。** 它會完整評估每個條件、寫完整
逐步記錄，但不送任何命令；`dry_run` 記在執行本身上，一個月後讀記錄仍然知道
當時有沒有碰到硬體。dry run 的檢查在引擎層，不在各節點——忘記檢查的節點型別
不該有辦法從測試送出真命令。

**節點可以個別停用。** 引擎跳過它但路徑仍通，等於把一步註解掉而不用重拉線。

**動作走同一道門。** Send Action / Set Data 全部經過 `dispatch_command()`，能力
檢查、方案包絡、稽核軌跡與人工操作完全相同；綁定場域的流程不能命令其他場域的
設備。工作流程不是特權路徑。

**Wait 是停車，不是輪詢。** 等待節點把 token 停到期望時刻才醒，途中被提早叫醒
（單步、慢動作）也不會重算時鐘。Condition Wait 等讀值達到條件才往下走，逾時走
逾時分支——沒有讀值視為「還沒達成」而不是達成，逾時就是接住永遠不回來的設備的
出口。IF-End Time 是每日時間區間（可選星期、可跨午夜），用**場域的時區**判讀
（場域→組織→UTC），因為 09:00–18:00 用 UTC 判讀，一年會有兩次變成夜班。

**暫停、單 Node 執行與停止點是操作者的除錯器。** 暫停凍結一次執行（token、計時、
context 全保留，Resume 從原地繼續）；暫停中的執行仍占用並行名額，否則暫停會變成
無限堆疊執行的後門。**單 Node 執行**只跑目前選取的那一個節點：執行一次、記錄結果、
不沿連線繼續就結束；節點上的停用與停止點旗標會被忽略——操作者指名要跑它（API:
`POST /workflows/{id}/run-node`）。節點可以設**停止點**：引擎在執行該節點**之前**
暫停，讓操作者檢查它即將依據的狀態；Resume 後執行一次、不重複觸發。節點間延遲
（0–30 秒，執行層級）是觀賞用的慢動作；另有 API 層級的 `/step` 端點做逐步除錯,
它會無視慢動作延遲、但絕不縮短 Wait 節點自己的計時。

**執行錯誤會停下整個流程**，失敗的節點記在記錄裡，編輯器把它標成紅色。

**箭頭圖塊也是裝飾。** `arrow` 節點是一個可縮放、可轉八個方向、可上色的指示
箭頭——註解「指向某處」的需求由它承擔（比在便利貼上拖自由箭頭更直觀）。它沒有
任何把手，完全不能連線。

**Note 是裝飾，不是流程。** 畫布上的便利貼可以調整大小，指示方式有兩種：
連向節點的虛線箭頭，以及**自由箭頭**——像對話框的尾巴，尖端拖到哪就指到哪、
不必接任何東西（存在 note 的 `arrow` 欄位）。連線箭頭只能從 Note 出去；任何
連進 Note 的邊在存檔時被拒絕，因為那在圖上看起來像流程而引擎當作死路。Note
的箭頭也不影響起點判定。Note 永遠不會被當成起點、永遠不執行。

**觀看執行走 SSE，不是輪詢。** 編輯器對進行中的執行開一條 server-sent events
串流（`/api/workflow-runs/{id}/stream`），run 狀態與新記錄以增量推送，輪詢自動
停用；串流斷了（token 過期、網路問題）輪詢自動接手,這是唯一的 fallback 路徑。
誠實地說：因為引擎在另一個行程、SQLite 沒有跨行程通知,伺服器端仍以短間隔查
資料庫——省的是 HTTP 層（一條連線、只送變化），不是查詢本身。要做到真推播需要
Redis pub/sub + ASGI，那是文件化的正式環境升級路徑，不是開發預設。

**節點可以上色。** 顏色存在圖裡，文字自動換成對比色（YIQ 亮度判定），所以
操作者選不出讀不了的組合。

新的節點型別註冊進 `apps/workflows/nodes/` 的 registry 即可——參數表單和調色盤
都是前端從 `/workflows/node-types` 讀出來渲染的，加節點型別不用改前端。節點的
顯示名稱與說明依 console 語系顯示（`workflows.nodeTypes.*`），沒有翻譯時退回
伺服器的英文原文。

### 1.11A 編輯器的操作習慣

畫布支援手已經熟悉的動作:從調色盤**拖曳**節點到畫布(點一下也可以)、Delete
刪除選取、Ctrl+C / Ctrl+V 複製貼上、Ctrl+Z 復原(最多 50 步)。

幾條規則:

- **任何欄位有焦點時快捷鍵一律不動作**——名稱欄裡的 Delete 是刪字,不是刪節點。
- 複製只帶**選取範圍內部**的連線;貼上的 Jump 若指向複製範圍內的節點,跟著改指
  到它的複本,指向範圍外的保持原目標——「複製這個片段」的語意。
- 刪除由編輯器自己處理(React Flow 的 `deleteKeyCode` 關閉),因為 payload 表與
  復原歷史必須同步更新;讓 React Flow 也刪一次會留下復原後重新出現的幽靈節點。

執行控制列放在畫布正上方:執行/測試、暫停/繼續、停止、單 Node 執行、節點間
延遲、一鍵自動排列。自動排列按「距離起點的最長路徑」分層、按父節點的重心排序
每一層,Note 不動——整理流程不該打亂別人放好的註解。參數有基本防呆(必填、
數值範圍、HH:MM 格式),錯誤即時顯示在檢視面板並標在節點上;離開頁面時若有
未儲存的變更會先確認。

### 1.12 儲能規劃的「執行工作流程」策略

`DispatchStrategy.WORKFLOW` 把一個場域的控制權交給指定的流程。調度引擎每個週期
確認該流程有在跑（沒跑就啟動、跑著就不動），**不再**替這個場域計算功率設定值——
否則就有兩個東西在指揮同一顆電池。流程被刪掉時，規劃會回報 `no_workflow` 而不是
悄悄退回別的策略：一個默默不動作的規劃跟一個正常的規劃在設定頁上長得一模一樣。

---

### 1.12C 規劃與電價沿場域樹繼承

場域的**有效規劃** = 自己的綁定,否則採最近祖先的綁定——綁在父場域的方案自動
涵蓋子場域,子場域自行綁定即覆蓋。電價方案掛在規劃上,因此電價繼承是同一條
規則的計費面。調度引擎、成本彙總、console 顯示走同一個解析
(`apps/ems/plans.py`);per-site 端點以 `inherited_from` 標明來源祖先。

**能源資產不繼承、即時計算不彙總子樹。** 電表綁在哪個場域,量的就是那個場域;
父場域的即時功率流與能源區間只計自己直接綁定的資產。跨子樹的彙總屬於報表層
(`GET /sites/{id}/summary` 與群組 rollup),在那裡父場域才涵蓋整棵子樹。

### 1.12B 儲能規劃是具名模板，場域綁定它

規劃不再是每個場域一列的隱形設定，而是**具名的策略設定檔**（與電價方案同一個
形狀）：在「儲能規劃」頁建立、命名、編輯，場域只是**綁定**其中一個——同一份設
定檔可以驅動整批相似的場域，換策略就是換綁定。刪除設定檔會解綁其場域（場域不
會被刪，只是停止調度並明白顯示「未綁定方案」）。API：`/ems/plans` CRUD 加上
`PUT /ems/sites/{id}/plan`（綁定，`plan_id: null` 解綁）。

### 1.12A 儲能策略：從標籤變成算術

在此之前,規劃上的「策略」多半是描述;現在每個策略都是 `apps/ems/strategy.py`
裡的實際計算,由調度引擎每個週期評估。共同原則:**讀值不新鮮就不動作**——
從停止更新的讀值做出的控制決策,是讓電池跟昨天的負載曲線打架的方法。

**權威順序**(`decide()`):
1. **進行中的需量反應事件**——對電網的承諾,壓過一切(包含工作流程接管);
2. **指定功率的排程窗**——操作者的明確覆蓋;
3. **策略**;
4. 運轉包絡 + **健康約束**,對以上任何來源的輸出一視同仁地夾限。

**契約容量管理(demand_cap)**:需量超過上限就放電壓回去;上限留空時採契約容量
的 95%(餘裕是取樣間隔的工作空間)。回充只在電價最低時段、且**永遠不超過需量
餘裕**——為了防超約而回充結果把需量充爆,是這個策略最經典的自打臉,有測試釘住。

**時間電價套利(tou_arbitrage)**:對電價方案每日取樣 96 點找出最高/最低價時段,
最低價充、最高價放;當日價差低於 `min_price_spread` 就完全不動——平價差裡來回
搬電,90% 的來回效率只是在付錢磨電池。禁止逆送時放電上限=場域自身負載;充電
永遠不超過契約容量餘裕。

**光儲自發自用(self_consumption)**:PV 盈餘充電、負載缺口放電,死區 0.2 kW
以下不追——追噪聲磨的也是電池。

**備援保留(backup_only)**:SOC 低於保留目標就補charge,其餘完全不動。

**需量反應(不是策略,是事件)**:`POST /ems/sites/{id}/demand-response` 觸發
(console 按鈕或外部 API 調度信號),指定放電 kW 與時長;重疊事件被拒絕;可
取消。進行中事件壓過所有策略——但仍受包絡與健康約束夾限,超出硬體的承諾仍然
是謊言。

**電池健康約束(所有來源共用)**:溫度超過上限(讀電池設備上指定的 metric)
雙向停機;當日等效循環數(當日放電 kWh ÷ 可用容量,從能源區間讀,重啟不歸零)
用完後禁止再放電、**但不禁止充電**——充電不消耗放電預算。

節奏誠實:策略跑在排程器週期(分鐘級),對 15 分鐘需量與電價段落足夠;它不是
毫秒級的 PCS 迴路,也不假裝是。

### 1.13 電價：台電內建方案

台電**沒有公開的即時電價 API**——電價是牌價，由電價費率審議會約每半年檢討一次。
所以正確的架構是「內建費率表」而不是「串接」：console 內建三個台電時間電價方案
（表燈簡易二段式、三段式、低壓電力二段式，`apps/ems/taipower.py`），一鍵套進
電價表單後全部欄位仍可編輯。每個方案標注**費率年度**，讓過期的表看得見而不是
默默算錯；累進加價、基本費（每戶）與功率因數調整不在 kWh 模型範圍內，套用時
的提示會講明「計費前請對照台電最新公告校對」。尖峰/離峰的解析走既有的
`resolve_price()`（場域時區、first-match-wins），成本與節費報表因此直接受惠。

### 1.14 通知：Email、LINE 與事件訂閱

通知管道（`NotificationChannel`）有四種：webhook、**email**（SMTP 由環境變數
設定，未設定時走 console backend——開發環境信件印在 worker log 裡，端到端可測
而不會寄丟）、**LINE 機器人**（Messaging API push；LINE Notify 已於 2025 年
停止服務，config 需要 channel access token 與接收對象 ID，token 存後不再回讀）
與 MQTT。

**警報與事件是兩個獨立的訂閱開關。** 警報是規則引擎的結論，由警報規則勾選
管道、依 `min_severity` 過濾；設備事件是設備自己回報的東西（vendor E-code、
斷線……），管道直接訂閱、依 `min_event_level` 過濾，不需要規則。分開是因為
受眾不同——想收「電池過熱」的 LINE 群未必想收每一條廠商事件碼。

送達沿用同一條先寫後送的路：`NotificationDelivery` 先落庫（alert 與 event
擇一,XOR constraint），worker 批次送、有上限的重試、錯誤可見。

## 2. 能量平衡：誰算、誰不算

### 2.1 基本規則

**每一條能量流，恰好要有一條量測路徑。**

一個 `EnergyAsset` 只有在 `include_in_balance = True`（預設）時才會進入場域的
能量平衡。設為 `False` 的資產仍然：

- 有自己的圖表與歷史
- 出現在設備列表與地圖
- 未來會有自己的耗能統計

但**不會**被加進 `load_kwh`、`grid_import_kwh` 等場域層級的數字。

### 2.2 什麼時候該設 `False`

| 情境 | 設定 |
| --- | --- |
| 總負載表 + 個別機器的分表 | 總表 `True`，個別機器 `False` |
| 沒有總表、逐饋線量測 | 所有饋線表 `True`（相加剛好涵蓋全部） |
| 市電總表以外的第二顆電錶 | `False` |
| 兩台 PV 逆變器 | **都 `True`**（實體上是兩個來源，相加正確） |
| 兩組電池 | **都 `True`**（同上） |
| 總表已含 EV 充電樁，又單獨量測充電樁 | 充電樁 `False` |

判準：**這個量測涵蓋的電流，是否已經被另一個 `True` 的量測涵蓋過。**

### 2.3 各角色進入哪一條流

```
grid_meter                → grid_import_kwh / grid_export_kwh / peak_import_kw
pv                        → pv_kwh
battery                   → battery_charge_kwh / battery_discharge_kwh + SOC
generator                 → generator_kwh          ← 獨立欄位
load_meter, ev_charger    → load_kwh
```

**`generator` 為什麼獨立於 `battery_*`**：往返效率的定義是
`discharge / charge`。柴發只放不充，把它的輸出併進 `battery_discharge_kwh`
會算出大於 1 的往返效率。

### 2.4 沒有負載表時的推導

若場域沒有任何 `include_in_balance=True` 的 load 角色資產，負載由節點平衡
反推：

```
load = grid_import − grid_export + pv + battery_discharge − battery_charge + generator
```

結果會被 clamp 到 ≥ 0。

### 2.5 積分方法

功率轉能量用**前值保持（zero-order hold）**：每個樣本的值假設保持到下一個
樣本為止。**不是梯形法。**

- 對回報頻率遠高於變化尺度的訊號，誤差可忽略
- 對馬達啟停這種突變負載有系統性偏差，方向取決於變化是上升或下降
- `coverage`（0..1）記錄該區間實際被樣本涵蓋的比例——這是品質指標，低於 0.8
  的區間不該被當成確定的數字
- recording policy 的 `max_interval_seconds`（心跳）決定誤差上界。要做精確
  耗能統計的設備，建議把心跳調到 300 秒以內

**若設備同時回報累計電能（counter），一律優先用 counter 差值**——那是設備
自己累計的，沒有取樣誤差。

### 2.6 跨場域彙總

彙總多個場域時（例如整個廠區）：

- **能量與金額**：直接相加
- **尖峰**：先把同一時間區間內各場域相加，再取這些總和的最大值。**絕不是各
  場域尖峰相加**（那會高估）。回應中的 `peak_basis` 標示：單一場域是
  `measured`，多場域是 `coincident_estimate`
- **比率**（自用率、自給率、往返效率）：分子分母各自加總後再除，**不是平均**
- **幣別**：組織有唯一的 `reporting_currency`，沒有電價方案的場域退回它，所以
  每一列都標得出來。各場域**真的**不一致時數字照給但 `currency` 回空字串——那不
  是可以粉飾的顯示缺口，把兩種幣別相加出來的數字沒有意義。詳見 §6.5

## 3. 命令什麼情況會被擋

所有下行命令都經過同一個關卡（`dispatch_command()`），依序檢查：

| 順序 | 檢查 | 錯誤碼 | HTTP |
| --- | --- | --- | --- |
| 1 | 設備已停用 | `device_disabled` | 409 |
| 2 | 命令不在 blueprint 的目錄裡 | `unknown_command` | 422 |
| 3 | 角色權限不足 | — | 403 |
| 4 | 參數不符 JSON-schema | `parameter_out_of_range` 等 | 422 |
| 5 | 設備尚未驗收（`pending`），且這是調度類命令 | `device_unconfirmed` | 409 |
| 6 | `is_dispatchable=False`，且這是調度類命令 | `asset_not_dispatchable` | 422 |
| 7 | 缺少該命令需要的能力 | `capability_not_supported` | 422 |
| 8 | 該設定會造成逆送，但不允許 | `export_not_permitted` | 422 |

生命週期與身分相關的攔截（都只作用於調度類命令）：

| 情況 | 錯誤碼 | HTTP |
| --- | --- | --- |
| 尚未驗收 | `device_unconfirmed` | 409 |
| 已退役 | `device_retired` | 409 |
| 暫停中 | `device_suspended` | 409 |
| 驗收時被拒絕 | `device_rejected` | 409 |
| 宣告類別與註冊不符 | `device_identity_mismatch` | 409 |

### 3.1 命令需要什麼能力，由「名稱**加上**參數值」決定

只看命令名稱是不夠的：

| 命令與參數 | 需要的能力 |
| --- | --- |
| `set_power_setpoint`，`power_w < 0` | `can_charge`（負值就是充電） |
| `set_power_setpoint`，`power_w > 0` | `can_discharge` |
| `set_power_setpoint`，`power_w = 0` | 不需要任何能力 |
| `set_mode`，`mode = charge` | `can_charge` |
| `set_mode`，`mode = discharge` | `can_discharge` |
| `set_mode`，`mode = auto` | **兩者都要**（auto 可能往任一方向） |
| `set_mode`，`mode = idle` / `standby` | 不需要 |
| `set_export_limit`，`limit_w > 0` | `can_export` |
| `set_export_limit`，`limit_w = 0` | 不需要（設 0 是**禁止**逆送，擋它反而顛倒） |

### 3.2 調度類 vs 設定類命令

blueprint 的命令定義可以標 `"kind": "config"`。設定類命令**不受
`is_dispatchable` 與 `commissioning_state` 限制**。

目前標為 `config` 的：`set_report_interval`、`sync_time`。

所以一顆電錶（`is_dispatchable=False`）仍然可以被要求改變回報頻率——那不會
移動任何電力。

### 3.3 生命週期狀態

見 §11。

## 4. 設備宣告：可以說，不能做

設備可以在 `status` 的 birth message 裡帶一個 `attributes` 物件，宣告自己的
類別、能力與額定值（格式見 [device-protocol.md](device-protocol.md) §3.7）。

### 4.1 絕對規則

**控制與安全檢查只讀已確認的欄位，永遠不讀設備宣告。**

宣告存在獨立的 `DeviceDeclaration` 表，而不是 `Device` 上的
`declared_*` 欄位。這不只是整潔問題：`dispatch_command()` 拿到的是 `Device`，
而 `Device` 上根本沒有承載宣告的欄位，因此想誤用也無從誤用。

### 4.2 收到宣告時會發生什麼

1. 沒有 `attributes` → 什麼都不做
2. `schema_version` 不認得 → 記一筆 `DeviceEvent`（`declaration.unsupported_version`），忽略內容
3. 與上一次宣告**完全相同** → 只更新接收時間，**不產生待審核**
   （設備每次重連都會發 birth message，否則審核佇列會被洗版）
4. 有變動 → 覆寫宣告記錄、算出 diff、狀態設為 `mismatched`、發一筆
   `DeviceEvent`（`declaration.changed`，或類別不同時的
   `declaration.identity_mismatch`）
5. **任何情況下都不改動 `Device` 的能力欄位**

### 4.3 有人偽造宣告會怎樣

1. 攻擊者必須先持有該設備的 MQTT 憑證（EMQX auth webhook 是 fail closed 的）
2. 他讓設備宣告 `can_charge: true`
3. 宣告存起來，狀態 `mismatched`
4. `Device.can_charge` **不變**，充電命令仍被 `capability_not_supported` 擋下
5. 操作者在設備頁看到「宣告與生效值不符」的 diff

**最壞情況是一個誤導操作者的提示，不是一個可執行的能力。**

### 4.4 採用宣告：只在驗收階段，只有一次

`POST /devices/{id}/declaration/review` `{"accept": true}`，需要 **ADMIN**，
而且**只在設備仍是 `pending` 時可用**。之後回 409 `declaration_not_adoptable`。

理由就是 §1.5 的政策：類別不會改變，所以驗收之後的分歧不是一個待批准的變更，
而是「硬體大概被換掉了」的訊號，正確的處置是建立接替設備。

採用後：能力欄位被寫入、`capability_source` 標為 `device`、生命週期轉為
`active`，並在 audit 留下 `device.declaration_accepted`。

`{"accept": false}` 是**知悉**（acknowledge）：宣告狀態改為 `acknowledged`，
設備完全不動。**知悉不會解除身分不符造成的命令凍結**——看到問題不等於解決
問題。

### 4.5 宣告狀態

| 狀態 | 意義 |
| --- | --- |
| `matched` | 與註冊資料一致 |
| `mismatched` | 有差異，尚未處理 |
| `acknowledged` | 差異已知悉，不再提示 |

### 4.6 身分不符：資料照收，命令凍結

當宣告的 `category` 與註冊的 blueprint 類別不同時：

1. **telemetry 照常接收**——資料不能丟
2. 記一筆 `DeviceEvent`（level `error`、code `declaration.identity_mismatch`）
3. 宣告標記 `identity_mismatch = true`
4. **所有調度類命令被拒絕**，回 `device_identity_mismatch`（409）
5. console 顯眼提示，並提供「替換設備」入口

第 4 點是重點：**身分不確定時，控制要收緊而不是照常放行。** 如果不確定這台
是什麼，就不該對它下能量指令。

只有**類別**不同會凍結命令；單純的能力差異只會標記為 `mismatched`。

### 4.5 哪些欄位維持自動更新

`firmware`、`hardware`、`ip`、`rssi`、`location` 仍然直接寫進 `Device`——
它們是純敘述性的，不影響任何控制決策。

界線很清楚：**這個值會不會被 `dispatch_command()` 讀到。**

## 5. 哪些情況記 `null`

系統的原則是：**不知道就記成不知道。** 把未知填成 0 會讓錯誤變成看起來合理的
數字，那比明顯的空白更難發現。

| 情況 | 記法 |
| --- | --- |
| 累計計數器倒退（換表／韌體重置／未知的溢位） | 該區間的 delta 記 `null`，**不是 0 也不是負數**，並發 `DeviceEvent`（`counter.reset`） |
| 計數器倒退但 `Metric.counter_max` 有值 | 做 wrap 修正 `(counter_max − first) + last`，並標記 `counter_reset` |
| 計數器倒退幅度小於容差（浮點雜訊） | 記 0 |
| 該區間完全沒有樣本 | 能量記 `null`，`basis = "unknown"` |
| 子樹裡沒有任何場域有能源資料 | `/sites/{id}/summary` 的 `energy` 回 `null` |
| 場域沒有電價方案 | 退回組織的 `reporting_currency`，成本記 0 但仍標得出幣別 |
| 跨場域幣別真的不一致 | 數字照給，`currency` 回空字串 |
| 電價方案的幣別與組織不符 | **儲存時**就擋（`currency_mismatch`，422），不等到出報表 |

## 6. 成本與節費

### 6.1 總計欄位：意義沒有變

`EnergyInterval` 上的三個總計欄位語意**維持不變**，只算市電：

```
energy_cost     = grid_import_kwh × 該時段電價
export_revenue  = grid_export_kwh × 該時段躉售價
estimated_savings = baseline_cost − actual_cost
```

電價由 `Tariff` 的時段定義解析（支援跨午夜的時段）。既有的儀表板、`_totals()`、
跨場域 roll-up 全都讀這三個欄位，所以它們不能改。

### 6.2 分項成本：新的細節層

每個來源實際花了多少，記在 `EnergyIntervalCost`（`interval` × `source` 唯一）。
用哪個模型由 `EnergyAsset.cost_model` 決定，空白時退回角色預設：

| 角色 | 預設模型 | 算什麼 |
| --- | --- | --- |
| `grid_meter` | `grid_tariff` | 購電量 × 時段電價（躉售併入同一列，金額為負） |
| `battery` | `battery_cycle` | 循環衰退（元/kWh 吞吐）+ 充電時買進那些電的成本 ÷ 往返效率 |
| `generator` | `diesel_fuel` | 油耗（L/kWh，可用負載率曲線）× 油價 + 元/運轉小時的維護 |

**未知的 key 會 raise，不會靜默回 0。** 成本靜默歸零是最難發現的錯誤之一。

`basis` 誠實標示可信度：`measured`（參數齊全）、`estimated`（用了預設值或推估的
充電價）、`unknown`。跨區間彙總時取**最差**的那一個——一個推估的區間就讓整個總計
是推估。

### 6.3 節費基準線：可設定，且允許沒有答案

`StoragePlan.savings_baseline` 三選一：

| 值 | 基準線 |
| --- | --- |
| `grid_only` | 什麼都沒裝，全部向台電買 |
| `no_storage` | 同樣的產電量，但沒有電池（預設） |
| `none` | 不算節費 |

兩件事刻意不做：

- **不把負值夾到 0。** 負的節費代表這次調度比什麼都不做還貴。那是真實的結果，
  藏起來等於讓報表替一個錯誤的決策背書。
- **停電期間記 `null`，不記數字。** 市電斷了的時候，柴發與電池的輸出沒有「改買
  市電」這個替代方案，拿市電價當基準是在比較一件不存在的事。目前用「該區間有
  發電機輸出」當作停電的近似——這是近似，不是偵測。


### 6.5 幣別：一個組織一種

`Organization.reporting_currency`（ISO 4217，預設 `TWD`）是整個租戶所有金額的
幣別。

放在組織而不是散在每個 `Tariff` 上，原因是**還沒設定電價的場域根本沒有幣別**。
它的成本是 0，但沒有幣別可標，於是前端把它印成 `0`，隔壁有電價的場域印成 `$0`，
同一欄兩種格式，看起來像壞掉。

三條規則：

| 情況 | 行為 |
| --- | --- |
| 場域沒有電價方案 | 用組織幣別 |
| 場域有電價方案 | 用方案的幣別（正常情況下兩者相同） |
| 多場域彙總且幣別真的不一致 | `currency` 回空字串，數字照給 |

不一致在**儲存電價方案時**就擋下來（`currency_mismatch`，HTTP 422），不是等到
出報表才發現。否則 `reporting_currency` 只會變成第三個會跟另外兩個矛盾的事實
來源。組織幣別留空代表「還沒決定」，此時不擋任何電價——設定過程不該卡住自己。

**匯率換算明確不在範圍內。** 匯率有時間性、有買賣價差、有會計政策，那是另一個
系統的職責。這個欄位說的是「這些數字本來就是什麼幣別」。

設計背景見 [device-classification.md](device-classification.md) §3.12「幣別與
單位」。

## 7. 運轉 session

`DeviceOperatingSession` 記錄一段連續的充電／放電／運轉。**per Device**，事件驅動
的邊界，和 15 分鐘固定網格的 `EnergyInterval` 是兩種粒度，不該互相推導。

`Device` 上另外快取三個 datetime：`last_charge_at` / `last_discharge_at` /
`last_running_at`。只快取這三個，因為它們可以索引——「找出 30 天沒放電的電池」是
一個 `WHERE`。時長與電量去 session 表撈就好。

### 7.1 判定：門檻 + 遲滯 + 最短時長

參數在 `EnergyAsset` 上（符號約定本來就在那裡）：

| 參數 | 預設 | 作用 |
| --- | --- | --- |
| `session_enter_kw` | 額定 × 2%（load 用 5%），下限 0.5 kW | 超過才算開始 |
| `session_exit_kw` | enter × 0.5 | 低於才算結束 |
| `session_min_duration_s` | 60 | 更短的直接丟棄 |
| `session_gap_s` | 300 | 這麼久沒資料就收尾 |
| `session_tracking_enabled` | `False` | 整個關掉；battery 才建議開 |

**遲滯**（enter > exit）是避免假 session 的主要機制：單一門檻遇到在門檻附近震盪的
負載會產生成千上萬筆。程式碼強制 `exit ≤ enter × 0.5`，設反了也不會抖。

**資料中斷**用**最後一個樣本的時間**收尾，`end_reason = "offline"`，能量只計到那裡
為止——中斷期間發生什麼事我們不知道，不往外推。

**還在跑的 session `ended_at` 留 `null`。** 對 24 小時不停的設備這是正確且有用的
答案（「已連續運轉 37 天」），不是缺漏值。

### 7.2 誰來算：排程回算，不是即時狀態機

`manage.py rebuild_sessions --hours 2`，由 `run_scheduler` 每輪呼叫。和
`aggregate_energy` 對稱，理由也一樣：亂序、遲到、重啟這三個問題，回算一次全部消失。
代價是「最後一次充電」最多延遲一個排程週期，而那個數字不需要秒級即時。

回算的左邊界會**往前延伸到跨越邊界的那個 session 的起點**，否則一段長放電會被切成
兩半。

## 7A. 自動調度

`apps/ems/dispatch.py` 把生效中的 `DispatchWindow` 變成真正的命令。

**時段選擇**：`priority` 高的贏；同 priority 由**較晚開始**的贏——所以今天臨時加的
一次性覆寫會蓋過它重疊到的每日排程，不必有人去調數字。

**只在目標值改變時送。** 排程每 5 分鐘跑一次；每次重送同一個設定值等於每 5 分鐘對
硬體發一次 MQTT。引擎用 `idempotency_key` 的 `dispatch:` 前綴認出自己上次送的值。

**運轉限制是真的閘門**，但兩條路徑刻意不同：

| 路徑 | 行為 | 理由 |
| --- | --- | --- |
| 排程 | **夾住**到 `max_charge_kw` / `max_discharge_kw` / SOC 界線 | 方案說 200、時段說 500，不是矛盾，是「跑 200」 |
| 手動 API | **拒絕**（`storage_plan_limit`，422） | 人打了一個數字，安靜地執行另一個更糟 |

SOC 限制**只在讀得到即時 SOC 時**套用。猜一個未知的 SOC 要嘛擋掉合法調度、要嘛放行
深度放電，兩個都不能接受。

引擎走的是同一個 `dispatch_command()`，所以 §3 的每一道關卡對它一樣有效。

## 9. 升級既有安裝要跑什麼

```bash
python manage.py migrate
python manage.py bootstrap --update-existing
```

第二行是關鍵：它依 category 把能力預設值寫進內建 blueprint。沒有它，所有
blueprint 的四個旗標都會是欄位預設值（`can_charge=False`、
`is_dispatchable=True`），電池會無法充電。

**既有資料的歸屬**：

- 所有既有設備 → `commissioning_state = confirmed`，四個能力欄位為 `null`
  （繼承 blueprint）
- 所有既有場域資產 → `include_in_balance = True`（行為不變）
- 所有既有能源區間 → `generator_kwh = 0.0`

既有設備的生命週期歸類（由 migration `0006_device_lifecycle` 的 data
migration 處理）：

- 原本的 `confirmed` → `active`
- 原本手動設了 `is_enabled=False` 的 → `suspended`（保留原意圖，但改用
  生命週期表達，兩個欄位從此不會矛盾）
- 既有宣告：有 diff 的 → `mismatched`，沒有的 → `matched`；`category` 有差異
  的另外標記 `identity_mismatch`

**若現場已經把個別用電設備建成 `load_meter`**，那些場域的 `load_kwh` 在此之前
就是錯的（重複計算）。把個別設備改成 `include_in_balance=False` 之後，需要
重算：

```
POST /api/ems/sites/{site_id}/rebuild-intervals?start=...&end=...
```

單次重算上限 90 天。

### 9.1 加入 session、成本模型與場域權限之後

```bash
python manage.py migrate
```

三件事需要知道：

- **既有 membership 的場域清單是空的**，代表整個組織，所以**沒有人的存取權改變**。
- **session 判定預設關閉**（`EnergyAsset.session_tracking_enabled = False`）。要用
  就逐一開啟——通常只有電池值得開。開完回算歷史：

  ```
  python manage.py rebuild_sessions --hours 720
  ```

- **成本分項要重算才會出現**。`EnergyIntervalCost` 是新表，既有區間裡沒有資料。
  先在需要計價的資產上填 `cost_model` 與 `cost_parameters`，再重算區間。
  `EnergyInterval` 的三個總計欄位語意不變，所以不重算也不會壞掉，只是沒有分項。

> `estimated_savings` 現在可以是 `null`（停電期間沒有基準線）。任何直接讀這個欄位
> 的下游查詢要處理 `null`——`Sum()` 會忽略它，但 Python 端的加法不會。

### 9.2 加入序號唯一性、設備成本與介面偏好之後

```bash
python manage.py migrate
python manage.py bootstrap --update-existing   # 藍圖的多語系說明
```

`uniq_device_org_serial` 是**部分**唯一索引（空白與軟刪除除外）。既有資料若已經有
重複的非空序號，migration 會失敗——這是刻意的，因為那代表同一台硬體被登記了兩次，
需要有人決定留哪一列：

```python
from django.db.models import Count
from apps.devices.models import Device
(Device.objects.exclude(serial_number="")

    .values("organization_id", "serial_number")
```

其餘都是新增的可空欄位與一張新表，既有行為不變。`MQTT_ENABLED` 預設 `1`，所以現有
部署的健康檢查行為也不變。

## 10. 設備替換

### 10.1 什麼時候要替換

硬體換成**不同類型或不同能力**的東西時。同型號的維修、更換零件、重新校正
都不算——那還是同一台設備。

### 10.2 一次呼叫，一個交易

```
POST /api/devices/{old_id}/replace
{"device_id": "ZQS-BESS-0001-R2", "name": "…", "serial_number": "…", "reason": "…"}
```

需要 **ADMIN**。單一交易內完成：

1. 以新 `device_id` 建立接替設備，繼承場域、blueprint、recording policy、座標
2. **搬移所有 `EnergyAsset` 綁定**
3. 搬移 device 層級的 alert 規則（加新的、移除舊的）
4. 舊設備設 `replaced_by` 指向新設備，並轉為 `retired`
5. 發放新的 MQTT 憑證（密碼只回傳一次）
6. 記一筆 audit（`device.replaced`）

回應會回報搬了幾筆資產綁定與幾條規則。

### 10.3 為什麼要一次做完

第 2 步是不能漏的那一步。綁定留在一台不再回報的設備上**不會產生任何錯誤**
——積分回空，場域數字就靜靜地少一塊。如果那是市電總表，整個場域會顯示成
沒有用電。分成多步操作就會出現「舊的停了、新的還沒綁」的空窗。

### 10.4 退役／暫停時的保護

直接把設備退役或暫停時，若仍有 `is_active=True` 的 `EnergyAsset` 綁在上面，
會被擋下：

```
409 device_in_energy_model
details.assets = [{asset_id, role, site}, …]
```

替換流程不受此限——它在同一個交易裡已經先把綁定搬走了。

### 10.5 報表串接

`POST /api/telemetry/series` 加 `"follow_replacements": true`，**預設關閉**。

關閉時：一台設備一條序列，就是資料原本的樣子。
開啟時：整條替換鏈合併成一條邏輯序列，回應的 `device_ids` 列出串了哪幾台。

**串接時同一時刻只取一台，以退役時間為切點。** 每台設備只貢獻
`[前一台的退役時間, 自己的退役時間)` 這個窗口內的資料。

這條規則不是形式主義：退役的硬體常常還在送資料——留在工作台上通電、或只是
還沒拔線——所以兩台在牆上時間會重疊。把重疊相加會**灌水能量、並製造出一個
從未發生過的尖峰**，而且兩者在圖表上都看起來很合理。

預設關閉的理由：串接是一種**解讀**（假設接替設備與前一台等價），不是資料本身。

## 11. 生命週期狀態

### 11.1 五個狀態

| 狀態 | 收 telemetry | 可連線 | 可下調度命令 | 用途 |
| --- | --- | --- | --- | --- |
| `pending` | ✓ | ✓ | ✗ | 自動建檔而來，等待驗收 |
| `active` | ✓ | ✓ | ✓ | 正常運轉 |
| `suspended` | ✗ | ✗ | ✗ | 暫時停用（維修中） |
| `retired` | ✗ | ✗ | ✗ | 已退役，被接替或不再使用 |
| `rejected` | ✗ | ✗ | ✗ | 驗收時判定不該存在 |

`pending` 照常收資料是刻意的：操作者需要看到它實際送什麼，才能判斷這是什麼
東西。

### 11.2 三個旗標的分工

| 欄位 | 回答什麼 | 誰設定 |
| --- | --- | --- |
| `commissioning_state` | 這台處於什麼階段 | 操作者，透過 API |
| `is_enabled` | 要不要收它的資料 | **不再手動設定**——由 service 依生命週期同步 |
| `deleted_at`（soft delete） | 這筆紀錄該不該存在 | 只用於「建錯了，當作沒發生過」 |

`is_enabled` 仍然是 ingest 路徑（ingestor、worker、EMQX auth webhook）唯一
讀的欄位，那條熱路徑沒有改變。改變的是沒有人再單獨設定它，所以「已退役」和
「可以連線」不可能互相矛盾。

**退役絕不使用 soft delete。** 軟刪除會讓設備從 API 消失，歷史就沒有入口了。
退役的設備照常查得到、歷史照常可讀，只是不能連線也不能被指揮。

### 11.3 退役可逆

ADMIN 可以把 `retired` 改回 `active`（硬體確實會從維修廠回來），並留下
`device.restored` 的 audit 記錄。

兩個要處理的情境：

- **接替設備還在服役** → 回 409 `successor_still_active`，要求先把接替設備
  退役或暫停。否則兩台會同時宣稱自己是同一件設備，串接報表就會有歧義。
- **識別碼衝突** → **不會發生**。`device_id` 全平台唯一，而退役的設備從來
  沒有交還自己的識別碼，所以復役永遠不會撞號。

復役時 `retired_at` 與 `replaced_by` 一併清空——它又是現役設備了，留著退役
時間會讓串接報表把它裁掉。

```
POST /api/devices/{id}/lifecycle  {"state": "active", "reason": "…"}
```

## 11A. 設備登記的約束

### 11A.1 序號在組織內唯一

序號識別一台實體設備，所以兩列共用一個序號代表**同一台硬體被登記了兩次**——接著它的
能量會被算兩次，而且兩列都不可信。

三個界定：

- **範圍是組織，不是平台。** 兩個租戶跟同一家廠商買，本來就會拿到相同的序號。
- **空白不比對。** 驗收時序號經常還不知道；強迫填一個佔位字串會比允許空白更徹底地
  破壞這個約束。
- **軟刪除的設備不擋。** 已經除役移除的東西不該阻止重新登記。

資料庫的部分唯一索引是最後防線，API 層另外檢查一次——目的是把**已經在用那個序號的
設備名稱**放進錯誤裡。「是哪一台？」是重複序號唯一會引發的問題。

### 11A.2 能源資產綁定跟著設備走

`EnergyAsset` 說的是「在場域 S，設備 D 供應能量流 R」。D 被登記到別的場域之後，把
綁定留在 S 不是一個過時的細節——它讓 S 的能源平衡繼續依賴一台不在那裡的設備，同時新
場域顯示成完全沒有綁定。**兩個數字都錯，而且都不會叫。**

所以 `PATCH /api/devices/{id}` 改變場域時，綁定一併搬移，並記進稽核 payload。

設備被移出所有場域時，綁定改為**停用**而不是刪除：它沒有地方可以跟過去，必須停止餵養
一個它已經不屬於的平衡，但仍然留著讓人看得出發生過什麼。

目的地已經有同一個 `(device, role)` 綁定時會回 409 而不是靜默刪掉其中一個——那正是
唯一約束存在的理由。

### 11A.3 設備成本

`Device` 上有 `capital_cost` / `cost_currency` / `commissioned_on` /
`expected_life_years` / `annual_maintenance_cost`。

放在設備上而不是藍圖上：這是**這一次採購**的商業事實。同一型號隔兩年買、或走不同
合約買，價格不一樣。藍圖記的是「這是什麼」，這裡記的是「這一台花了多少」。

`annual_cost` = 直線折舊 + 年度維護。**沒有資料時回 `null` 而不是 `0.0`**——零會讓
每一個回收年限看起來都很漂亮。

沒有殘值、沒有折現。兩者都是合理的精算，而且都不該由平台預設：折現率是某個人的財務
政策。

**資本支出不進 `EnergyIntervalCost`。** 它不是「搬運電能」的成本；併進去會讓「這個
區間花了多少」同時代表兩件事，而且會和電池的循環成本重複計算——循環成本本來就已經是
採購價換算成每 kWh 的數字。所以它有自己的端點：
`GET /api/ems/sites/{id}/investment`。

反過來，兩者有一個**正確**的連接：電池資產填了 `warranted_throughput_kwh` 時，
`battery_cycle` 會用 `capital_cost ÷ 保證吞吐量` 算出循環成本，不必有人自己去除。

## 12. 場域權限

存取控制有**三個維度**：哪個租戶（`Organization`）、什麼角色（`Role`）、組織的哪
一部分（`Membership.sites`）。

兩條規則決定它怎麼讀：

- **空清單代表整個組織。** 每個既有 membership 都是這個狀態，所以加上這個維度沒有
  改變任何人的存取權。刻意不是空集合——空集合讀起來是「什麼都看不到」，而那正是
  某天有人搞混這兩者時會把所有人鎖在門外的差別。
- **指定一個場域等於連同它的整棵子樹。** 負責一個廠的人就是負責廠裡的東西；要求
  管理員把每條產線列出來會讓這個功能無法使用，更糟的是——新增一條產線的那天它會
  安靜地出錯。

範圍**不會提升權限**，只跟角色取交集。被限制在單一廠區的 viewer，在那裡仍然是
viewer。

### 12.1 幾個刻意的選擇

| 情況 | 行為 | 理由 |
| --- | --- | --- |
| 範圍外的**設備／告警** | 404 | 「它存在但不是你的」本身就是一則沒有給出的資訊 |
| 範圍外的**場域** | 403 `site_out_of_scope` | 請求者是拿著 id 直接問的，已經知道它存在 |
| **沒有場域的設備** | 受限的人看不到 | 那是新設備在管理員指派之前所在的池子 |
| 受限的 admin 建立場域 | 必須指定範圍內的 parent | 否則新場域會從他自己的清單消失，看起來像存檔失敗了 |
| 受限的 admin 授權他人 | 只能授出自己有的場域 | 否則範圍就自我瓦解了 |
| superuser | 不受限 | 要除錯的東西正是這套範圍時，逃生口必須還能用 |

### 12.2 實作位置

請求進來時在 `AuthContext.site_scope` 展開一次（`None` = 不受限），之後：

```python
ctx.scope_queryset(queryset, field="site_id")   # 收窄清單
ctx.allows_site(site_id)                        # 單筆判斷
ctx.require_site(site_id)                       # 單筆判斷，不通過就 403
```

`field` 是通往場域的 lookup 路徑，所以同一個呼叫適用於 `Site`（`id`）、
`Device`（`site_id`）與經由關聯抵達的（`device__site_id`）。

**時序查詢也要擋。** `POST /api/series` 直接吃 device id，少了這道防線，受限的
使用者只要知道 id 就能讀到整個租戶的資料。
