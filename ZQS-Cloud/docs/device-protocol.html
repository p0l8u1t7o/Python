ZQS Cloud 裝置通訊協定：Sparkplug B（逐步開發指南）¶

設備／閘道器端從零開始接上平台的完整步驟。照順序做，每一步都有「要送什麼 payload」與「怎麼驗收」。

本平台遵循 Eclipse Sparkplug B 規範（namespace spBv1.0）：標示「規範要求」的不是 ZQS 的偏好，是規範本身的規定，改不了；照著做的設備可以直接接上任何 Sparkplug 主機（Ignition、HiveMQ、Cirrus Link…）。伺服器會驗證本文的每一個欄位，不符合的一律拒絕，請把本文視為契約。

機讀版契約

ProtocalBufferPayload/sparkplug_b.proto（線上位元組格式，Eclipse Tahu 原版）與 ProtocalBufferPayload/zqs_profile.proto（本文所有 metric 名稱、型別、命令與回覆的可機讀對照）。用 protoc 產生你的語言的型別，再對照本文組 payload。該資料夾的 README 有各語言指令。

1. 步驟 1：拿到位址與憑證¶

1.1 三層位址¶

spBv1.0/{group_id}/{訊息型別}/{edge_node_id}/{device_id}
        └group     └型別      └邊緣節點       └設備
層級是什麼誰決定
group_id你的組織代碼平台發放，例如 demo
edge_node_id一條 MQTT 連線平台發放
device_id掛在該連線下的一台設備平台發放

最重要的一句話：一條 MQTT 連線 = 一個 edge node。 不是一台設備一條連線。現場典型的樣子是一台 EMS 閘道器對外講 MQTT、對內講 Modbus，底下掛著電池、電錶、變流器：

EdgeNode  ZQS-GW-0001          ← 一組帳密、一條連線、一個 seq 計數器
  ├ Device ZQS-BESS-0001
  ├ Device ZQS-METER-0001
  └ Device ZQS-PV-0001

絕對不要讓兩個行程用同一個 edge_node_id 連線。 它們會共用一個 seq 計數器卻各自遞增，主機看到的是永遠對不上的序號；而且 MQTT 會讓後連上的把先連上的踢掉，兩邊無限互踢。要跑多個行程，就申請多個 edge node。

1.2 沒有閘道器的設備：自己就是 edge node¶

一台自己會講 MQTT 的設備（韌體裡就有 MQTT client 的 PCS、獨立電錶）不需要閘道器。它自己就是 edge node，同時也是掛在自己底下的那台設備。 平台在 POST /api/devices 註冊時會自動建立承載連線的節點，你會拿到：

你拿到的東西值
group_id組織代碼，例如 demo
edge_node_id通常與設備 id 相同
device_id你的設備 id
Usernamenode-<group_id>-<edge_node_id>
Password只顯示一次（用途見附錄 D）

以 ZQS-BESS-0001 為例：

發布  spBv1.0/demo/NBIRTH/ZQS-BESS-0001                  ← 節點宣告
發布  spBv1.0/demo/DBIRTH/ZQS-BESS-0001/ZQS-BESS-0001    ← 設備宣告
發布  spBv1.0/demo/DDATA/ZQS-BESS-0001/ZQS-BESS-0001     ← 讀值
遺言  spBv1.0/demo/NDEATH/ZQS-BESS-0001
訂閱  spBv1.0/demo/NCMD/ZQS-BESS-0001
訂閱  spBv1.0/demo/DCMD/ZQS-BESS-0001/+

你要做的事跟閘道器完全一樣，一個步驟都不能省，只是每種訊息各一則。兩個常見誤解：「只有一台設備能不能只發 NBIRTH？」不行——節點層級的讀值（NDATA）平台不儲存，量測必須掛在 device 層，所以必須有 DBIRTH。「兩層 id 一樣很多餘？」它讓同一份韌體之後裝到閘道器後面時完全不用改。

1.3 允許的字元¶

規範保留 +、#、/ 給 topic 結構。平台再嚴一點：A-Z a-z 0-9 . _ -，長度 3–64 字元。

驗收：拿到三個 id 與帳密後，先用任何 MQTT 客戶端（例如 mosquitto_sub）以該帳密連上 broker 並訂閱 spBv1.0/{group}/DCMD/{node}/+；被拒就回附錄 D。

2. 步驟 2：建立 MQTT 連線¶

項目值
ProtocolMQTT 3.1.1 或 5.0（內建開發 broker 只支援 3.1.1）
BrokerEMQX（正式）／manage.py run_broker（開發）
Port1883 未加密、8883 TLS（正式環境請用 TLS）
Client IDzqs:<edge_node_id>（ACL 可綁定此值）
Username / Password步驟 1 拿到的那組，屬於節點不屬於設備
Keepalive建議 45 s；直接決定斷線多久被發現（附錄 C）
Clean sessiontrue（規範要求）。MQTT 5：Clean Start=true 且 Session Expiry Interval=0
Will（遺言）topic spBv1.0/{group}/NDEATH/{node}、payload 見 2.1、QoS 1、retain false，在 CONNECT 封包裡設定

為什麼 clean session 必須 true：持久 session 會讓 broker 在重連後補送斷線前排隊的命令，而那時節點已經發過新的 NBIRTH、重新宣告過狀態，那道命令會套在已作廢的狀態上。

QoS 與 retain 是規定死的：

訊息QoSRetain
NBIRTH / DBIRTH / NDATA / DDATA / DDEATH0false
NDEATH（遺言）1false
NCMD / DCMD（主機發）0false
STATE（主機發）1true

全是 QoS 0 是因為順序保證來自 payload 的 seq，遺失靠「要求重生」補救；QoS 1 買到的是重複訊息，不是安全。遺言不能 retained，否則它會活得比那次連線更久，節點回來後任何新訂閱者仍會被告知它死了。

2.1 遺言（NDEATH）的 payload¶

NDEATH 的內容只有一個 metric，而且沒有 seq（規範排除：遺言是 broker 在節點無法預知的序號位置代發的）。它必須在 CONNECT 之前就組好，因為遺言要放進 CONNECT 封包；連上之後才設的遺言 broker 從來沒收到過。

Topic     spBv1.0/{group}/NDEATH/{node}      QoS 1，retain false
Payload.timestamp = now_ms                    ← 組 payload 當下的時間（連線前），不是死亡時間
Payload.seq       = （不帶）
metrics:
  bdSeq   Int64   5                           ← 必填，唯一的 metric；與這次連線的 NBIRTH 相同

逐位元組（供手寫編碼器對拍；bdSeq=5、timestamp 省略成 0 便於閱讀）：

08 00                      Payload.timestamp = 0（實際請填 epoch ms）
12 0d                      Payload.metrics，長度 13
   0a 05 62 64 53 65 71    Metric.name = "bdSeq"
   20 04                   Metric.datatype = 4（Int64）
   58 05                   Metric.long_value = 5

三件事要記住：

  • 每次連線 bdSeq +1（0–255 循環），NBIRTH 與遺言用同一個值；重連時要重新組一份新的遺言再 CONNECT。平台用它辨認「這則死亡屬於哪一次 session」，過時的遺言會被忽略，節點不會被自己上一次的遺言打死。
  • 正常關機 broker 會丟棄遺言，所以主動斷線前要自己發一則內容相同的 NDEATH（步驟 10）。
  • 設備層級沒有遺言：DDEATH 由節點自己發（步驟 10），內容只有 timestamp 與 seq，不帶任何 metric。

連線後立刻做的事（順序固定）：

  1. 訂閱 spBv1.0/{group}/NCMD/{node} 與 spBv1.0/{group}/DCMD/{node}/+——先訂閱再宣告，否則空檔進來的命令會漏。
  2. 發 NBIRTH（步驟 4），seq=0。
  3. 每台設備發 DBIRTH（步驟 5）。
  4. 之後才允許 DDATA。

在 NBIRTH 出去之前不可以發布任何東西。 實務上第一則 DDATA 很容易跟 birth 搶跑，因為多數 MQTT 函式庫的「已連線」回呼跑在另一個執行緒；結果是 seq 變成 0、0、1，主機一連上就判定序號有問題。

重連：認證失敗不要密集重連（密碼不會自己修好，broker 會限流），用 1–60 s exponential backoff 加 jitter；每次重連 bdSeq +1、重新走步驟 2→5。

驗收：連上後直接拔網路線，console 應在 ≤ 83 s 內把閘道器標成離線（遺言生效）。若要 180 s 以上才離線，代表遺言沒有在 CONNECT 裡設定。

3. 步驟 3：會組 Payload¶

Sparkplug B 的 payload 是 Protocol Buffers，不是 JSON（規範強制，也是能與其他 Sparkplug 系統互通的原因）。schema 在 ProtocalBufferPayload/sparkplug_b.proto。

3.1 Payload 與 Metric 結構¶

message Payload {
  optional uint64 timestamp = 1;   // epoch 毫秒（UTC）
  repeated Metric metrics  = 2;
  optional uint64 seq      = 3;    // 0–255，每則 +1
  optional string uuid     = 4;
  optional bytes  body     = 5;
}

message Metric {
  optional string name      = 1;   // BIRTH 必填；DATA 可只帶 alias
  optional uint64 alias     = 2;
  optional uint64 timestamp = 3;   // 取樣時間，省略則沿用 payload.timestamp
  optional uint32 datatype  = 4;   // 見 3.2
  optional bool   is_historical = 5;
  optional bool   is_transient  = 6;   // 顯示、評估告警，但不入庫
  optional bool   is_null       = 7;   // 沒有讀值時設 true，不要送 0
  optional MetaData    metadata   = 8;
  optional PropertySet properties = 9; // unit、severity、message、level…（見 5.3、7）
  oneof value {
    uint32 int_value     = 10;
    uint64 long_value    = 11;
    float  float_value   = 12;
    double double_value  = 13;
    bool   boolean_value = 14;
    string string_value  = 15;
    bytes  bytes_value   = 16;
    // DataSet / Template / extension 本平台不使用
  }
}

timestamp 一律 epoch 毫秒；超過未來 5 分鐘或早於過去 7 天會被拒絕——payload 層不合理整則退回，單一 metric 不合理只丟那一個。

3.2 資料型別¶

datatype 是決定怎麼讀 oneof 的唯一依據，填錯 −5 °C 會變 4294967291。

值型別放在哪個欄位
1/2/3Int8 / Int16 / Int32int_value（二補數）
4Int64long_value（二補數）
5/6/7UInt8 / UInt16 / UInt32int_value
8UInt64long_value
9Floatfloat_value
10Doubledouble_value
11Booleanboolean_value
12Stringstring_value
13DateTimelong_value（epoch 毫秒）

沒有讀值時設 is_null = true，不要送 0。「沒讀到」和「讀到 0」是兩件事，整個能量積分都靠這個區別。

3.3 seq：每一則 +1¶

除了 NDEATH，每一則訊息都帶 seq：NBIRTH 為 0，之後每則 +1，255 後回 0。主機靠它發現遺失，發現缺號就要求重生（步驟 9），不會猜。

多執行緒的陷阱。 採集迴圈與命令回覆迴圈都會發布時，序號的配置與送出必須在同一個鎖裡。只鎖計數器不夠：兩個執行緒拿到 7 和 8，卻以 8、7 的順序到達 socket，主機分不出這和遺失有什麼差別。本專案的參考實作也踩過。

3.4 alias：省頻寬¶

BIRTH 時為每個 metric 指派數字 alias，之後 DATA 只帶 alias 不帶名稱：

DBIRTH:  name="battery_soc"  alias=1  datatype=10  double_value=62.0
DDATA:                       alias=1              double_value=78.5

alias 在節點內（node metric）或設備內（device metric）唯一。沒指派也能運作，只是每則都要重複完整名稱。

3.5 Metric 命名空間（ZQS profile）¶

Sparkplug 規定 topic、編碼與狀態機，刻意不規定 metric 叫什麼。以下是本平台的約定，之後每個步驟都會用到：

前綴意義出現在
Properties/…身分與中繼資料（韌體、型號、座標）NBIRTH、DBIRTH
Capabilities/…設備宣稱能做什麼DBIRTH
Ratings/…銘牌額定值DBIRTH
Alarm/<code>故障，Boolean：true 發生、false 解除DDATA（DBIRTH 帶作用中的）
Event/<code>操作記錄，StringDDATA
Command/…命令關聯DCMD 下行、DDATA 回覆
Node Control/…規範定義的節點可寫控制（Rebirth）NBIRTH、NCMD
Device Control/…設備可寫控制DBIRTH、DCMD
其他量測值，進時序資料庫DBIRTH、DDATA

量測值名稱用小寫 snake_case（battery_soc、grid_power_w）。Battery/SOC、Battery SOC 都會正規化成同一個 key，但同一台設備請固定一種。內建 key 見附錄 A。

驗收：用你的編碼器組一則「單一 double metric 的 DDATA」，與參考實作（services/sparkplug/payload.py，或附錄 F 的逐位元組範例）比對位元組完全一致。

4. 步驟 4：NBIRTH（閘道器出生）¶

Topic spBv1.0/{group}/NBIRTH/{node}，連線後第一則訊息，seq = 0。完整 payload：

Payload.timestamp = now_ms
Payload.seq       = 0
metrics:
  bdSeq                  Int64    5          ← 必填（規範）。每次連線 +1（0–255 循環），與遺言相同
  Node Control/Rebirth   Boolean  false      ← 必填（規範）。宣告可接受重生要求
  Properties/Firmware    String   "2.1.4"    ← 以下選填
  Properties/Hardware    String   "GW-500 rev C"
  Properties/IP          String   "10.20.30.40"
  Properties/RSSI        Int32    -63

4.1 bdSeq：讓死亡對得上出生¶

bdSeq 同時出現在 NBIRTH 和 NDEATH（遺言）裡，值必須相同。它解決的是：一則姍姍來遲的遺言可能在節點已重連後才被處理；平台比對 bdSeq，發現這則死亡屬於已被取代的 session 就忽略——否則剛回來的節點會被自己上一次的遺言打死。

NBIRTH  bdSeq=5   ← 這次連線
NDEATH  bdSeq=5   ← 遺言，對應同一次

4.2 NDATA：平台不儲存¶

節點層級的量測值平台接受但不儲存——資料模型裡沒有「屬於一條連線而不屬於設備」的量測。節點的韌體、IP 放在 NBIRTH 的 Properties/。

驗收：console「設備」頁的閘道器變成上線；驗收工具檢查「NBIRTH seq 是否為 0、bdSeq 是否與遺言一致、是否宣告 Node Control/Rebirth」。

5. 步驟 5：DBIRTH（設備宣告）¶

Topic spBv1.0/{group}/DBIRTH/{node}/{device}，每台設備一則。DBIRTH 的定義是「這台設備提供的全部 metric」，不是抽樣，而且每個都要帶當下的數值——主機剛連上就有東西可顯示。BIRTH 沒列出的 alias 會被平台刪除（出生宣告是完整清單，沒列到的就是退役了）。

5.1 完整 payload 範例（電池）¶

Payload.timestamp = now_ms
Payload.seq       = 1                               ← 接在 NBIRTH 之後
metrics:
  # ---- 宣告：身分（Properties/）--------------------------------------------

5.2 宣告「可以說，不能做」¶

宣告的值不會自動生效。 伺服器把宣告原封不動存起來、與目前設定比對差異，等管理者在 console 上接受或拒絕。在被接受之前，它完全不影響這台設備被允許執行哪些命令——一台被入侵的機器無法靠改口宣告替自己解鎖充電權限。內容與上次相同不會重複產生待審核項目，所以每次重連都發是安全的（而重連會很頻繁地重發 BIRTH）。

Properties/Schema Version 是 profile 的版本（metric 的名字就是 schema）；填了平台不認得的版本，宣告會被記錄然後忽略。

5.3 帶上單位，就會即插即用¶

在每個量測 metric 的 properties 帶 unit，平台看到目錄裡沒有的 key 時會直接用出生宣告把它建起來：單位、資料型別、彙總方式全部推出來，一台從沒設定過的設備連上來圖表就有座標軸。可用的 property：

property作用
unit單位字串：W、kWh、degC、%…
kindgauge（預設）、counter、state
description說明文字
display_name顯示名稱
counter_max累計值溢位翻轉的上限，知道就填（回捲時平台記 null 而不是負值）
  • 單位是 kWh、Wh、m3 這類累計單位時自動視為 counter（取差值不積分）；要推翻就明填 kind。
  • 單位是 % 或 degC 會套用寬鬆的合理範圍，超出的照存但標記可疑。
  • 這只建立標籤，不授予權限；已存在的 metric 定義永遠不會被覆蓋。

驗收：console 設備頁顯示上線且量測值有數字；「設備宣告」出現待審核項目；管理者接受後能力旗標生效。驗收工具檢查「BIRTH 有沒有指派 alias」。

6. 步驟 6：DDATA 週期回報¶

Topic spBv1.0/{group}/DDATA/{node}/{device}。只送有變化或到時間的 metric，可只帶 alias：

Payload.timestamp = now_ms
Payload.seq       = 7
metrics:
  alias=1   Double  -11800.0        ← battery_power_w
  alias=2   Double  62.3            ← battery_soc
  alias=6   Double  28.7            ← battery_temperature_c
  alias=4   is_null=true            ← 這一筆沒讀到：送 null，不送 0

規則：

  • 至少每 60 s 送一則 DDATA 當心跳，即使數值沒變。任何上行都會重置「資料已過期」計時器（180 s）；只在變化時才發布的設備在穩態下會被標成資料已過期。伺服器端的 recording policy 決定哪些讀值真的入庫，高頻發布不會塞爆資料庫——不要為了省空間在設備端節流。
  • 累計計數器（kWh）送絕對累計值，不要送差值；回捲由平台依 counter_max 處理。
  • 只想顯示、不想留存的瞬間值設 is_transient = true。
  • 正負號約定（附錄 A）：grid_power_w + 購電 − 逆送；battery_power_w + 放電 − 充電。硬體相反請在平台的能源資產上設「Invert sign」，不要改韌體。
  • 關口電表停電時把 grid_voltage_v、grid_frequency_hz 如實回報為 0，不要用最後有效值填補；平台以「電壓低於方案門檻且持續 N 秒」判定停電，停電期間不下設定點，孤島供電由設備自己完成。

驗收：時序資料頁看得到曲線；儲能頁不顯示「資料已過期」；驗收工具「seq 是否連續」通過。

7. 步驟 7：告警與事件¶

兩者都放在 DDATA 裡，可以和量測值同一則。

7.1 告警 Alarm/<code>¶

name       = "Alarm/E0500"
datatype   = Boolean
value      = true                              ← true 發生、false 解除
properties = { severity: "major",              ← info | warning | major | critical
               message:  "Insulation resistance low",
               resistance_kohm: 41 }           ← 其餘 property 原樣存進告警 details

以相同 code 送 false 即解除；平台會分別通知「🔴 發生」與「🟢 解除」。告警持續期間重複送 true 只累加發生次數。DBIRTH 裡請帶上目前仍作用中的告警，重生後狀態才一致。

7.2 事件 Event/<code>¶

name       = "Event/E0231"
datatype   = String
value      = "Cooling fan speed below threshold"   ← 訊息本文
properties = { level: "warning",                   ← debug | info | notice | warning | error | critical（預設 info）
               fan_rpm: 820 }

事件無狀態，不會「解除」。code 只能含字母數字與 -_。

驗收：告警頁出現該告警、送 false 後自動解除；事件頁有一筆紀錄；若設了 LINE／Email 通知，會收到發生與解除各一則。

8. 步驟 8：接收命令並回覆¶

Sparkplug 把命令模型化為「寫入 metric」且沒有定義回覆訊息。這對設定值夠用，對稽核不夠（無法回答「哪一道命令沒被回應」），所以本 profile 多帶一個關聯 metric Command/ID——仍完全合規。

8.1 收到的 DCMD¶

Topic spBv1.0/{group}/DCMD/{node}/{device}：

Payload.timestamp = 1780000000000
metrics:
  Command/ID          String    "0f9d7a1c-4c1a-4e0e-9a7d-8f2b1c3d4e5f"   ← 回覆時原樣帶回
  Command/Name        String    "set_power_setpoint"
  Command/Expires     DateTime  1780000060000                           ← 過期不要執行，回 expired
  Command/power_w     Double    -200000                                 ← 參數：Command/<參數名>
  Command/valid_until String    "2026-08-23T10:15:00Z"                  ← 選填，見 8.4
  Command/on_expiry   String    "reserve"                               ← 選填

8.2 回覆（DDATA）¶

發一則 DDATA（不是別的型別），建議同一則一併帶上受影響的量測值：

Payload.seq = 8
metrics:
  Command/ID          String  "0f9d7a1c-…"     ← 原樣帶回
  Command/Status      String  "succeeded"      ← accepted | succeeded | rejected | failed | expired
  Command/Message     String  ""               ← 選填：拒絕或失敗的原因
  Command/Result/<key> …                       ← 選填
  alias=1             Double  -200000.0        ← 新的 battery_power_w

執行需要時間的命令先回 accepted，完成後再回 succeeded／failed；終態之後才到的 accepted 會被忽略，順序錯亂不會出事。

8.3 設備端必須做的事¶

  1. 忽略 Command/Expires 已過的命令（回 expired 或不回；伺服器已標記過期）。
  2. 在本地也驗證參數與能力；伺服器雖已依藍圖檢查，設備仍是最後一道防線（負功率需要 can_charge、正功率需要 can_discharge）。
  3. 重複的 Command/ID 視為重送，直接重發前一次的回覆，不要執行兩次。
  4. 命令處理放在獨立事件迴圈，長時間執行的命令才不會阻塞回報——但發布本身要序列化（3.3）。

8.4 設定點有效期與 watchdog（fail-safe）¶

雲端每次下 set_power_setpoint 都可附 valid_until（ISO 8601 UTC）與 on_expiry。設備在該時刻之後不等雲端自行降級：

on_expiry行為
idle功率歸零
hold維持最後設定點（只給確定安全的場合，例如小功率充電）
reserve充到備援水位後停止（SOC 門檻隨方案設定下發）

沒有 valid_until 的命令永不過期（舊行為）。雲端會在到期前重送同一個設定點（新的 valid_until）——刷新就是心跳。設備連續 N 個心跳週期（預設 60 s × 3）沒收到任何設定點、或 MQTT 連線中斷超過同樣時間，就執行離線政策（同三種，預設 reserve）。斷網兩小時不會把電池放乾，靠的是這個而不是雲端。

可用的命令與參數範圍見附錄 B。

驗收：在 console 設備頁下一道 set_power_setpoint，命令頁狀態變 succeeded 且新的功率讀值在下一則 DDATA 出現；下一道 60 s 有效期的設定點後拔掉雲端，61 s 後電池應依 on_expiry 歸零／保持／回充。驗收工具檢查「命令有沒有回覆」。

9. 步驟 9：重生（Rebirth）——唯一的復原路徑¶

不是選配。 沒有實作它的設備在第一次掉訊息之後就再也對不齊了。NBIRTH 必須宣告 Node Control/Rebirth = false（步驟 4）。主機在下列情況會寫入 true：

  • seq 出現缺號（有訊息遺失，對應表可能已不準）；
  • 收到對應表裡沒有的 alias（主機沒看到那次 BIRTH，例如主機比設備晚啟動）；
  • 操作者在 console 手動要求。

收到的 NCMD（topic spBv1.0/{group}/NCMD/{node}）：

metrics:
  Node Control/Rebirth   Boolean  true

要做的事：重新發一次完整的 NBIRTH（seq 歸零、bdSeq 不變）與所有 DBIRTH。 平台對同一節點的重生要求有 30 秒冷卻，不會變成風暴。設備層級的 Device Control/Rebirth 同理，走 DCMD。

驗收：驗收工具「重生要求有沒有被理會」通過；或在 console 設備頁按「要求重生」，觀察 NBIRTH/DBIRTH 重送。

10. 步驟 10：離線與關機¶

正常關機時遺言不會發。 MQTT 規格明訂：送出 DISCONNECT 正常關閉時 broker 會丟棄 will。所以計畫性關機、韌體更新重開、維護斷線都不會觸發遺言——請在主動斷線前自己發：

1. 每台設備  DDEATH  spBv1.0/{group}/DDEATH/{node}/{device}   QoS 0
              Payload.timestamp = now_ms, Payload.seq = 下一個序號, metrics = []（不帶任何 metric）
2. 節點      NDEATH  spBv1.0/{group}/NDEATH/{node}            QoS 1
              Payload.timestamp = now_ms, 不帶 seq, metrics = [ bdSeq Int64 5 ]（與遺言、NBIRTH 相同，見 2.1）
3. 等 0.5 s 讓 broker 收下（有些 broker 會丟棄緊接 DISCONNECT 的 PUBLISH）
4. DISCONNECT

否則這個節點在 console 上會維持「線上」直到逾時掃描（180–225 s）把它撿走。離線判定的三條路徑與實際數字見附錄 C。

驗收：主動關機 ≤ 15 s 顯示離線；拔線 ≤ 83 s。

11. 步驟 11：驗收¶

出貨前跑一次一致性測試。它用真的 MQTT 封包解析你的連線，逐項檢查本文每一條規則，用中文說明哪裡不對、怎麼改：

# 先確認工具本身是對的
python scripts/run_device_test.py self-test

# 再測你的設備（PowerShell 包裝：scripts\test-device.ps1）
python scripts/run_device_test.py device --device ZQS-BESS-0001

檢查項目：clean session、遺言的 topic/QoS/retain/bdSeq、NBIRTH 的 seq 是否為 0、bdSeq 與遺言是否一致、是否宣告 Node Control/Rebirth、BIRTH 有沒有指派 alias、seq 是否連續、命令有沒有回覆、重生要求有沒有被理會。細節見 設備測試工具。

開發完成檢查表：

  • ☐ 遺言在 CONNECT 裡、QoS 1、retain false、bdSeq 與 NBIRTH 相同
  • ☐ 先訂閱 NCMD/DCMD 再發 NBIRTH；NBIRTH seq=0 且是第一則
  • ☐ DBIRTH 帶 Properties/Category、全部 metric、alias、unit、目前值
  • ☐ DDATA ≤ 60 s 一則；沒讀值送 is_null；計數器送絕對值
  • ☐ seq 配置與送出在同一把鎖裡
  • ☐ Alarm/Event 的 properties 帶 severity/message、level
  • ☐ DCMD 回 Command/ID + Command/Status；重複 ID 不重複執行；過期不執行
  • ☐ valid_until 到期／斷線 watchdog 自行降級
  • ☐ 收到 Rebirth=true 重送 NBIRTH + 所有 DBIRTH
  • ☐ 主動關機前送 DDEATH + NDEATH

附錄 C：離線判定的實際數字¶

三條獨立路徑會把設備標成離線，走哪一條由設備端的實作決定：A 設備自己送 NDEATH/DDEATH；B broker 發遺言（keepalive 的 1.5 倍後，45 s → 最遲 67.5 s）；C 伺服器每 30 s 巡檢，最後上行超過 DEVICE_OFFLINE_GRACE_SECONDS（預設 180 s）就翻成離線。console 清單每 15 s 重拉、單一設備頁每 5 s：

情況路徑console 顯示離線
節點主動送 NDEATHA≤ 15 s（設備頁 ≤ 5 s）
斷電、拔線——且有註冊遺言B≤ 約 83 s（67.5 + 15）
正常 DISCONNECT 但沒先送 NDEATHC180–225 s
沒有註冊遺言C180–225 s
broker 自己掛了C180–225 s（所有設備一起）

「離線」（status）與「資料已過期」（last_seen_at 超過 180 s）是兩件事：連線活著不等於資料是新的，一台 PINGREQ 照送但採集迴圈卡死的設備在 broker 眼中完全健康。任何上行都重置這個計時器——所以步驟 6 要求 ≤ 60 s 一則心跳。

附錄 D：帳密與 ACL¶

這組帳密只用來連上 MQTT broker，不是 API 帳號、不能登入 console、不帶組織權限；它回答「這條連線是不是那個 edge node」。帳密屬於節點不屬於設備——一台閘道器前置十二顆電錶只登入一次。

時機動作
註冊閘道器POST /api/edge-nodes
註冊直連設備POST /api/devices（自動建立隱含節點並發憑證）
事後輪替POST /api/edge-nodes/{id}/credential

Password 是 24 bytes 隨機字串，平台只存雜湊；API 回應裡出現的那一次是唯一一次，遺失只能輪替，輪替讓舊密碼立即失效。EMQX 每次 CONNECT 都用 webhook 問平台（POST /api/emqx/auth）——在 console 停用一個節點，下一次連線就被拒；每次 publish/subscribe 也問（POST /api/emqx/acl），強制：topic 在 Sparkplug 命名空間、(group_id, edge_node_id) 屬於這組憑證、方向正確（節點只能發 NBIRTH/NDEATH/NDATA/DBIRTH/DDEATH/DDATA、只能訂閱 NCMD/DCMD）。少了第二項，任何有效憑證都能替鄰居發 NDEATH。

選用的 Client ID pinning：設了 allowed_client_id 後，帳密正確但 client id 不符也拒絕，用來擋「同一組帳密被複製到第二台機器」互踢。認證失敗的原因：密碼錯或已輪替 → 請管理者輪替；節點被停用 → 重新啟用；client id 與 pinning 不符 → 檢查是否為 zqs:<edge_node_id>。

宣告（步驟 5）是「我說我是什麼」，帳密是「我是誰」，兩者刻意分開；宣告不會提升權限。

附錄 E：主機狀態（STATE）¶

平台在 spBv1.0/STATE/{host_id}（預設 zqs-cloud，SPARKPLUG_HOST_ID 可改）發布自己的死活，retained、QoS 1，內容是 UTF-8 JSON（命名空間裡唯一不是 protobuf 的東西）：

{"online": true, "timestamp": 1780000000000}

設備可以訂閱它判斷「現在發出去有沒有人在聽」，不訂閱也可以。

附錄 F：LabVIEW 與手寫編碼器¶

protobuf 沒辦法像 JSON 用字串串接組出來，這是設備端最大的一項工作。三條路：A 現成 protobuf toolkit（VIPM 搜尋 protobuf），把 sparkplug_b.proto 丟進去產生型別，長期最省事；B 手寫編碼器；C 先用參考實作（Python）當橋接把整條鏈路跑通、確認位址帳密都對，再回頭換編碼層——把「協定理解錯」和「編碼寫錯」分開處理。

手寫時 Sparkplug 只用到三種 wire type：0 varint（int/uint/bool/enum）、2 length-delimited（string/bytes/巢狀 message）、1 64-bit／5 32-bit（double/float）。每個欄位前是 varint 的 key：(欄位編號 << 3) | wire_type。「一則帶單一 double metric 的 DDATA」：

Payload.timestamp (欄位1, varint)   → 0x08, varint(epoch_ms)
Payload.metrics   (欄位2, 長度限定) → 0x12, len, <Metric 的位元組>
  Metric.alias        (欄位2, varint) → 0x10, varint(alias)
  Metric.timestamp    (欄位3, varint) → 0x18, varint(epoch_ms)
  Metric.datatype     (欄位4, varint) → 0x20, 10        (Double)
  Metric.double_value (欄位13, 64bit) → 0x69, <8 bytes little-endian>
Payload.seq       (欄位3, varint)   → 0x18, varint(seq)

固定格式的 telemetry 只需要 varint 編碼與 8-byte double 兩個子 VI；實作完一定要對拍。參考實作：services/sparkplug/node.py（序號、alias、生死流程）、services/sparkplug/payload.py（編解碼）、simulator/gateway.py（最精簡的正確閘道器）。其他要點：維持單一持續連線、producer/consumer queue（擷取 → queue → 發布，斷線時 queue 落地稍後回補）、命令在獨立事件迴圈處理、但發布本身序列化。

附錄 G：沒有硬體時的快速驗證¶

.\scripts\sim-console.ps1    # 桌面主控台：登記的設備以 MQTT 客戶端上線

主控台對每台登記的閘道器各開一條連線、底下掛該閘道器的所有設備——這才是 Sparkplug 的正常用法。它發布與本文完全相同的訊息，可當 wire format 的參考實作；主控台還能鎖定物理量或覆寫單一量測值、模擬停電，用來驗證雲端的計算與 fail-safe（見 客戶展示指南 §六A）。
