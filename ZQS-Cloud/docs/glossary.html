專有名詞解釋¶

依主題分組。每個詞先給一句話定義，再說明它在 ZQS Cloud 裡實際對應到什麼（哪個畫面、哪個欄位、哪段程式）。想知道背後的原理請看 技術原理。

1. 設備與通訊¶

名詞 定義 在本系統中
MQTT 一種輕量的發布／訂閱訊息協定。客戶端連到一台 broker，對「主題」（topic）發布或訂閱訊息，彼此不直接連線。 設備與平台之間唯一的資料路徑。開發環境用內建 broker（zqs-broker，port 1883），正式環境用 EMQX。
Broker MQTT 的訊息中樞，負責收下發布的訊息並轉給訂閱者。 MQTT_HOST / MQTT_PORT；模擬器主控台上可直接改 IP／Port 連任何 broker。
QoS（Quality of Service） MQTT 的送達保證等級：0 最多一次、1 至少一次、2 恰好一次。 遙測用 QoS 0（掉一筆無妨）、NDEATH 與主機狀態用 QoS 1（不能掉）。見 services/sparkplug/topics.py。
Retain（保留訊息） broker 記住某主題最後一筆訊息，新訂閱者一連上就收到。 只有主機 STATE 訊息保留；遙測不保留，否則新連線會讀到舊值。
Last Will（遺囑訊息） 客戶端連線時預先交給 broker 的一則訊息；連線異常中斷時由 broker 代為發布。 每台閘道器的遺囑就是它的 NDEATH。注意：正常 DISCONNECT 會讓 broker 丟棄遺囑，所以乾淨關機必須自己發 NDEATH。
Sparkplug B Eclipse 制定的 MQTT 應用層規範：規定主題結構、protobuf 格式的 payload、上線／離線流程、序號與別名。讓不同廠商的設備能被同一個主機理解。 本平台的唯一設備協定，namespace spBv1.0。完整說明見 裝置通訊協定（Sparkplug B）。
Group ID Sparkplug 主題的第二層，一群邊緣節點的邏輯分組。 = 組織的 slug（例如 zqs-demo）。租戶隔離的第一道。
邊緣節點（Edge Node / EoN） Sparkplug 裡「一條 MQTT 連線」的身分：擁有自己的序號計數器與生死訊息。通常是現場的閘道器。 「閘道器」頁面的每一列；模型 EdgeNode。一台閘道器一條連線，兩個程式自稱同一個 node id 會互踢。
閘道器（Gateway） 現場把 Modbus／RS-485 等本地協定轉成 MQTT 上雲的那台設備。 本系統把「閘道器」與「邊緣節點」當同一件事；整合說明頁可登錄、發憑證、要求重生。
設備（Device） 掛在邊緣節點底下、被它代為上傳的一台實體裝置（PCS、電表、逆變器…）。 模型 Device；Sparkplug 主題第五層 device_id。
NBIRTH / DBIRTH 節點／設備的「出生證明」：連線後先發，宣告所有指標的名稱、型別、別名與目前值。 平台靠 DBIRTH 自動登錄指標（即插即用）；設備也在這裡宣告自己是什麼（DeviceDeclaration）。
NDATA / DDATA 節點／設備的遙測資料，之後每次只送變化的指標。 擷取管線 → worker → TelemetrySample（歷史）與 LatestSample（最新值）。
NDEATH / DDEATH 節點／設備的「死亡」訊息，代表離線。 收到後設備狀態變 offline；NDEATH 會連帶把該節點底下所有設備標離線。
NCMD / DCMD 主機送給節點／設備的命令。 平台的「控制指令」走 DCMD；回覆（ack）則是設備用 DDATA 帶回 Command/ID、Command/Status。
bdSeq（Birth/Death Sequence） 每次連線遞增一次的序號，同時出現在 NBIRTH 與 NDEATH，用來判斷一則死亡訊息屬於哪一次連線。 舊連線遲到的 NDEATH 不會把剛重連的節點打離線（「superseded session」）。
seq（Sequence Number） 每則訊息遞增（0–255 循環）的序號，用來偵測漏訊。 漏號 → 平台要求重生（rebirth）而不是猜。
別名（Alias） DBIRTH 裡替每個指標配一個整數，之後 DDATA 只送整數不送名稱，省頻寬。 別名表存在資料庫（MetricAlias），行程重啟不會失憶。
重生（Rebirth） 主機要求節點重新發 NBIRTH/DBIRTH。 漏號、別名對不上、或操作者在整合頁按「要求重生」時送 Node Control/Rebirth。Sparkplug 唯一合法的復原手段。
即插即用（Plug-and-play） 設備第一次出現時，平台從 DBIRTH 自動建立指標定義。 INGEST_AUTO_PROVISION 控制是否連設備也自動登錄；預設只登錄指標，設備要先登記。
設備宣告（Declaration） 設備在 DBIRTH 裡自稱的類別、能力與身分。 只能「說」，不能自動生效：平台顯示但不採信，需人工驗收（§4 of 系統邏輯總覽）。
憑證（Credential） 閘道器連 broker 用的 MQTT 帳號密碼。 登錄閘道器時產生，密碼只顯示一次；可輪換。正式環境由 EMQX 以 webhook 向平台驗證。

2. 能源與計費¶

名詞 定義 在本系統中
表後儲能（Behind-the-meter, BTM） 裝在用戶電表「後面」（用戶側）的電池，對台電來說只看得到電表的淨值。 整個系統的主題：電池充放電改變的是關口電表讀數，因此改變電費。
關口電表（PCC meter） 用戶與電網交界處（Point of Common Coupling）的電表，台電計費依據。 能源資產角色 grid_meter；正值 = 購電、負值 = 躉售。
能源資產（Energy Asset） 把一台設備綁到一個能源角色（市電電表／負載電表／光電／電池／充電樁／發電機），並指定它的功率與電量指標。 儲能頁「綁定資產」。沒有綁定，該場域的能源平衡、成本、節費全部是空的。
能源平衡 負載 = 市電 + 光電 + 電池放電 − 電池充電 + 發電機。 apps/ems/aggregator.py；沒有負載電表時由其他項推導。
結算區間（Energy Interval） 把連續的功率讀值積分成一段固定時間（預設 15 分鐘）的 kWh 與費用。 EnergyInterval；所有圖表、報表、節費的基礎單位。
15 分鐘需量（Demand） 台電計費用的「15 分鐘平均功率」（kW）；整月最高的那一段就是最高需量。 peak_import_kw、總覽頁需量費表的「實際最高需量」。
契約容量（Contract capacity） 用戶向台電申請的用電上限（kW），決定基本電費。 儲能方案欄位 contract_capacity_kw；超過就是「超約」。
超約（Over-contract） 最高需量超過契約容量。台電對超過部分加倍計費：10% 以內 2 倍、超過 3 倍。 apps/ems/demand.py 的 excess_charge()；總覽頁「含避免超約」金額。
基本電費（Demand charge） 依契約容量或最高需量、以每 kW 每月費率計的固定費用。 電價方案欄位 demand_charge_per_kw；為 0 時需量費表顯示「電價未設基本電費」。
流動電費（Energy charge） 依用電度數（kWh）× 單價計的費用。 區間的 energy_cost = 購電 kWh × 該時段單價。
時間電價（TOU, Time-of-Use） 依尖峰／離峰時段給不同單價的電價方案。 電價方案頁；內建台電 114 年表燈二段式、三段式、低壓電力二段式。
尖峰／離峰 TOU 裡單價高／低的時段；台電另分夏月（6–9 月）與非夏月。 方案的 periods；策略以「今天最貴／最便宜的時段」判斷。
契約容量管理（Demand cap） 策略：需量快超過上限時放電壓低，離峰再充回。 DispatchStrategy.DEMAND_CAP；對台灣用戶通常是最值錢的策略。
時間電價套利（TOU arbitrage） 策略：離峰便宜時充電、尖峰貴時放電，賺價差。 DispatchStrategy.TOU_ARBITRAGE；價差低於門檻不動作。
光儲自發自用（Self-consumption） 策略：光電餘電先充進電池、傍晚放給自己用，少躉售。 DispatchStrategy.SELF_CONSUMPTION。
需量反應（Demand response, DR） 電力公司臨時要求用戶減少用電的事件，配合可獲補償。 儲能頁「需量反應」卡片可觸發事件，優先於方案策略。
SOC（State of Charge） 電池目前電量百分比。 指標 battery_soc；方案的 SOC 上下限是策略的硬邊界。
SOH（State of Health） 電池健康度百分比（剩餘容量相對出廠）。 指標 battery_soh。
PCS（Power Conversion System） 電池與電網之間的雙向變流器，平台下的設定點就是下給它。 設備類型 bess-pcs；命令 set_power_setpoint（W，正放電負充電）。
設定點（Setpoint） 平台要求 PCS 維持的功率值。 調度引擎每 60 秒算一次，只在目標變動時重送。
往返效率（Round-trip efficiency） 充進去 1 kWh 能放出多少（約 0.85–0.92）。 方案欄位；節費計算時扣除損耗。
自發自用率 / 自給率 光電發出的電有多少自己用掉 ／ 自己的用電有多少不靠市電。 儲能頁兩個百分比卡片；公式見 技術原理。
節費基準線（Savings baseline） 「如果沒有電池會花多少」的假想情境，節費 = 基準線 − 實際。 方案欄位 savings_baseline：no_storage（同光電無電池）或 grid_only（什麼都沒裝）。負值不隱藏。
運轉區段（Operating session） 一段連續的充電／放電／運轉期間，由門檻與遲滯判定。 儲能頁「運轉紀錄」；資產上的 session 參數。
成本模型（Cost model） 把某來源的能量換算成金額的規則。 battery_cycle（循環成本）、diesel_fuel、grid_tariff、grid_export；資產上可選。

3. 平台與操作¶

名詞 定義 在本系統中
組織（Organization） 一個租戶。所有資料以組織隔離。 = Sparkplug group id；設定頁可改名稱、時區、幣別。
場域（Site） 一個用電地點；可有父子關係（園區 → 廠房）。 場域頁；方案與電價沿場域樹繼承，子場域可覆寫。
儲能方案（Storage plan） 一組具名的策略與限制（契約、SOC 範圍、功率上限、電價），綁到一或多個場域。 儲能規劃頁；是模板，不是場域的附屬品。
調度引擎（Dispatch engine） 每個週期依方案策略算出每個場域電池的設定點並送命令的程式。 manage.py run_dispatch，由 run_scheduler 每 60 秒呼叫。
排程調度時段（Dispatch window） 人工指定「幾點到幾點強制充／放／待命」，生效時優先於策略。 儲能頁「排程調度」。
警報規則（Alert rule） 指標超過門檻持續一段時間就產生警報的規則，含遲滯與冷卻。 警報規則頁；警報解除時也會通知。
遲滯（Hysteresis） 解除門檻與觸發門檻之間的差距，避免在臨界值附近反覆觸發。 規則欄位；遲滯太寬（≥ 帶寬一半）會讓警報永不解除，表單會擋。
通知管道（Notification channel） 警報／事件的送達方式：Email、LINE 機器人、Webhook、MQTT。 規則頁下方；每個管道有「測試發送」。
設備事件（Device event） 設備自己回報的事件或警報（Event/<code>、Alarm/<code> 指標）。 事件紀錄頁；警報型事件標「發生／解除」。
記錄策略（Recording policy） 決定哪些指標要存歷史、存多密（死區、最小／最大間隔）、存多久。 記錄策略頁；可綁設備類型或單台覆寫。
死區（Deadband） 變化量小於此值的讀值不存歷史（但最新值永遠更新）。 記錄策略規則。
工作流程（Workflow） 在畫布上畫的控制邏輯：條件判斷、計時、命令、跳轉、子流程。 工作流程頁；引擎設計見 工作流程引擎設計手冊。
乾跑（Dry run） 完整評估流程但不送任何命令。 編輯器「測試」按鍵。
分支（Token） 工作流程裡一個同時執行中的路徑；多個起點或一個輸出多條線就是多個分支。 並行上限以分支計（WORKFLOW_MAX_CONCURRENT_RUNS）。
稽核紀錄（Audit log） 誰在什麼時候做了什麼（登入、改設定、下命令…）。 稽核紀錄頁。
API 金鑰 給外部系統呼叫 API 用的長效憑證。 設定頁；權限與角色相同。
角色（Role） owner / admin / operator / viewer 四級權限。 operator 可下命令不能登錄設備；viewer 只能看。
SSE（Server-Sent Events） 伺服器主動推送的單向 HTTP 串流。 整個 console 的即時更新（/api/live/stream）與工作流程執行監看。
Rollup 把結算區間再彙總成日／月／場域樹的統計。 build_rollups；報表與父場域加總。
模擬器（Simulator） 獨立的 MQTT 客戶端程式，照 fleet.json 扮演閘道器與設備。 scripts\sim-console.ps1；與平台只共用線上格式。
