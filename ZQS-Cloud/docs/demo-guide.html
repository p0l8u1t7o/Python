客戶展示指南¶

一條指令把資料庫重建成「多場域、多設備、策略各異」的展示租戶，設備透過 MQTT（Sparkplug B）真實上傳、真實接受指令，儲能的受益數字由平台從實際調度結果算出來，不是寫死的。

一、準備（展示前 2 分鐘）¶

.\scripts\reset-demo.ps1            # 清空資料庫 → 重建 → 7 天歷史 → 啟動整個堆疊
.\scripts\reset-demo.ps1 -HistoryDays 30 -NoStart   # 只重建，歷史 30 天

完成後開 http://127.0.0.1:5173，帳號：

角色 帳號 密碼
管理員 admin@example.com ChangeMe-2026!
值班工程師（operator） operator@example.com 同上
管理階層（viewer） viewer@example.com 同上

堆疊包含：內建 MQTT broker、API、擷取管線、工作流程引擎、排程器（能源彙總 + 調度引擎，每 60 秒）、前端。啟動後所有設備都是離線的——展示開始前開 .\scripts\sim-console.ps1 按「全部上線」，20 台設備就以 MQTT 客戶端連上來；按「全部離線」可以當場示範離線偵測。

契約容量刻意訂在各場域自然尖峰之下：A 棟自然尖峰約 760 kW、契約 680 kW，沒有儲能就會超約，所以契約容量管理的效益一目了然。

三、建議的展示流程（約 15 分鐘）¶

1. 設備真的在上傳（地圖 / 設備頁，2 分鐘）¶

  • 地圖頁：四個場域、20 台設備全部在線。
  • 任選一台儲能 PCS 進設備頁：每 5 秒更新一次，SOC、功率、溫度、PCS 狀態都在動；資料走的是 Sparkplug B DDATA，不是平台模擬。
  • 打開閘道器頁面可看到 NBIRTH / DBIRTH 的指標宣告。

2. 設備接受指令（設備頁 → 指令，3 分鐘）¶

  • 在任一 PCS 的設備頁下達 set_power_setpoint，例如 power_w = -200000（充電 200 kW）。
  • 指令狀態在一秒內變成 succeeded（設備 ack），電池功率隨即變成 −200 kW，SOC 開始上升，同一場域的市電電表取用量同步上升 200 kW——這就是「表後」：電表看到的是負載 − 光電 − 電池。
  • emergency_stop 會讓電池立刻歸零並覆寫任何設定點。

3. 策略自動調度（儲能規劃頁，3 分鐘）¶

  • 儲能規劃頁：四個方案、各自綁定的場域。點開「園區契約容量管理」，看得到 A 棟是繼承、B 棟是覆寫。
  • 調度引擎每 60 秒評估一次。展示時可手動跑一次乾跑看決策與理由： 
    .venv\Scripts\python.exe manage.py run_dispatch --dry-run
    輸出類似 HSINCHUA-BESS-01: 95000 W demand 745.0 kW over ceiling 650.0 kW。
  • 引擎真的下指令後，設備頁的指令列表會出現發出者 dispatch-engine，電池功率跟著變。

週末電價全日離峰，時間電價套利策略在週末「不動作」是正確行為（價差為 0）；若展示日是週末，台中廠房當天不會套利，但歷史資料裡的工作日都有。

3b. 工作流程範例（工作流程頁，3 分鐘）¶

六個可直接執行、畫布上附註解的範例（apps/core/showcase_workflows.py）：

名稱 場域 示範的節點與模式
削峰與低電量保護 A 棟 兩條並行分支、條件計時（連續 30 秒）、設定點歸零、每 30 秒迴圈
離峰充電排程 A 棟 跨午夜時間窗（22:30–06:30）、電量判斷、等待節點

建議現場示範「需量反應演練」：執行 → 看節點依序亮起（動畫連線）→ 指令列表出現 ack → 台中電表取用下降 300 kW → 120 秒後恢復。迴圈型流程會一直跑到手動停止；它們和調度引擎都會對同一台電池下設定點，展示時二擇一（停用該場域方案，或只看流程的動作），避免兩個控制者互相覆寫。

4. 後續計算與受益（總覽頁，5 分鐘）¶

  • 總覽頁「各場域電費與節費」：時間範圍切到 7 天。
  • 長條圖：電費 vs. 節費（能源面：與「同樣光電、沒有電池」的基準線比較，可能為負，不隱藏）。
  • 下方表格 需量費受益：每個場域的契約容量、未調度最高需量、實際最高需量、降低需量、需量費受益（含避免超約罰款）。A 棟約 760 kW → 650 kW，一週估算受益數萬元；台北總部同理。
  • 儲能頁（各場域）：能源區間、充放電 kWh、SOC 曲線、成本來源分解。
  • 報表頁：rollup 後的日/月彙總，父場域「新竹科學園區」會把 A、B 棟加總。

5. 事件與告警（告警頁，2 分鐘）¶

  • 模擬器帶 --faults：每隔一段時間隨機一台設備送出事件（Event/Alarm）。
  • 告警規則：SOC 過低、電池／PCS 溫度過高、市電電壓異常、各場域超過契約容量。
  • 通知管道範例（Webhook，預設停用）示範通知佇列。

四、常用指令¶

# 獨立設備模擬器（堆疊啟動後所有設備都是離線的；在這裡按「全部上線」）
.\scripts\sim-console.ps1            # 首次會先從平台匯出 simulator\fleet.json
.\scripts\sim-console.ps1 -Export    # 平台登記變動後重新匯出

# 調度引擎
.venv\Scripts\python.exe manage.py run_dispatch --dry-run

# 重新產生歷史（不清設備）
.venv\Scripts\python.exe manage.py generate_history --days 7 --interval 300 --clear --with-faults

模擬器與平台完全解耦：只靠 simulator/fleet.json 與 MQTT，主控台上可改 broker IP／Port，並能看每台設備當下送出的量測值。物理模型：每個場域一組負載曲線（廠房兩班制、辦公上班時段）、太陽曲線、電池 SOC 積分與上下限；電網功率 = 負載 − 光電 − 電池，因此任何指令都會立刻反映在電表上。「電池自主削峰」選項讓電池在平台尚未下設定點時自己削峰；預設是完全聽平台的，以突顯調度引擎的作用。

五、展示前的自我檢查¶

.venv\Scripts\python.exe scriptserify_calculations.py     # 3,300+ 項數字交叉比對（API 彼此一致）
cd frontend; npx playwright test                             # 70+ 項 e2e：每頁、每個按鍵、畫面數字 = API 數字、三語、角色

verify_calculations.py 檢查：總覽總計 = 各場域加總、需量費受益可由尖峰／契約／費率重算、場域摘要 = 區間加總、每個區間的電費／節費可由 kWh 與單價重算、即時功率流平衡（市電 = 負載 − 光電 − 電池）、今日數字 = 各場域加總、父場域 = 子樹加總、自發自用率／自給率、投資攤提。e2e 的 numbers.spec.ts 再確認總覽與儲能頁顯示的數字與 API 相同；buttons.spec.ts 逐頁按下每一個非破壞性按鍵並要求無錯誤、無 5xx。

e2e 會在 A 棟留下一台延遲探針設備（LAT-PROBE-0001）與少量測試資料。展示前請再跑一次 .\scripts eset-demo.ps1 還原乾淨資料。

六、受益數字怎麼算¶

  • 能源面節費（estimated_savings）：每個結算區間，「同樣負載、同樣光電、沒有電池」的電費 − 實際電費。充電時為負、放電時為正，整週加總為淨效益。
  • 需量費受益（demand_savings）：區間平均需量取窗口內最高值；(未調度最高需量 − 實際最高需量) × 方案電價的每月基本電費費率，加上避免的超約罰款（台電規定：超約 10% 以內 2 倍、超過 3 倍）。窗口為整月時即為帳單數字，其他窗口為估算。
