技術原理¶

這份文件解釋為什麼系統這樣運作——每個機制背後的電力、通訊與軟體原理，以及它在本系統中的落點。名詞定義在 專有名詞解釋，實際行為規則在 系統邏輯總覽。

1. 資料怎麼從設備到畫面¶

flowchart LR
  D[設備 / 閘道器] -->|Sparkplug B over MQTT| B[(Broker)]
  B -->|訂閱 spBv1.0/#| I[Ingestor]
  I -->|記憶體／Redis 匯流排| W[Worker]
  W --> T[(TelemetrySample 歷史)]
  W --> L[(LatestSample 最新值)]
  W --> A[警報引擎]
  L -->|0.5 s 掃描| S[SSE live feed]
  S --> C[Console]
  1. 設備只跟 broker 說話。 它不知道平台在哪裡、有幾台；它只發布到約定的主題。這就是為什麼模擬器可以完全獨立、為什麼換 broker 只要改一個 IP。
  2. Ingestor 只做「收與驗」。 解 protobuf、檢查租戶（group id 必須是已存在的組織）、大小上限，然後放進匯流排。它不碰資料庫，所以再大的流量也不會卡在 DB 上。
  3. Worker 做所有有狀態的事。 序號檢查、別名解析、指標自動登錄、寫歷史與最新值、死區、事件、警報評估、命令回覆比對。一批一批處理（批次 = 一次從匯流排取出的訊息），所以同一批內的順序很重要——死亡訊息必須贏過同批較早的資料（這是實際踩過的坑）。
  4. 畫面不輪詢。 Console 開一條 SSE 連線，伺服器每 0.5 秒問資料庫「自上次以來誰變了」，只推送變動的 id，前端只重抓那幾個查詢。量到 MQTT 發布到畫面更新約 0.3–0.6 秒。

2. Sparkplug B 為什麼比「自訂 JSON」好¶

問題 自訂 JSON 的下場 Sparkplug B 的解法
設備離線怎麼知道？ 靠逾時猜，要等幾分鐘 NDEATH 遺囑：broker 在連線斷掉的瞬間代發；加上 bdSeq 分辨是哪一次連線的死亡
訊息有沒有漏？ 不知道 seq 0–255 循環；漏號就要求 rebirth 重新宣告，不猜
每筆都帶欄位名稱很肥 是 別名：DBIRTH 宣告一次名稱↔整數，之後只送整數
新設備要改平台程式 是 DBIRTH 宣告指標（名稱、型別、單位），平台自動登錄
不同廠商格式不同 每家寫轉換器 規範固定主題與 protobuf schema，任何 Sparkplug 主機都讀得懂
命令怎麼確認執行了 自己發明 規範沒定 ack，本平台以 DDATA 帶 Command/ID + Command/Status 回覆（見 裝置通訊協定（Sparkplug B） §5）

生死流程（每一條連線）：

CONNECT（帶遺囑 = NDEATH, bdSeq=n）
→ NBIRTH(bdSeq=n, seq=0) → DBIRTH… (seq=1,2…)
→ DDATA… (seq 遞增)
→ 正常關機：DDEATH… → NDEATH(bdSeq=n) → 等 0.5 s → DISCONNECT
   異常斷線：broker 代發 NDEATH(bdSeq=n)

兩個細節是實際踩出來的：正常 DISCONNECT 會讓 broker 丟棄遺囑，所以乾淨關機一定要自己發 NDEATH；而某些 broker 會把緊跟著 DISCONNECT 的 PUBLISH 丟掉，所以發完 NDEATH 要等一下再斷線。平台另有 180 秒的逾時掃描當保險。

3. 能源平衡與積分¶

每個場域的瞬時功率滿足：

負載 = 市電 + 光電 + 電池放電 − 電池充電 + 發電機

平台的正負號約定：市電正值 = 購電，電池正值 = 放電（對外供電）。設備若相反，在資產綁定勾「反轉正負」。

功率（kW）變成電量（kWh）靠梯形積分：相鄰兩筆讀值的平均功率 × 間隔時間。累積電量指標（*_energy_kwh）若存在，優先用計數器差值，因為它是電表自己的積分、不受取樣間隔影響；計數器回繞（例如 32 位元溢位）用 Metric.counter_max 修正。

為什麼是 15 分鐘區間：台電以 15 分鐘平均功率計需量，用同樣的粒度結算，區間的 peak_import_kw 才能直接對應帳單上的數字。

4. 電費與儲能的受益從哪裡來¶

台灣工業電費 = 基本電費（依契約容量／最高需量，每 kW 每月）+ 流動電費（kWh × 時段單價）+ 超約罰款 + 功率因數調整。表後儲能能動的是前三項：

受益來源 原理 系統怎麼算
削減最高需量 尖峰時放電，關口電表的 15 分鐘平均下降 → 月最高需量下降 → 基本電費下降 demand_savings = (未調度最高需量 − 實際最高需量) × 每 kW 費率；未調度需量 = 負載 − 光電（同一區間）
避免超約 超過契約的部分 10% 內 2 倍、超過 3 倍計費；壓在契約下就沒有罰款 excess_charge()：分段計算基準線與實際的罰款差
時間電價套利 離峰 2.4 元充、尖峰 5.9 元放，扣掉往返損耗仍有價差 每個區間 estimated_savings = 基準線電費 − 實際電費，整段期間加總
光電自用 餘電躉售價低於購電價；存起來晚上自己用，省的是購電價 自發自用策略；節費同樣由基準線比較算出

節費為什麼可能是負的：充電的區間實際電費比基準線高（多買了電），放電的區間才賺回來。單看一天（尤其週末電價全日離峰）會是負的，整週才是淨效益。系統不把負值藏起來，因為藏起來的報表會替壞決策背書。

需量費的窗口問題：費率是「每月」的，但畫面可以選任意窗口。系統把窗口內最高需量用月費率計價——窗口正好是整月時就是帳單數字，其他時候是估算，頁面上有註明。

5. 策略為什麼要看「場域自己的需量」¶

契約容量管理的判斷式是「需量 > 上限就放電」。但電表讀值已經包含電池自己的功率：電池充電 120 kW 會把電表推高 120 kW，下一輪引擎看到超約就改放電，再下一輪又看到空間改充電——追自己的尾巴。

所以策略先還原場域本身的需量：native = grid + battery（放電為正，放電會壓低電表），再拿 native 跟上限比。離峰回充的上限也只到契約的 95%，免得夜間充電本身變成當月最高需量。這兩條都是實機觀察到震盪後才加的。

策略每 60 秒評估一次（正式環境 300 秒），用的是 15 分鐘需量與電價段落的時間尺度，不是毫秒級的 PCS 控制迴路——那是 PCS 自己的事。

6. 警報：門檻、持續、遲滯、冷卻¶

一條規則要同時回答四個問題，少一個就會誤報或漏報：

  • 門檻（threshold）：超過多少算異常。
  • 持續（for_duration）：要連續超過多久才算——過濾瞬間尖峰。實作是「從第一次超過起算，中途回落就重計」，跟 PLC 的 on-delay timer 相同。
  • 遲滯（hysteresis）：回到門檻以下多少才算解除——避免在門檻附近反覆觸發／解除。
  • 冷卻（cooldown）：解除後多久內不再重新觸發。

「沒有讀值」永遠不等於 0：一台斷線的設備功率不是 0，是未知；拿 0 去比 power < 100 會讓安全聯鎖在設備斷線時反而觸發。條件判斷在沒讀值或讀值過舊時走「無讀值」分支，工作流程與警報引擎都一樣。

7. 工作流程引擎：為什麼是 token 不是執行緒¶

畫布上的流程可能要跑幾天（「守住設定點直到條件解除」）。用執行緒實作，行程重啟就全部消失。本引擎把每一個分支的位置存在資料庫（WorkflowToken），引擎每 2 秒被叫醒一次、把能動的 token 各推一步、寫回、返回——沒有任何東西停在 Python 堆疊上。重啟後從資料庫的位置繼續。

由此衍生的規則：Jump 讓出一個週期（否則迴圈是 busy-wait）、分支抵達已有分支的節點就合流（否則跳回分岔點會指數成長）、等待是「停車到某時刻」不是 sleep、條件計時每個週期重取樣。完整設計與踩過的坑見 工作流程引擎設計手冊。

8. 即時性：SSE 與輪詢的取捨¶

方式 延遲 成本 本系統
前端每 5 秒輪詢 最差 5 秒 N 個查詢 × 5 秒 × N 個分頁 只剩 fallback
SSE（一條連線，伺服器每 0.5 秒查變化） ~0.5 秒 一條連線；伺服器每 0.5 秒一次索引查詢 目前作法
WebSocket + Redis pub/sub ~10 ms 需要 ASGI 與 Redis 正式環境升級路徑

誠實的說法：伺服器端仍然在「查」資料庫（worker 在另一個行程、SQLite 沒有跨行程通知），省下的是 HTTP 往返與無謂的重抓，不是查詢本身。Windows 時鐘 15 ms 一跳，比較時間用 >= 而不是 >，否則同一跳內寫入的列會漏掉。

9. 模擬器的物理模型¶

模擬器不是在「回放數字」，而是在跑一個最小的電廠模型，所以平台下的每一道命令都會產生後果：

  • 負載：依場域類型（廠房兩班制／辦公上班時段／園區）的 24 小時形狀 × 尖峰 kW，週末打折，±2% 雜訊。
  • 光電：06:00–18:00 的正弦曲線 × 裝置容量（× 天氣因子，歷史產生器才有）。
  • 電池：依平台最後一次設定點出力，受額定功率與 SOC 上下限限制；SOC 以實際搬動的能量積分。
  • 電表：grid = load − pv − battery。

因此「引擎下放電 300 kW」→「電池功率 +300 kW、SOC 下降」→「電表購電少 300 kW」→「下個結算區間的需量與電費變低」→「總覽頁受益增加」是一條真實的因果鏈，不是四個各自編的數字。

10. 多租戶與安全邊界¶

  • 租戶 = 組織 = Sparkplug group id。訊息的 group id 不是已存在的組織就丟棄並記錄——不會有「預設租戶」接住錯投的資料。
  • 場域範圍：成員可被限制只看到某幾個場域（含子場域）；API 查詢一律經 scope_queryset。
  • 命令閘門：每個命令依名稱與參數值決定需要哪種能力（可充電／可放電／可輸出／可調度）；工作流程與調度引擎送命令走的是和人手相同的 dispatch_command()，不是特權路徑。
  • 憑證：每台閘道器一組 MQTT 帳密，EMQX 以 webhook 向平台驗證並套 ACL，設備只能發布自己的主題。
